## 一、取 digest（二选一）

### 方式 A（推荐）：一键脚本

```bash
# 0) 先看环境与最近几次 CI（只读）
bash script/deploy/deploy-backend-image.sh status

# 1) 解析本次 e491b64 那次 CI 产出的 digest（只打印 digest，诊断信息走 stderr）
bash script/deploy/deploy-backend-image.sh resolve
```

脚本按这个优先级取 digest：① 你显式给的 `DIGEST=`；② 那次 CI 的**运行日志**里
`sha-<sha>: digest: sha256:<64hex>`；③ `docker buildx imagetools inspect`（取 `Manifest.Digest`）。
两种情况会直接**拒绝继续**（fail-closed）：CI 结论不是 `success`；或日志里解析出多个候选 digest 不唯一。

### 方式 B：手工看 CI 的 Job Summary

GitHub → **Actions → "Compile, test and build image"（`ci.yml`）** → 选 **head commit = `e491b64…`** 的那次 →
**Job Summary** 里应有：

```
### Published image
`ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-e491b64…`
Digest: `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:…………（64 位）`
```

**必须先满足**：该次运行 `status = success`，且 Job Summary 里真的有 `Digest:` 那一行。
没有 ⇒ **停止，不要发布**（先看 CI 为什么没产镜像）。

## 二、派发发布

### 方式 A（推荐）：脚本（默认干跑，`--apply` 才真的发）

```bash
# ① 干跑：只打印将要部署的那串不可变 digest + 等价的 gh 命令，不动任何东西
bash script/deploy/deploy-backend-image.sh deploy

# ② 确认上面那串 digest 无误后，真正派发 + 轮询到结束
bash script/deploy/deploy-backend-image.sh deploy --apply

# 若宿主磁盘预检失败（根分区 <3GB / df 读不到），由你判断后再放行：
bash script/deploy/deploy-backend-image.sh deploy --apply --allow-unknown-disk

# 也可以直接指定 digest（例如从 Job Summary 抄来的）
DIGEST=sha256:<64位> bash script/deploy/deploy-backend-image.sh deploy --apply
```

### 方式 B：手工 `gh`

```bash
gh workflow run deploy-poc.yml --repo Ningchirsty/hotter-ai-platform --ref main \
  -f image=ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64位>
gh run list --workflow=deploy-poc.yml --limit 3
gh run watch <run-id> --exit-status
```

### 方式 C：手工 curl（没有 `gh` 时）

```bash
: "${GITHUB_TOKEN:?需要一个有 actions:write 的 token}"
curl -sS -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H 'Accept: application/vnd.github+json' \
  https://api.github.com/repos/Ningchirsty/hotter-ai-platform/actions/workflows/deploy-poc.yml/dispatches \
  -d '{"ref":"main","inputs":{"image":"ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64位>"}}'
# 之后用 Actions 页面（或同样的 curl 查 runs）看结果
```

> ⚠️ 无论哪种方式，**输入里都必须带 `image`**（必填、无默认），否则会被工作流第一步的正则挡下——
> 这是刻意的，正是为了不让"照默认点下去"发成旧镜像。

## 三、这条工作流会做什么（不用你干预）

`deploy-poc.yml` 在切镜像**之前**会：校验镜像形状 → **宿主容量预检**（根分区 <3GB 或读不到就拒绝，
除非显式 `allow_unknown_disk`）→ checkout →（可选）预装归档 →
★**Prepare additive runtime schema：重放 23 份"只新增"脚本**（2026-10-12 起从 12 份补齐，
含此前漏掉的 11 份 `aig_*` 补列迁移）→ `sudo /usr/local/sbin/hotter-release backend "$IMAGE"`
（只切服务、失败自动回滚代码；契约明确**不** `docker compose down`、不删卷、不导 SQL、不恢复数据）。

细节与"它明确不会做什么"见 `15-后端镜像发布操作指导.md` §三。
