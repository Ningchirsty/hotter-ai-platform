## 一、先说结论：要做的就三件事

| # | 做什么 | 谁做 | 卡不卡发布 |
|---|---|---|---|
| 1 | 在目标库执行 **11 份 `aig_*` 脚本**（顺序见 §三） | 有库权限的运维 | **必须，且在发布后端之前** |
| 2 | 补 3 个**生产配置**（`aigov.model-crypto.*`，与 snail-ai 对齐） | 运维 | **必须**，否则治理台录不了密钥 |
| 3 | 发布**后端 + 前端**镜像（治理台有界面改动，前端必须一起发） | 按既有 workflow | 常规 |

> ⚠️ **发布入口不会执行 SQL**（与人才库那次同一个坑）。脚本必须人工执行，见 §三。

**另一个必须先知道的点**：`aigov` 的配置在仓库里**一处都没有**（我 grep 过全部 `application*.yml`），
所以生产全靠**显式配置 + 代码默认值**。默认值对"能跑"是够的，但对"能用"不够——
`aigov.model-crypto` 不配，治理台就无法录入模型密钥（见 §四）。

## 三、步骤 1：在目标库执行脚本（**发布后端之前**）

### 3.1 本次预演的证据（先看这个再动手）

在全新 MariaDB 实例（临时 datadir + 独立端口 3410，未碰任何既有库）上按下面的顺序执行：

```
13 份脚本 第一遍执行 → 13/13 exit=0
第二遍重跑（除安装类菜单脚本）→ 全部 OK（幂等）
```

即：**除两份平台基座脚本与 `aig_ai_gov_menu.sql` 外，其余脚本都可以安全重跑。**

### 3.2 脚本与顺序

```bash
# 平台基座（全新库才需要；存量库跳过）
script/sql/ry_vue.sql                        # sys_* 表（含 sys_menu/sys_role/sys_dict）
script/sql/ry_ai.sql                         # sai_* 表（模型主数据，治理层只读它）

# 本模块
# ⚠️ 存量库**不要**跑 aig_ai_gov.sql：它是 drop table + create table（不是 if not exists），
#    重放会清掉 aig_capability / aig_model_governance / aig_capability_model /
#    aig_route_policy / aig_invocation_audit（含追加型审计，不可恢复）。
#    存量库的正确做法见下面「按环境选路径」的第二种。
script/sql/aig_ai_gov.sql                    # 治理 5 张表 + 场景绑定表【仅全新库；存量库跳过】
script/sql/aig_ai_task.sql                   # 统一任务 5 张表（create table if not exists，幂等）
script/sql/aig_task_execution_mode.sql       # 迁移：aig_task.execution_mode 列（幂等；存量行回填 PLATFORM，调度器只碰 PLATFORM）
script/sql/aig_ai_gov_menu.sql               # 菜单/角色/字典【安装类：纯 insert，非幂等，只跑一次】
script/sql/aig_ai_gov_menu_migration.sql     # 增量：模型新增权限点（幂等）
script/sql/aig_ai_task_menu.sql              # 增量：任务菜单与权限（幂等）
script/sql/aig_data_level_strict.sql         # 字典增加 STRICT 第 4 级（幂等）
script/sql/aig_model_capability_tags.sql     # 迁移：capability_tags 列（幂等，自带存在性判断）
script/sql/aig_model_cost_limit_amount.sql   # 迁移：cost_limit_amount 列（幂等）
script/sql/aig_route_scenario_binding.sql    # 迁移：场景绑定表 + 审计 scenario_code（幂等）
script/sql/aig_audit_provider_usage.sql      # 迁移：审计 provider_id/usage_json/input_snapshot_ref（幂等）
script/sql/aig_provider_bluocto.sql          # 种子：bluocto 供应商 + 7 个图像模型 + 能力 + 策略 + 绑定（幂等，但**默认打开外部图像通路**，见脚本头）
```

**按环境选路径：**

- **全新库**：从上到下全跑一遍（14 份）。
- **存量库**（已装过平台，或跑过任意版本的 `aig_ai_gov.sql`）：
  **跳过 `ry_vue.sql` / `ry_ai.sql` / `aig_ai_gov.sql`**，只跑后面那些**增量**脚本
  （`aig_ai_task.sql`、`aig_task_execution_mode.sql`、`aig_ai_gov_menu_migration.sql`、`aig_ai_task_menu.sql`、
  `aig_data_level_strict.sql`、5 份 `*_migration` 式的列/表迁移、`aig_provider_bluocto.sql`）。
  5 份迁移脚本会先查 `information_schema` 再决定是否 `ALTER`，**在全新库上跑也只是空转**（已实测），
  所以两类环境可以共用同一套增量脚本，不必纠结跑没跑过。
  > 创作域侧的任务接线脚本（`dp_generation_aig_task_id.sql` 等）不在本清单，见
  > `08-WP3剩余三项-服务器执行说明.md` §一；跑它之前必须先有内容模块的 `cp_content.sql`。
- **`aig_ai_gov_menu.sql` 只跑一次，且只在全新库上跑**：它是 97 条纯 `insert`（固定主键），
  重复执行会在**第一条**就 `ERROR 1062 Duplicate entry`（`sys_dict_type.PRIMARY`），
  而且 mysql 批处理遇错即退——**指望"重跑一次补齐菜单"是走不通的**。
  已经装过的环境，缺的菜单/授权靠 `aig_ai_gov_menu_migration.sql` 与 `aig_ai_task_menu.sql`
  这两份**可重复执行**的增量脚本补齐；若要补的是 `aig_ai_gov_menu.sql` 里独有的行，
  把该文件的 `insert into` 批量改成 `insert ignore into` 后再跑（只插差集，不动既有行）。

### 3.3 在服务器上怎么执行

```bash
# 1) 确认后端实际连的库（不要凭猜）
sudo docker exec <backend容器> env | grep -i -E 'datasource|mysql|url' | sed 's/:[^:@]*@/:***@/g'

# 2) 把脚本送进容器并按顺序执行（库名以实际配置为准）
for f in aig_ai_gov aig_ai_task aig_ai_gov_menu aig_ai_gov_menu_migration aig_ai_task_menu \
         aig_data_level_strict aig_model_capability_tags aig_model_cost_limit_amount \
         aig_route_scenario_binding aig_audit_provider_usage aig_provider_bluocto; do
  sudo docker cp script/sql/$f.sql <mysql容器>:/tmp/
  sudo docker exec -i <mysql容器> sh -c \
    'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 <库名> < /tmp/'$f'.sql' \
    || echo "FAILED: $f"
done
```

> **带 `--default-character-set=utf8mb4`**：这些脚本里有中文注释与中文菜单名，
> 不指定字符集在部分客户端上会写进乱码（乱码写进 `sys_menu.menu_name` 会直接显示在界面上）。

> **这段循环是「全新库」的路径**：它第一项就是 `aig_ai_gov`（drop + create）。
> **存量库请先把 `aig_ai_gov` 从循环里去掉再跑**（见 §3.2 的破坏性警告）——
> 特别注意：该脚本重放时**照样返回 exit=0**，所以循环里的 `|| echo "FAILED"` **拦不住它**，
> 数据已经被清掉而日志一片正常。这是本手册里最容易造成不可恢复损失的一步。

## 四、步骤 2：生产配置（**只有 3 个是必须的**）

### 4.1 必须配：`aigov.model-crypto.*`（与 snail-ai 逐字节一致）

| yml 键 | 环境变量（Spring relaxed binding） | 生产要求 | 不配的后果 |
|---|---|---|---|
| `aigov.model-crypto.secret-key` | `AIGOV_MODEL_CRYPTO_SECRET_KEY` | **必须与 snail-ai 的 `snail-ai.crypto.secret-key` 完全一致**（32 个 hex 字符 = 16 字节） | 与 snail-ai 不一致 → 治理台写进去的密文 **snail-ai 解不开**，模型静默不可用 |
| `aigov.model-crypto.iv` | `AIGOV_MODEL_CRYPTO_IV` | 同上，与 `snail-ai.crypto.iv` 一致 | 同上 |
| `aigov.model-crypto.enabled` | `AIGOV_MODEL_CRYPTO_ENABLED` | 要**在治理台录入密钥**就必须 `true` | `false` 时治理台拒绝录入/清除密钥，密钥只能去 snail-ai 管理端配 |

> ⚠️ **`enabled=true` 但 `secret-key`/`iv` 为空 → 应用启动直接失败**（刻意的自检：
> 宁可起不来，也不要"密钥写进去但别人解不开"在运行期才暴露）。要么三项都配，要么
> `enabled` 保持 `false` 且两个密钥也不填。
>
> ✅ **配完看启动日志里的 `fingerprint`**（形如 `fingerprint=8fa13a559078`），
> 与 snail-ai 侧日志中的同一值比对：**不一致就说明两边参数不同，此时任何密文都解不开**。
> 这个指纹是 key+iv 的 SHA-256 前 12 位，不泄漏密钥本身。

### 4.2 建议确认（默认值可用，但要知道含义）

| yml 键 | 默认 | 说明 |
|---|---|---|
| `aigov.external-api.enabled` | `true` | 关闭后直连外部网关的调用器不可用 |
| `aigov.external-api.image-response-format` | `url` | **必须保持 `url`**：bluocto 实测（网关不支持该字段会直接 400）。拿到 URL 后调用器会立刻下载成字节，不依赖 URL 长期有效 |
| `aigov.external-api.image-timeout-ms` | `180000`（3 分钟） | **实测单张约 69–76 秒**；若上游更慢再调大 |
| `aigov.external-api.image-max-bytes` | `8388608`（8MB） | 实测产出 6.1MB，通过 |
| `aigov.retry.enabled` / `max-attempts` / `base-backoff-ms` / `max-backoff-ms` | `true` / `3` / `200` / `2000` | 只对"可重试"类生效（限流/超时/服务不可用） |
| `aigov.route.require-model-tags` | `false` | `false`＝未声明标签的模型放行并写提示；补齐标签后可改 `true` 收紧 |
| `aigov.route.require-model-cost` | `false` | 同上，针对"未声明单次成本上限" |
| `aigov.callback.secrets.<providerCode>` | 空 | 目前不需要：bluocto 是同步返回、无回调。**但未配密钥的回调一律拒绝**（这是刻意的） |
| `aigov.task.scheduler.enabled` | **`false`** | 见下 |
| `aigov.task.scheduler.timeout-seconds` | `1800` | 在途任务超时阈值（**别设太小**：一次出图就要 70 秒级） |
| `aigov.scheduling.enabled` | `false`（**生产为 `true`**） | 调度子系统启用点：注册 `@EnableScheduling`。**不打开它，所有 `@Scheduled` 任务都不会跑且无任何报错**（见 4.2 下方"调度启用点"） |
| `aigov.model.health-probe.enabled` | `false`（**生产为 `true`**） | 是否**允许**模型健康探测（只决定"允许"，不决定"谁触发"）。`only-bound=true` ⇒ 只测有绑定的模型；`stale-hours=6` ⇒ 同一模型 6 小时内不复测，故稳态外呼 ≈ 每个外部模型每 6 小时 1 次 |
| `aigov.model.health-probe.interval-ms` | `1800000`（30 分钟） | `fixedDelay` 语义：实际间隔 = 本轮耗时（实测约 133 秒）+ 该值。**首轮在容器启动后立即执行**（未设 `initialDelay`） |

**关于任务调度器（`aigov.task.scheduler.*`）**：默认 **关闭**，因为它是可选的多实例安全组件。
两条触发路径，任选其一：

1. **应用内定时**：置 `aigov.task.scheduler.enabled=true`，**并且**容器必须启用了调度
   （见下方"调度启用点"）。
2. **外部 cron / 任务平台**：保持 `false`，由外部按周期调
   `POST /aigov/task/scheduler/sweep`（需 `aig:task:operate`）。

> **⚠️ 勘误（2026-10-08 实测）**：本节此前写着"已核实 `ruoyi-admin → ruoyi-job →
> `ruoyi-common-job` 这条链带 `@EnableScheduling`，所以生产上这个开关是有效的（不需要额外加注解）"。
> **这句话是错的**，而且错得很隐蔽：那条依赖链确实存在，但 `ruoyi-common-job` 的
> `SnailJobConfig` 上是
> `@AutoConfiguration` + `@ConditionalOnProperty(prefix="snail-job", name="enabled", havingValue="true")`
> 与 `@EnableScheduling` **写在同一个类上**——`snail-job.enabled=false`（生产即如此）时
> **整个配置类都不生效，`@EnableScheduling` 也随之失效**。
> 后果是：三个 `@Scheduled` 任务（任务扫描 / 审批超时扫描 / 模型健康探测）在生产**一个都不会跑，
> 且不会有任何报错**——只是"什么都没发生"。**只把开关置 true 是不够的**，这正是当时没被发现的原因。

### 调度启用点（2026-10-08 新增）

| 项 | 内容 |
|---|---|
| 启用点 | `AigSchedulingConfig`（`ruoyi-ai-gov`）上的 `@EnableScheduling`，由 `aigov.scheduling.enabled` 门控 |
| 生产取值 | `true`（`application-prod.yml`） |
| 生效范围 | 注册的是**全局**后处理器；本仓共 3 个 `@Scheduled`（全在 `ruoyi-ai-gov`），其中任务扫描与审批超时扫描各自被自己的开关门控且生产为关闭 ⇒ **实际只激活"模型健康探测"一个任务** |
| 另一条路径 | `snail-job.enabled=true` 也会带来 `@EnableScheduling`，但生产**没有部署 SnailJob server**（17888 不可达），打开只会在启动时连不上 |
| 已知代价 | 探测单轮实测约 133 秒，**占用 1 个调度线程**。本仓 `@Scheduled` 跑在 `ruoyi-common-core` 的 `ThreadPoolConfig` 定义的那个全局 `ScheduledExecutorService` 上（核心线程数 = `availableProcessors()+1`，线程名 `schedule-pool-%d`；生产实测线程名即 `schedule-pool-1`，8 核 ⇒ 9 线程），**不是** Spring Boot 默认的单线程调度器；`spring.task.scheduling.pool.size` 在本仓**不参与**调度，不要用它来调 |

它负责两件事：`RETRY_WAIT → QUEUED` 的重试驱动，以及"卡在途"的超时判定（多实例抢锁，抢输的计 `skipped`）。
**不做这两件事，失败任务会一直停在"等待重试"**。

### 4.3 明确不要动

- `aigov.snail-ai.*`（`enabled=false` 默认）：这是走 snail-ai 内部路径的开关，本次用直连调用器，不需要开。
  若要开启，注意**阶段2 起不再有 `agent-id` 这个配置**：改为按路由选中的模型反查 Agent
  （`sai_agent.chat_model_id`），查不到就明确失败——详见 `docs/aigov/draft/SPEC-AI治理层阶段1.md` 的
  「模型 ↔ Agent 错配」一节。可选配置 `aigov.snail-ai.app-id`：只接受该作用域（或本地执行）的 Agent；
  开启后**调用前还会核对客户端身份**（`snail-ai.app-id` 必须存在于 `sai_app` 且启用、
  `snail-ai.token` 与库中一致），不一致就报出来而不是等超时；模型连通性测试也会先报这段结论。
- `aigov.package.store-body`（默认 **false**）：Package 包体是否留存到对象存储，见附录 A.6；
- `aigov.package.security.*`（**默认全开、默认值够用**）：注册 Package 时的**包体内容安全检查**阈值。
  这是唯一一处"读的人容易关掉它"的配置，所以下面逐项写明。**代码里的默认值就是生产口径**
  （`AigPackageSecurityProperties`；`application.yml` 里刻意没有这段，改它要显式写配置）：

  | 配置项 | 默认 | 含义 / 超过会怎样 |
  |---|---|---|
  | `aigov.package.security.enabled` | `true` | 包体扫描总开关。**关掉等于回到"包体从头到尾没人看"**——那是 F-02 之前的状态，见下方警告 |
  | `.max-entries` | `2000` | 单个包体允许的最大条目数，超过按 zip bomb 形态拒绝（`UNBOUNDED_CODE_EXECUTION`） |
  | `.max-total-bytes` | `268435456`（256MB） | 解压后总字节上限 |
  | `.max-entry-bytes` | `67108864`（64MB） | 单个条目解压后字节上限 |
  | `.max-compression-ratio` | `200` | 单条目最大压缩比（解压后/压缩后）。文本类资源正常在 10:1 上下，经典 zip bomb ≥1000:1 |
  | `.sniff-bytes` | `4096` | 每个条目读进来做**魔数嗅探**的字节数上限 |
  | `.max-text-scan-bytes` | `8388608`（8MB） | **第二切片新增**：每个条目做**凭据特征全文扫描**的字节上限。超出部分不扫，结论里会写"只扫到上限"（不把"扫了一部分"说成"全文扫过了"） |
  | `.reject-non-zip-archives` | `false` | **第二切片新增**：非 ZIP 压缩包形态（gzip/bzip2/xz/7z/rar/cab/tar）是否直接拒绝。**默认 false = 维持原行为**（只报告形态、不拒绝）；要收紧上传口准入策略时把它改成 `true`，不必改代码 |

  > **⚠️ 关掉 `aigov.package.security.enabled` 意味着什么**：包体内容**完全不再被检查**。
  > 一个 Manifest 干净、但包里塞了 `install.sh` 或 ELF 的包会被**照单收下**——这不是"降级运行"，
  > 而是把 F-02 那道检查整个拿掉。这个开关存在的意义只有一个：**某个客户端的合法包被误拦时，
  > 运维先开门再定位**。因此：
  > 1. 关闭时服务端会**打出 warn**（扫描器里显式记录），别把它当静默开关；
  > 2. 定位完必须**立刻改回 `true`**，并在发布记录里写明这次开关的时间窗；
  > 3. 关闭期间上传的包，**事后没有任何证据行**可以回查（`aig_package_rejection` 只在拒绝时留痕）。
  >
  > **它检查什么、不检查什么**（别把"开了"读成"全查了"）：查 ZIP 形态（`PK` 魔数）、路径穿越/
  > 绝对路径/盘符/反斜杠、**符号链接与特殊文件**（自解中央目录读 Unix 模式位）、脚本扩展名与
  > ELF/PE/Mach-O/class 魔数、私钥与 `docker.sock`/`id_rsa`/`AWS` 凭据特征（**扫到 8MB/条**）、
  > 条目数/体积/压缩比、以及**中央目录声明条目数与实际条目数是否一致**。
  > **不查**：被编码或拆分的凭据（base64 过的私钥、把 `AKIA` 拆成两段）、超出 `max-text-scan-bytes`
  > 的正文、非 ZIP 形态的**内容**（默认只报告形态，除非把 `reject-non-zip-archives` 打开）、
  > 以及**任何"跑起来会做什么"**——平台不执行包里的东西，执行外部代码的前提是沙箱运行时（P1-003）。
  >
  > **排查被拒的上传**：被拒时**不登记任何包**（`aig_package` / `aig_package_version` 都不增行），
  > 证据在 `aig_package_rejection` 一行：`reject_reason`（`ARCHIVE_UNSAFE` / `MANIFEST_INVALID` /
  > `CHECKSUM_MISMATCH`）、`hit_rules`（如 `UNBOUNDED_CODE_EXECUTION`）、`body_sha256` 与
  > `body_size`（对方到底交了什么）、`operator_id`。**按 `body_sha256` 查**最准确。
- `aigov.model-test.*`：连通性测试的超时与重试，默认够用。

### 4.4 宿主机 docker 代理配置（**2026-10-10 做过一次变更，必读**）

**变更**：`/etc/systemd/system/docker.service.d/http-proxy.conf` 里指向 **运维工作站** 的
`HTTP_PROXY` / `HTTPS_PROXY` 两行被**注释掉**（保留 `NO_PROXY`，并把各镜像仓库域名补进 `NO_PROXY`）。
原文件已备份为同目录下的 `http-proxy.conf.bak-<时间戳>`。

**为什么改**（实测，不是推测）：

- 该配置把 docker daemon 的所有 HTTPS 出站指向 `http://192.168.2.144:7897` —— 那是运维工作站上的
  一个 `netsh` 端口转发（`192.168.2.144:7897 → 127.0.0.1:7897`），而**该端口后面已经没有任何进程**
  （工作站上只有一台已停止的 WSL 发行版）。
- 后果：**任何不在 `NO_PROXY` 里的镜像拉取都失败**，不止 ghcr。
  发布日志原话：`read tcp 192.168.2.134:33236->192.168.2.144:7897: read: connection reset by peer`。
  一次前端发布因此失败（**失败发生在替换容器之前，生产未受影响**——`ruoyi-web` 仍是旧容器）。
- 宿主机自身**直连可用**：`https://ghcr.io/v2/` 返回 401（= 到达注册表，只是未认证），
  `https://github.com/` 返回 200。也就是说这个代理不是"必须的"，而是让发布**依赖运维工作站开机**。

**为什么可以安全重启 dockerd**：该宿主机 `LiveRestoreEnabled=true`，重启 dockerd **不会**杀掉运行中的容器
（本次实测：重启前后都是 11 个运行中容器，`Up` 时间未被重置）；且长驻服务都是 `restart: unless-stopped`。
重启后各容器健康探针短暂显示 `health: starting`，约一个探针周期后回到 `healthy` —— 那不是重启，是探针状态重置。
发布脚本有前置断言 `backend is not healthy → die`，所以**等健康探针恢复再发布**。

**回退**（如果哪天证明必须走代理）：

```bash
sudo cp -a /etc/systemd/system/docker.service.d/http-proxy.conf.bak-<时间戳> \
           /etc/systemd/system/docker.service.d/http-proxy.conf
sudo systemctl daemon-reload && sudo systemctl restart docker
```

**运维注意**：发布链路的镜像拉取现在**不再依赖任何工作站**。如果将来又有人在宿主机上配 HTTP(S)_PROXY，
请同时确认该代理真的活着，并把镜像仓库域名放进 `NO_PROXY`——否则发布会在 `docker pull` 这一步失败，
而报错信息（`connection reset by peer`）看起来像网络抖动，不像配置问题。

> 同一台运维工作站上 git 也配了指向同一个已死代理的 `http.proxy`（表现为 `git push` 报
> `Failed to connect to github.com port 443 via 127.0.0.1`）。那是工作站的用户级配置，本次**没有改动**，
> 只在需要推送时用一次性参数绕过：`git -c http.proxy= -c https.proxy= push origin main`。

## 五、步骤 3：录入 bluocto 的密钥（**脚本里刻意不写密钥**）

`api_key` 是 SM4 密文列。**不要在 SQL 里填明文**，也不要用别的工具随便加密——
必须与 snail-ai 的 `CryptoHelper` 逐字节一致。正确路径是让服务端加密落库：

**方式 A（一次覆盖整个供应商，推荐）**：治理台 →「模型注册中心」→ 供应商管理 → 「批量配密钥」。
**方式 B（API）**：

```bash
curl -X PUT 'https://<生产域名>/aigov/model/secret/batch' \
  -H 'Authorization: Bearer <你的登录 token>' \
  -H 'Content-Type: application/json' \
  -d '{"providerId": <bluocto 的 sai_model_provider.id>, "apiKey": "sk-…"}'
```

- 需要权限 `aig:model:secret`；
- `modelIds` 不传 = 该供应商下**全部已登记模型**（含停用模型）；
- 明文只加密**一次**再复用（SM4/CBC 固定 IV 下，与逐行加密逐字节等价——有单测钉着这条等价性）；
- 传 `modelIds` 时若混入别家模型 → **整批拒绝**（避免"以为在改 A 家，实际把 B 家的凭据覆盖了"）。

**录完立刻验证**：治理台 →「模型注册中心」→ 该模型 → 「连通性测试」。
预期通过。若返回 401/403，先看是**密钥错**还是**余额不足**——现在这两种错误分类是分开的：
`QUOTA_EXCEEDED`（额度/余额不足，去充值）与 `AUTH_FAILED`（鉴权失败，换密钥），
审计的 `error_summary` 会带上上游原文。

    | `QUEUED` | `DISPATCHED` | 内核已接单（登记那一刻就落 `DISPATCHED`，此处是不变式） |
    | `RUNNING` | `RUNNING` | 同名同义 |
    | `SUCCEEDED` | `SUCCEEDED` | 任务侧 `SUCCEEDED` 的定义本就是「执行成功（**待复核，≠通过**）」，与「已出图」同义 |
    | `FAILED` | `FAILED` | `error_code` 记 `UNKNOWN`（内核错误码未与平台分类对齐，**不猜**；会转人工） |
    | `TIMEOUT` | `FAILED` | 任务侧没有超时态，归到可重试的超时分类 `TIMEOUT` |
    | `CANCELED` | `CANCELLED` | 同名同义 |
    | `APPROVED` / `REJECTED` | **两步**：`REVIEW_PENDING → APPROVED`/`REJECTED` | 任务侧有「`APPROVED` 必经 `REVIEW_PENDING`」这条既有不变式；`SUCCEEDED` 的本意就是「等复核」，所以这一步**不是伪造**；两步同事务，中间态对外不可见 |

    **三条刻意的取舍**：㈠**登记与候选入库同一事务**（登记失败整笔失败）——静默不登记
    ＝产出了一份没有治理账的产出，正是本模块一路在堵的口子；㈡**回写挂在「状态真的变了」这个钩子上，
    且失败不拖垮刷新**——`queryPage`（打开列表）也会调刷新，挂在入口就会「看一眼列表＝反复写任务事件」，
    回写是观测面，出错不该让创作域刷新失败，但必须 `WARN` 留痕；㈢**失败不回落到平台的重试/转人工**——
    EXTERNAL 任务用普通 `transition(...→FAILED)`，**不**走 `recordFailure`（那会按可重试分类算出
    `RETRY_WAIT`，而平台不会重试业务域的任务，治理台就会显示一个「等待重试」却永远没人重试的任务）；
    创作域的「重试」是**新建候选**（新的一行 → 新的一条任务）。
    **已知边界（未做）**：没有 `traceId`（`dp_generation` 本来就没有 invoke trace，**不伪造**）；
    回写是**拉模式**，只有刷新观测到变化才写，内核不会主动推；`register` 之后若候选被回退到
    `REJECTED` 等再改判，任务侧按状态机判可迁移才写，不可迁移时只 `WARN` 不改状态。
  - 存量侧不变：`IAigTaskMirrorProvider`（aigov 侧 SPI，注册分发）+ `CreativeTaskMirrorProvider`
    （creative 侧实现，读 `dp_generation` 的**已落库状态**，恒只读）。已知代价：镜像不刷新内核实时状态、
    可能滞后（该 provider 自述）。**新登记的任务与镜像读的是同一张 `dp_generation`，不会出现两套事实**；
    镜像保留是为了让**接线之前的历史候选**在治理台仍可见。
- ✅ **任务失败原因现在真的落列**（2026-10-08，做上面这条接线时发现并修）：
  `aig_task.error_code` / `error_message` 两列此前**全表无人写入**，而治理台任务列表与详情
  **都在渲染它们**（`frontend/src/views/aigov/task/index.vue` 第 139/232 行）——即那两处**恒为空**；
  更刺眼的是平台侧 `recordFailure(taskId, version, errorClass, errorMessage)` **明明收到了**
  错误分类与原因，却只把它们拼进事件说明字符串，从不写这两列。
  修法：新增 `IAigTaskService#transition(..., errorClass, errorMessage)` 重载——
  目标为 `FAILED` 时写入（分类为空按 `UNKNOWN` 记，**不假装知道**）、为 `SUCCEEDED` 时**清空**
  （成功还挂着上一次尝试的旧错误码比没有更坏；MyBatis-Plus 默认忽略 null 字段，所以清空写**空串**而不是
  null，否则根本改不动这一列）、其余状态**不碰**（`RETRY_WAIT`/`NEED_HUMAN` 正需要保留失败原因）；
  原 5 参 `transition` 委托给新重载（既有调用方**零改动**，无行为变化）；
  `recordFailure` 改走该重载，创作域失败回写也走它（内核 `TIMEOUT`→`TIMEOUT`、
  `FAILED`→`UNKNOWN`——内核错误码未与平台分类对齐，不猜）。
  验证：aigov 单测 **+4**（失败写两列、无分类记 UNKNOWN、成功清空、`RETRY_WAIT` 不碰），
  创作域 **+1**（成功回写**不**走带错误信息的重载，避免往成功行上写错误码）。

### A.4 门槛的证据规则（**不是靠声明，是查库**）

发布推进接口的入参里有 `passedGates`（本次认为已通过哪些门槛）。其中**四道**门槛平台会**自己去库里核证据**：

| 门槛 | 证据来源 | 不满足时的报错 |
|---|---|---|
| `MANIFEST_VALIDATION` | Package 版本的 `scan_result` 必须是 `PASS` | 「不允许声明…而库里没有证据：scan_result=未扫描/REJECT」 |
| `SANDBOX_RUN` | `aig_sandbox_run` 里**该版本最近一次**运行：`exit_code=0` 且 `timed_out=0` 且 `network='none'`（登记方式见 A.4.3） | 「不允许声明「沙箱已跑通」而库里没有证据：最近一次运行超时被杀…」并回显实测数字 |
| `GOLDEN_CASE` | 版本声明的**每一条**用例，其最近一次运行必须 `result_status=PASS`，且 `review_result` 为 null 或 `PASS` | 「逐用例结论：case-x=REVIEW_MANUAL」之类 |
| `CANARY` | **灰度期内的真实调用表现**（`aig_invocation_audit` 按 `agent_version_id` 统计）：① 调用次数 ≥ `aigov.canary.min-invocations`（默认 50）② 失败率 ≤ `aigov.canary.failure-rate-limit`（默认 5%）③ 严重错误 ≤ `aigov.canary.severe-errors-allowed`（默认 0） | 「调用次数不足…；失败率超标…；出现严重错误…」**一次列全**，并附实测数字与严重错误明细 |

另外两条不变式也在服务层（不满足就拒）：
- `DISABLED → STABLE` 必须能在发布事件账本里找到该版本**曾经 STABLE 过**——否则"先停用再启用"就是绕道发布；
- 受限通道（TESTING/BRAND/DEPT）发到 CANDIDATE/STABLE 必须有**启用中的绑定**——否则"已发布"与"谁都看不见"同时成立。

#### A.4.1 `CANARY`（灰度达标）的口径

**这道门槛此前是唯一"调用方说过了就过了"的**——它原先没有任何证据校验，
见 A.7 的 C3 记录。补上之后，口径如下，几条都是刻意的：

- **灰度窗口 = 从「进入 CANDIDATE」的那一刻起**：起点取发布事件账本里该对象
  `to_status=CANDIDATE` 那条事件的 `operate_time`，终点是查询时刻。不是"这个版本有史以来的
  全部调用"——拿进入灰度之前的表现来证明灰度达标是两回事。账本里没有这条记录就**直接不达标**
  （没有灰度期，就无从统计灰度表现）。
- **严重错误 = 错误分类**（`aig_invocation_audit.error_class`，取值来自 `AigErrorClassEnum`）
  属于 `POLICY_DENIED / INVALID_REQUEST / OUTPUT_UNPARSABLE / AUTH_FAILED / QUOTA_EXCEEDED`
  之一的失败：这几类说明**版本或平台配置错了**（策略不允许、schema 不符、凭据或额度断供），
  重试一万次还是同样的结论。而 `RATE_LIMITED / TIMEOUT / UNAVAILABLE / UNKNOWN` 只是"当时环境不好"，
  **只计入失败率**，不单独否决——否则一个认不出的偶发抖动就能否掉整轮灰度。
- **只统计最终失败**：主候选失败、备选成功的调用是**成功**的，不算严重错误；
  否则「换候选」这种正常容错反而会把版本否决掉。
- **不经任务、未绑定 Agent 版本的调用不计入任何版本**（`agent_version_id` 为空是"本次未绑定"，
  不是"不知道"）：记到随便一个版本头上会让"灰度达标"变成假账。
- **阈值没有"关闭"开关**（与 `GOLDEN_CASE` / `MANIFEST_VALIDATION` 一致）：证据校验一旦能关，
  门槛就回到了"声明式达标"。**可调的是数值，不是"要不要查"。**
- ⚠️ **升级注意**：`agent_version_id` 与 `error_class` 两列是随 C3 一起加上的，
  **它们上线之前的历史调用没有这两个维度**，因此不会计入任何版本。也就是说灰度计数
  实质上是**从这两个列上线并开始记录之后**才累积的；一个已经停在 CANDIDATE 的版本，
  在攒够调用之前无法转正式——这是刻意的（没有观测就不该转正式），不是故障。
- 页面/命令行可先查 `GET /aigov/evaluation/canary-evidence?targetType=&targetVersionId=`
  拿到实测数字、阈值与差在哪（权限沿用 `aig:evaluation:query`，未新增权限点）。

#### A.4.2 调用授权审批（`require_approval` 从"装饰开关"变成真闸门）

`aig_route_policy.require_approval`（「调用前是否需要审批」）**早就存在**——建表、实体、VO/BO 都有，
治理台「路由策略」页有开关、列表也显示「需要/不需要」。但在 C3③ 之前，**全仓库唯一读它的地方是
把它拼进 `policyHits` 的说明文本**：管理员打开开关、页面显示「需要」，调用却照跑不误。
现在它真的会拦人了。

- **闸门在哪**：路由引擎只把要求<b>转达</b>成 `AigRouteDecision.approvalRequired`（它拿不到调用人），
  真正的判定在统一调用入口——那里才有调用人，判定所需的两样东西必须在同一个地方碰面。
- **授权粒度＝人 × 能力 × 数据等级**：审批本就是按 (能力,数据等级) 的策略触发的；
  批准 INTERNAL 不该顺带放行 RESTRICTED/STRICT（数据等级是安全维度，越高越严）。
- **两个时间别混**：`expire_time` 管「还能不能批准」（超时即为 `EXPIRED`，且**不得再批准**），
  `valid_until` 管「授权还管不管用」。**有效授权＝`status='APPROVED' 且 valid_until > now`**；
  授权过期<b>不改状态</b>（过期是时间的函数），所以「批准过」这个事实永远查得到。
- **申请入口是显式的**：治理台「调用授权」页提交「能力 + 数据等级 + 理由」→ 审批 → 授权。
  被拒的调用返回错误码 `APPROVAL_REQUIRED`（不是 `POLICY_DENIED`），消息里给出「去申请」的指引。
  申请前服务端会先核对策略：能力不存在、该组合没有启用中的策略、策略并不要求审批——
  这三种情况**当场说清**（审批放行不了它们），避免"提交完、批完、发现还是被拒"。
- **申请人不得自审**（分离职责，服务端强制，不靠页面藏按钮）；**驳回必须写明原因**。
- **决定/撤回都走条件更新（CAS）**：`update ... where status='PENDING'`，影响 0 行即报"已被并发处理"，
  两个审批人同时点不会都成功，也不会把已驳回的覆盖成批准。
- **阈值**：授权有效期 `aigov.approval.grant-ttl-minutes`（默认 **30 分钟**）；
  申请单审批时限 `aigov.approval.request-ttl-minutes`（默认 **1440 分钟＝24 小时**）。
  **没有"是否启用审批"的总开关**——要不要审批是逐策略配的（默认 `'N'`），再叠一个全局开关
  只会造出「策略说需要、全局说不用」这种自相矛盾。
- **超时扫描**：`aigov.approval.expire-scan-enabled`（默认关）驱动内置定时器，
  或由 cron/SnailJob 调 `POST /aigov/approval/expire-scan`。**正确性不依赖它**：
  授权判定看 `valid_until > now`，批准动作自己会拒绝过期单——扫描只是把「已超时」落进状态列、让积压可见。
- ⚠️ **升级行为**：现有种子数据的 `require_approval` **全是 `'N'`**，所以本功能上线
  **不改变任何既有部署的调用行为**；直到管理员把某个 (能力×数据等级) 的策略改成 `'Y'` 才会开始拦。
  打开之前请先把审批人配好（`aig:approval:approve` 默认只给 AI 管理员与安全），否则单子会堆着。

#### A.4.3 `SANDBOX_RUN`（沙箱跑通）的口径与登记步骤

**这道门槛此前也是"调用方说过了就过了"**（5 道门槛里最后一处），2026-10-10 补上证据（ADR-015 第三切片）。

判据（`aig_sandbox_run` 里该版本**最近一次**运行，缺一不可）：

| 判据 | 为什么 |
|---|---|
| `exit_code = 0` | 非 0 不是"执行器故障"，而是这段代码自己没跑成 |
| `timed_out = 0` | 超时被杀算"跑起来了"，但不算"跑通了"——两件事必须分开 |
| `network = 'none'` | 出网策略属 F-09（未冻），当前只有无网条件可采信。带网跑的结果也允许登记，但**不能据此过门槛** |

**只看最近一次**：允许"挑一次成功的算数"，会让已经坏掉的版本拿着旧成绩单继续往发布链路上走。

登记步骤（**在宿主机上做，不是在平台上点**）：

```bash
# 1) 宿主机：确认白名单里有这个镜像（白名单不存在会直接拒绝，这是刻意的 fail-closed）
sudo cat /etc/hotter-sandbox/images.allow      # 每行一个镜像 ref，按摘要钉死
sudo docker image inspect <ref> >/dev/null     # 沙箱不自行拉远端镜像

# 2) 宿主机：放一个作业（request.json **必须原子写入**：先写 .tmp 再 mv，否则 worker 会看到半截）
JOB=/var/lib/hotter-sandbox/work/jobs/<jobId>            # 建议用 agentCode-<时间戳>-<随机>
mkdir -p "$JOB"
cat > "$JOB/.request.tmp" <<'JSON'
{"image":"<白名单里的 ref>","cmd":"<要跑的命令>","timeoutSec":120,
 "agentCode":"<agent 编码>","versionId":"<版本ID>","requestId":"<业务请求ID，可空>"}
JSON
mv "$JOB/.request.tmp" "$JOB/request.json"

# 3) 宿主机：跑一轮 worker（常驻单元还没上，见 A.8）
/opt/hotter-sandbox/sandbox-worker.sh --once
cat "$JOB/result.json"                          # 结果 + 产物 sha256 清单
cat "$JOB/.executor-stdout.log"                 # 执行器原始输出（证据，保留）

# 4) 把它**原样**登记进平台（result.json 原文，不要手改、不要只挑几个字段填）
curl -sS -X POST "$BASE/aigov/sandbox/run/record" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @<(jq -n --arg t AGENT_VERSION --argjson v <版本ID> --arg j <jobId> \
      --rawfile r "$JOB/result.json" \
      '{targetType:$t,targetVersionId:$v,jobId:$j,resultJson:$r}')

# 5) 核对证据结论（也在发布前用来自查"还差什么"）
curl -sS "$BASE/aigov/sandbox/run/evidence?targetType=AGENT_VERSION&targetVersionId=<版本ID>" \
  -H "Authorization: Bearer $TOKEN"
```

几条**必须知道**的行为（都是刻意的，不是缺陷）：

- **缺字段一律拒绝登记**，尤其 `network` / `timedOut`：缺了就不能采信。若"缺了就默认成 `none`/`false`"，
  这份证据就变成**由登记代码造出来的**，恰好把要证明的那件事补上了。
- **一个作业只能登记一次**（`job_id` 唯一）：重复登记会让"跑通过几次"变成假账。要重新验证就重新跑一个作业（新 jobId）。
- **只收原文**：接口不接受"你自己填的退出码/网络模式"——那等于允许提交一份库里没有原文支撑的结论。
- 原文与被服务端实算的 `result.json` SHA-256 一并留存：事后改口能被发现。
- 权限 `aig:sandbox:record`（登记）与 `aig:sandbox:list`（查看）**只授 aig_admin**。
- **产物本体还不在平台里**：账本记的是产物的路径/大小/哈希，产物文件仍在宿主 scratch（tmpfs，重启即清空）。
  要留产物请现在就从 `$JOB/work/` 取走——登记到 `aig_task_artifact` 是下一件事。

### A.6 刻意不做的事（别当成缺陷）

- **生成任务构建的黄金用例只覆盖"草案/prompt 派生"这一段**：实际提交出图任务花钱且结果非确定，
  归沙箱试跑与连通性测试；用例产出里 `submission_not_performed=true` 就是这句声明的机器可读版本。
- **策划的「品牌要求 → 分镜」这段接线原先没被覆盖**（评测执行器只调 3 参形态，而生产走带
  必显信息/卖点的 5 参重载）——**已补**：执行器接受可选的 `brand_brief` 并喂给同一派生器，
  新增用例 `case-plan-brand-brief` 断言「必显信息进末屏、两条卖点各进一个卖点屏」。
  没填品牌要求的项目行为不变（新字段为「未使用」，分镜与从前逐字一致）。
- **四个内置 Agent 直接落 STABLE**（不是 DRAFT）：它们不走第三方 Package 安装链路，
  同等门槛由平台 CI 与代码评审承担；同时补了一条发布事件让"曾 STABLE 过"为真
  （否则一旦停用，按 §5.4 的保护就再也启用不回来）。
- `aig_skill_version` **没有** `evaluation_run_id` 列（设计只给了 Agent/Package 版本），
  Skill 版本的评测证据直接取评测账本，不做冗余的第二份"最近一次"。
- **两个「停用」是两件事，别混**：
  - **包级**（`aig_package.status='1'`，接口 `POST /aigov/agent/package/{id}/disable`）：
    此后**不再接受新版本上传、不能安装**——影响的是**将来**；**不动**已经装出去、正在被使用的版本。
    可逆（`/enable`），幂等（已是该状态时 `changed=false`）；
  - **版本级**（`POST /aigov/agent/package/version/{id}/disable`）：把该包带进来的 Agent/Skill 版本
    **批量下线**——影响的是**已经装出去、可能正在被业务使用的**那些版本（STABLE 也会被撤下）。
  接口、权限（同一个 `aig:package:disable`）、页面按钮与说明都刻意分开，为的是挡住「误以为停了」。
- **Package 包体留存默认关闭**（第二期 B2 已实现，开关 `aigov.package.store-body`）：
  关闭时（默认）行为与之前完全一致——包体只用于核对校验和、不留存；
  开启后留存到对象存储，对象键写在该**版本**的 `body_ref`（逐版本，不是逐包：每次上传的包体可能不同），
  对象在私有前缀 `aig-private/` 下、**不登记 `sys_oss`**（否则持有 `system:oss:download` 的账号
  可绕过治理模块授权直接下载包体）。**无论开关状态，上传响应里的 `bodyStored`/`bodyRef` 都如实回报**；
  开启后留存失败即整笔上传失败（不落半截状态）。
  ⚠️ 开启前请确认 `sys_oss_config` 有启用中的配置——否则上传会从"能用"变成"报错"。

#### A.9.1 三个会让烟测"看起来失败"的姿势问题（都不是缺陷）

1. **HTTP 状态码恒为 200，判据在响应体 `code` 里。**
   `curl -I` 看状态码会发现 `/aigov/agent/list`（未登录）和 `/aigov/agent/not-exists` 都是 `200`，
   容易误判成"鉴权没生效/路由不存在"。RuoYi 用统一响应体，真实状态是 `"code":401` / `"code":404`。
   **判据要读 body，不要读 HTTP 状态。**
2. **缺 `HR_ENCRYPT_KEY` 会 fail-closed 起不来。**
   `mybatis-encryptor.enable=true`（HR 模块的密文列用了它），密码为空时启动直接失败：
   `MybatisPlusAutoConfiguration ... mybatis-encryptor.password 不能为空`。
   这是设计如此（缺密钥宁可不启动，也不静默存明文），部署时由环境变量注入（AES 需 16/24/32 字节）。
3. **登录接口带 `@ApiEncrypt`，明文登录会被 403 挡住。**
   `api-decrypt.enabled=true` 时 `CryptoFilter` 要求请求带 `encrypt-key` 头，否则抛
   「没有访问权限，请联系管理员授权」。真前端会做 RSA+AES 握手；命令行烟测要么按协议加密，
   要么临时 `--api-decrypt.enabled=false`（**只用于烟测，不要带进生产**）。
   另外：带 token 的请求除 `Authorization: Bearer <token>` 外**还需要 `clientid` 头**
   （多客户端校验），少一个就是 `code=401`。

- `GET /aigov/evaluation/declared-cases?targetType=AGENT_VERSION&targetVersionId=<id>` → **2 条**
  （正好是该版本 `config_json.golden_cases` 声明的两条，证明这个新接口真的读得到声明）；
- 写接口的**反面对照**：`POST /aigov/agent/release/advance` 用 `expectedStatus=DRAFT`
  推进一个实际已是 `STABLE` 的版本 → 被拒并给出可读原因
  「你的视图已过期：库中当前状态是 STABLE…请刷新后重试（对象 AGENT_VERSION #…）」，
  证明严格状态机与乐观并发校验在真容器里生效；
- **Package 全链路（真 HTTP，`multipart`）**：
  ① 校验和不一致 → 拒绝且不落任何行（消息里同时给出"声明的"与"平台算出的"两个哈希）；
  ② 校验和一致 → 登记成功、`scanResult=PASS`；
  ③ `POST /package/version/{id}/install` → `alreadyInstalled=false`、建出 DRAFT 的 Skill 版本；
  ④ 隔开 `@RepeatSubmit` 窗口后重装 → `alreadyInstalled=true`、全部 `existing`（**幂等**）；
  ⑤ 同 `(package, version)` 重传 → 「该包的这个版本已存在，不允许覆盖…（版本不可变）」；
  ⑥ 账本 2 行：`UPLOAD/PASS` + `INSTALL/PASS`（detail 写明"安装 0 个 Agent、1 个 Skill（均为 DRAFT）"）；
  ⑦ 查库对账：`aig_skill_version.release_status=DRAFT`、`package_version_id` 回指安装来源、
      `config_json` 里 `data_level`/`scenario_codes`/`source_package.manifest_hash` 都在
      （即两条落库口径在真库里成立）。
- 顺带证明了 `@RepeatSubmit` 生效：窗口内重复提交会被「不允许重复提交，请稍候再试」拦下
  ——做幂等验证时**必须先等过窗口**，否则测到的是防重而不是幂等。

#### A.9.4 "父菜单必须授权"这个坑：真系统里的反面对照

治理台页面菜单是单独一份 `aig_agent_registry_pages.sql`，其中显式补了一次**父菜单**
（`AI平台治理`）对三个角色的授权。为什么必须补——用真系统做了反面对照：

建一个只挂 `aig_viewer` 的账号（`aigsmoke`），调 `GET /system/menu/getRouters`
（注意路径是 **`/system/menu/getRouters`**，不是 `/getRouters`）取它自己的路由树：

| 步骤 | 页面授权 | 父菜单授权 | 路由树里的 aigov 页面 |
|---|---|---|---|
| 1. 当前状态 | 5 个页面行都在 | **在** | **10 个**（5 个 WP3 页面 + 5 个既有只读页），父级 `/ai-gov` 在树里 |
| 2. **只删父菜单授权**（5 个页面授权一个没动） | 5 个页面行仍在 | **不在** | **0 个** —— 父节点不在集合里，子节点就没有挂载点 |
| 3. 恢复父菜单授权 | 5 个页面行仍在 | 在 | 回到 **10 个** |

也就是说：**页面授权正确、父菜单没授权 = 用户完全看不到这些页面**，而且从权限表上查
"页面授权"是查不出问题的（第 2 步里那 5 行明明还在）。RuoYi 的
`selectMenuTreeByUserId` 用 `getChildPerms(menus, 0)` 从 `parentId=0` 往下走，
父菜单不在用户已授权菜单里，整棵子树都不会被遍历到。

**给验收的启示**：查菜单问题不要只查 `sys_role_menu` 里"页面有没有授权"，
要连**父级是否授权**一起查；本地 `verify-registry-menu.ps1` 现在就把这条做成了断言
（"有页面必有已授权的父菜单"，三个角色都查）。
