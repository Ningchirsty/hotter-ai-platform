## 一、先说结论：要做的就三件事

| # | 做什么 | 谁做 | 卡不卡发布 |
|---|---|---|---|
| 1 | 在目标库执行 **11 份 `aig_*` 脚本**（顺序见 §三） | 有库权限的运维 | **必须，且在发布后端之前** |
| 2 | 补 3 个**生产配置**（`aigov.model-crypto.*`，与 snail-ai 对齐） | 运维 | **必须**，否则治理台录不了密钥 |
| 3 | 发布**后端 + 前端**镜像（治理台有界面改动，前端必须一起发） | 按既有 workflow | 常规 |

> ⚠️ **发布入口不会执行 SQL**（与人才库那次同一个坑）。脚本必须人工执行，见 §三。

**另一个必须先知道的点**：`aigov` 的配置在仓库里**一处都没有**（我 grep 过全部 `application*.yml`），
所以生产全靠**显式配置 + 代码默认值**。默认值对"能跑"是够的，但对"能用"不够——
`aigov.model-crypto` 不配，治理台就无法录入模型密钥（见 §四）。

## 三、步骤 1：在目标库执行脚本（**发布后端之前**）

### 3.1 本次预演的证据（先看这个再动手）

在全新 MariaDB 实例（临时 datadir + 独立端口 3410，未碰任何既有库）上按下面的顺序执行：

```
13 份脚本 第一遍执行 → 13/13 exit=0
第二遍重跑（除安装类菜单脚本）→ 全部 OK（幂等）
```

即：**除两份平台基座脚本与 `aig_ai_gov_menu.sql` 外，其余脚本都可以安全重跑。**

### 3.2 脚本与顺序

```bash
# 平台基座（全新库才需要；存量库跳过）
script/sql/ry_vue.sql                        # sys_* 表（含 sys_menu/sys_role/sys_dict）
script/sql/ry_ai.sql                         # sai_* 表（模型主数据，治理层只读它）

# 本模块（存量库从这一行开始也行——aig_ai_gov.sql 是 create table if not exists）
script/sql/aig_ai_gov.sql                    # 治理 5 张表 + 场景绑定表（规范 DDL，含全部新列）
script/sql/aig_ai_task.sql                   # 统一任务 5 张表
script/sql/aig_ai_gov_menu.sql               # 菜单/角色/字典【安装类，不幂等，只跑一次】
script/sql/aig_ai_gov_menu_migration.sql     # 增量：模型新增权限点（幂等）
script/sql/aig_ai_task_menu.sql              # 增量：任务菜单与权限（幂等）
script/sql/aig_data_level_strict.sql         # 字典增加 STRICT 第 4 级（幂等）
script/sql/aig_model_capability_tags.sql     # 迁移：capability_tags 列（幂等，自带存在性判断）
script/sql/aig_model_cost_limit_amount.sql   # 迁移：cost_limit_amount 列（幂等）
script/sql/aig_route_scenario_binding.sql    # 迁移：场景绑定表 + 审计 scenario_code（幂等）
script/sql/aig_audit_provider_usage.sql      # 迁移：审计 provider_id/usage_json/input_snapshot_ref（幂等）
script/sql/aig_provider_bluocto.sql          # 种子：bluocto 供应商 + 7 个图像模型 + 能力 + 策略 + 绑定（幂等）
```

**按环境选路径：**

- **全新库**：从上到下全跑一遍（13 份）。
- **存量库**（已装过平台，或跑过旧版 `aig_ai_gov.sql`）：从 `aig_ai_gov.sql` 开始跑完即可。
  4 份 `*_migration` 式的脚本就是为存量库准备的——它们会先查 `information_schema`
  再决定是否 `ALTER`，所以**在全新库上跑也只是空转**（已实测），不必纠结跑没跑过。
- **`aig_ai_gov_menu.sql` 只跑一次**：它是纯 `insert`（固定主键），重复执行会主键冲突。
  已经跑过的环境，后续菜单靠 `aig_ai_gov_menu_migration.sql` 与 `aig_ai_task_menu.sql` 这两份
  **可重复执行**的增量脚本补齐——这也是它们存在的原因。

### 3.3 在服务器上怎么执行

```bash
# 1) 确认后端实际连的库（不要凭猜）
sudo docker exec <backend容器> env | grep -i -E 'datasource|mysql|url' | sed 's/:[^:@]*@/:***@/g'

# 2) 把脚本送进容器并按顺序执行（库名以实际配置为准）
for f in aig_ai_gov aig_ai_task aig_ai_gov_menu aig_ai_gov_menu_migration aig_ai_task_menu \
         aig_data_level_strict aig_model_capability_tags aig_model_cost_limit_amount \
         aig_route_scenario_binding aig_audit_provider_usage aig_provider_bluocto; do
  sudo docker cp script/sql/$f.sql <mysql容器>:/tmp/
  sudo docker exec -i <mysql容器> sh -c \
    'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 <库名> < /tmp/'$f'.sql' \
    || echo "FAILED: $f"
done
```

> **带 `--default-character-set=utf8mb4`**：这些脚本里有中文注释与中文菜单名，
> 不指定字符集在部分客户端上会写进乱码（乱码写进 `sys_menu.menu_name` 会直接显示在界面上）。

## 四、步骤 2：生产配置（**只有 3 个是必须的**）

### 4.1 必须配：`aigov.model-crypto.*`（与 snail-ai 逐字节一致）

| yml 键 | 环境变量（Spring relaxed binding） | 生产要求 | 不配的后果 |
|---|---|---|---|
| `aigov.model-crypto.secret-key` | `AIGOV_MODEL_CRYPTO_SECRET_KEY` | **必须与 snail-ai 的 `snail-ai.crypto.secret-key` 完全一致**（32 个 hex 字符 = 16 字节） | 与 snail-ai 不一致 → 治理台写进去的密文 **snail-ai 解不开**，模型静默不可用 |
| `aigov.model-crypto.iv` | `AIGOV_MODEL_CRYPTO_IV` | 同上，与 `snail-ai.crypto.iv` 一致 | 同上 |
| `aigov.model-crypto.enabled` | `AIGOV_MODEL_CRYPTO_ENABLED` | 要**在治理台录入密钥**就必须 `true` | `false` 时治理台拒绝录入/清除密钥，密钥只能去 snail-ai 管理端配 |

> ⚠️ **`enabled=true` 但 `secret-key`/`iv` 为空 → 应用启动直接失败**（刻意的自检：
> 宁可起不来，也不要"密钥写进去但别人解不开"在运行期才暴露）。要么三项都配，要么
> `enabled` 保持 `false` 且两个密钥也不填。
>
> ✅ **配完看启动日志里的 `fingerprint`**（形如 `fingerprint=8fa13a559078`），
> 与 snail-ai 侧日志中的同一值比对：**不一致就说明两边参数不同，此时任何密文都解不开**。
> 这个指纹是 key+iv 的 SHA-256 前 12 位，不泄漏密钥本身。

### 4.2 建议确认（默认值可用，但要知道含义）

| yml 键 | 默认 | 说明 |
|---|---|---|
| `aigov.external-api.enabled` | `true` | 关闭后直连外部网关的调用器不可用 |
| `aigov.external-api.image-response-format` | `url` | **必须保持 `url`**：bluocto 实测（网关不支持该字段会直接 400）。拿到 URL 后调用器会立刻下载成字节，不依赖 URL 长期有效 |
| `aigov.external-api.image-timeout-ms` | `180000`（3 分钟） | **实测单张约 69–76 秒**；若上游更慢再调大 |
| `aigov.external-api.image-max-bytes` | `8388608`（8MB） | 实测产出 6.1MB，通过 |
| `aigov.retry.enabled` / `max-attempts` / `base-backoff-ms` / `max-backoff-ms` | `true` / `3` / `200` / `2000` | 只对"可重试"类生效（限流/超时/服务不可用） |
| `aigov.route.require-model-tags` | `false` | `false`＝未声明标签的模型放行并写提示；补齐标签后可改 `true` 收紧 |
| `aigov.route.require-model-cost` | `false` | 同上，针对"未声明单次成本上限" |
| `aigov.callback.secrets.<providerCode>` | 空 | 目前不需要：bluocto 是同步返回、无回调。**但未配密钥的回调一律拒绝**（这是刻意的） |
| `aigov.task.scheduler.enabled` | **`false`** | 见下 |
| `aigov.task.scheduler.timeout-seconds` | `1800` | 在途任务超时阈值（**别设太小**：一次出图就要 70 秒级） |

**关于任务调度器（`aigov.task.scheduler.*`）**：默认 **关闭**，因为它是可选的多实例安全组件。
两条触发路径，任选其一：

1. **应用内定时**：置 `AIGOV_TASK_SCHEDULER_ENABLED=true` 即可。
   已核实 `ruoyi-admin → ruoyi-job → ruoyi-common-job` 这条链带 `@EnableScheduling`，
   所以生产上这个开关是有效的（不需要额外加注解）。
2. **外部 cron / 任务平台**：保持 `false`，由外部按周期调
   `POST /aigov/task/scheduler/sweep`（需 `aig:task:operate`）。

它负责两件事：`RETRY_WAIT → QUEUED` 的重试驱动，以及"卡在途"的超时判定（多实例抢锁，抢输的计 `skipped`）。
**不做这两件事，失败任务会一直停在"等待重试"**。

### 4.3 明确不要动

- `aigov.snail-ai.*`（`enabled=false` 默认）：这是走 snail-ai 内部路径的开关，本次用直连调用器，不需要开；
- `aigov.model-test.*`：连通性测试的超时与重试，默认够用。

## 五、步骤 3：录入 bluocto 的密钥（**脚本里刻意不写密钥**）

`api_key` 是 SM4 密文列。**不要在 SQL 里填明文**，也不要用别的工具随便加密——
必须与 snail-ai 的 `CryptoHelper` 逐字节一致。正确路径是让服务端加密落库：

**方式 A（一次覆盖整个供应商，推荐）**：治理台 →「模型注册中心」→ 供应商管理 → 「批量配密钥」。
**方式 B（API）**：

```bash
curl -X PUT 'https://<生产域名>/aigov/model/secret/batch' \
  -H 'Authorization: Bearer <你的登录 token>' \
  -H 'Content-Type: application/json' \
  -d '{"providerId": <bluocto 的 sai_model_provider.id>, "apiKey": "sk-…"}'
```

- 需要权限 `aig:model:secret`；
- `modelIds` 不传 = 该供应商下**全部已登记模型**（含停用模型）；
- 明文只加密**一次**再复用（SM4/CBC 固定 IV 下，与逐行加密逐字节等价——有单测钉着这条等价性）；
- 传 `modelIds` 时若混入别家模型 → **整批拒绝**（避免"以为在改 A 家，实际把 B 家的凭据覆盖了"）。

**录完立刻验证**：治理台 →「模型注册中心」→ 该模型 → 「连通性测试」。
预期通过。若返回 401/403，先看是**密钥错**还是**余额不足**——现在这两种错误分类是分开的：
`QUOTA_EXCEEDED`（额度/余额不足，去充值）与 `AUTH_FAILED`（鉴权失败，换密钥），
审计的 `error_summary` 会带上上游原文。

## 八、回滚

| 要回滚的 | 怎么做 | 代价 |
|---|---|---|
| 后端/前端 | 按既有流程重新发布**上一个 digest** | 界面与接口回到旧版；`aig_*` 表与数据仍在（新代码不读它们即可） |
| 菜单/权限 | 删除本次新增菜单与角色绑定（见下），再清缓存 | 只是界面入口消失，不影响数据 |
| 数据库 | **一般不需要**：本轮只加表/加列/加菜单，没有改语义、没有删列、没有加约束 | — |
| 彻底移除 bluocto 通路 | 把 `aig_capability_model` 里 `capability_code='image_generation'` 的绑定删掉即可（无绑定＝无候选＝不会路由过去） | 登记还在，但不会有任何外部请求 |

```sql
-- 只回滚菜单与角色绑定（数据表保留）
delete from sys_role_menu where menu_id in
 (1763000000000001401,1763000000000001402,1763000000000001403,1763000000000001204);
delete from sys_menu where menu_id in
 (1763000000000001401,1763000000000001402,1763000000000001403,1763000000000001204);

-- 立刻停掉外发（保留登记，最温和的一种）
delete from aig_capability_model where capability_code='image_generation';
```

> 删菜单后要清一次菜单缓存（后台「系统管理 → 菜单管理」刷新，或重启后端），否则界面不会立刻变。

## 十、仍然开着的事项（不影响本次发布）

  "按供应商记币种"还是"统一换算入账"；

  要接需换一个含对话模型的令牌分组；
