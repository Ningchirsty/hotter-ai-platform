### 2.2 为什么要把"契约冻结"单独做一个增量

岗位包的 Action 会带 `routeKey`，门户据此跳转。这里有**三类"不会报错"的错法**，
它们都只能在运行期被用户发现：①前后端名单不一致（后端发得出、前端不认识 → 点了没反应；
反过来那个入口永远配不出来）；②键在白名单里但前端没有那个页面 → 点进去空白；
③启动方式/目标类型被扩成自由字符串 → 岗位包能声明平台没实现的类型。
所以这三条都钉到**构建期**（CI 会红），而不是靠评审。

### 2.3 契约测试做了什么（这是本增量真正的价值）

1. **前后端键集合必须完全一致**（读前端注册表源码解析键，两个方向都比）；
2. **每个 routeKey 的目标路径必须能在菜单脚本里找到组件**（`<path 去掉斜杠>/index`）——
   这条把"声明"与"真的存在那个页面"绑在一起，防的就是"入口能点、点进去空白"；
3. **不在白名单的键解析为 null/false**（调用方据此拒绝，不许猜路径）；
4. **三个枚举是封闭集合**（扩值必须同时改测试，是刻意的摩擦）；
5. 仓库根可定位（否则检查会静默空转）。

### 3.2 四个刻意的取舍（都在脚本注释里）

1. **`scenario_version.release_status` 沿用既有发布状态机取值**（F-10）——不另立一套状态、
   也不新造审批表。场景/岗位的发布走同一台机器。
2. **`role_binding` 只存 `sys_dept.dept_id` 与 `brand_id`，不做外键、不建授权体系**（F-05）：
   它只是"谁能看到卡片"的可见性过滤；真实数据权仍由 RuoYi 数据权限 + 治理层 `org_scope` 决定。
   脚本注释里写明了这一点，避免后来人把它当授权表用。
3. **`action` 拆表、`category` 留在 `manifest_json`**：action 要支持"按分类查卡片/排序/单独启停"，
   每次解析 JSON 不现实；分类数量少、与 action 同版本、总是整份读取，留清单里即可——
   多一张表就多一处要与版本对齐的地方。`action.category_code` 必须能在该版本清单里找到（服务层校验）。
4. **`workflow_adapter` 是封闭枚举而不是自由字符串**：它指向"这次交给谁去跑"
   （创作域阶段机/视频链路/内容链路/不挂流程），**不是流程引擎**；自由字符串会让人声明
   一个平台没实现的适配器，失效表现是"卡片能点、任务起不来"。

### 3.4 增量 1b：岗位包校验器（✅ 已完成）；服务与 API 仍待做

**校验规则**（一次列全，不抛第一个错）：岗位编码形态与版本 SemVer、分类至少一个且编码唯一、
默认分类必须在本包内、卡片至少一张且编码唯一、卡片分类必须在本包内、标题必填、
启动方式/目标类型必须在封闭枚举里、**纯导航的 routeKey 必须命中白名单**、
**SCENARIO 引用必须是 `scenario://<code>@<版本>` 且该场景版本真的存在**、
**STUDIO 必须给 studioRouteKey 且命中白名单**、
**轻量能力不许指向 routeKey**（那是 NAVIGATION 的语义，混在一起会让"启动方式"失去意义）、
上下文键必须在白名单里（不允许包要求约定外字段，更不能借它覆盖身份）、

### 3.5 增量 1b 收尾：发布流转守卫、清单哈希、实体与 Mapper（✅ 已完成）

这三块在服务与 API 之前先落地（它们都是"配错了不会报错"的那类东西）：

| 落地物 | 它守的事 |
|---|---|
| `workspace/helper/AigRoleReleaseTransition`（+6 用例） | 允许的发布流转是**一张写死的边表**：DRAFT→TESTING→PUBLISHED，任何已存在的状态→DISABLED（可撤销），DISABLED 可重新启用。**刻意不允许 PUBLISHED→DRAFT**（否则"员工当时看到的是什么"答不上来）与 **X→X**（同状态不是流转）。`visibleToEmployees` 只有 PUBLISHED |
| `workspace/helper/AigRoleManifestHasher`（+5 用例） | 直接**复用训练台那份规范化实现**（`AigStudioContentHasher`），不写第二份：同一串内容在两处算出不同哈希是"两边各自都能跑、合起来才出错"。有用例把"复用同一实现"钉住 |
| `workspace/domain/{AigScenario,AigScenarioVersion,AigRoleProfile,AigRoleVersion,AigRoleAction,AigRoleBinding}` + 六个 `BaseMapperPlus<实体,实体>` Mapper | 六张表的实体与数据访问。泛型第二参数用实体自己（T==V）：本增量只需要数据访问，**不为了让 VO 好看而多加一层转换器**（守卫 `AigMapperVoConverterCoverageTest` 只对 T≠V 要求生成转换器） |

★这次 CI 抓到过一个**本地绿、CI 红**的真缺陷：`describeAllowed` 直接遍历 `Set.of(...)` 返回的集合，
而 **`Set.of` 的迭代顺序未定义** → 本地给 `TESTING/DISABLED`、CI 给 `DISABLED/TESTING`。
这不只是 flaky 测试：那是**给人看的报错文案**（"从当前状态能去哪"），不确定的文案会让人以为行为变了。
修法是按 `Enum.values()` 的**声明序**遍历再筛。同一教训在服务层又用了一次（`allowedTransitions` 也按声明序输出）。

**六条设计取舍**

1. **发布后不可变**：只有 DRAFT 能改清单/卡片，其余状态一律拒绝——否则"员工当时看到的是哪一份配置"无法回答。
   要改就出新版本。
2. **离开 DRAFT 必须先校验通过**（TESTING/PUBLISHED），且**校验的是库里那一份**（重新读清单 + 卡片行），
   不是调用方刚提交的入参：入库后才出现的"清单与卡片表漂移"只有这样才看得见。
   **停用不需要先证明它是对的**——叫停一个配错的东西不该被校验拦住。
3. **保存草稿不要求校验通过**：草稿就是"还没配好"的东西，能存下来才能继续配；门槛只放在发布那一步。
4. **覆盖草稿要带 CAS**（`expectedManifestSha256`）：两个人同时编辑时，后保存的不能默默盖掉先保存的。
   `casMatches` 刻意要求**两侧都非空白**——把"期望为空"当成匹配等于给并发编辑开后门。
5. **发布与停用是两个端点、两个权限点**：`@SaCheckPermission` 是静态的，一个"给我目标状态"的端点
   没法既是发布又是停用；合成一个就必然让"能发布"等于"能叫停"。发布接口只接受 TESTING/PUBLISHED。
6. **允许的流转与可见性由服务端算好**（`allowedTransitions` / `visibleToEmployees`）交给前端：
   前端各写一份判断，迟早会出现"界面说能点、后端拒绝"或"界面看不到但门户里能看见"两套口径。
   管理台的 `presentation.ts` 只做显示，**不复制状态机**。

另外两条小口径：`manifest_json` **入库即规范化**（`AigRoleManifestHasher.canonicalize`），
因此 `manifest_sha256 == hash(manifest_json)` 恒成立，谁手工改了库里的文本，重算哈希就对不上；
读一份已存版本时会额外核对**清单哈希**与**清单里的版本号**是否与记录一致（`storedProblems`）。

**六条取舍**

1. **可见性自己实现（F-06）**：`aig_agent_binding` 今天只是发布许可证、没有运行时消费方，
   所以门户可见性不能指望别处。规则是 fail-closed 的四步：①状态必须 PUBLISHED（复用
   `AigRoleReleaseTransition.visibleToEmployees`，状态未知一律不可见）；②`audienceScope=ALL` 全员可见；
   ③`ASSIGNED_ORG` 必须**至少一条生效中的绑定**命中用户的组织范围或品牌；
   ④**读不懂的范围声明（含 null）一律不可见**——不能当成"那就给所有人看"。
2. **"生效中"也要判定**：`enabled='Y'` 且落在 `[effectiveFrom, effectiveTo]`（闭区间，两端可空）。
   少了这步，一个"下月才生效"或"已过期"的绑定会立刻对员工生效——那是只有业务方在特定日期才会发现的问题。
3. **组织范围 = 本部门 + 全部祖级**：岗位绑定常挂在集团/子公司层级（F-05：组织树只有前两级），
   只按本部门精确匹配会让"给华东子公司发布的岗位"对华东下每个部门都不可见。
   解析是纯函数并逐条钉住（空串/`0` 不是部门；脏 token 只忽略、不会让整条链失效）。
4. **一个岗位只出现一次**，取版本号**最大**的可见版本：员工要的是"这个岗位现在怎么做"。
   比较必须按数字段（`1.10.0 > 1.9.0`）——字符串比较会让员工一直用旧配置，而界面上看起来"我们明明发布过了"。
5. **过滤在服务端**：不该看到的卡片**根本不发到浏览器**（停用中的卡片、
   分类已不在清单里的"漂移卡片"都被剔除）。前端 `presentation.ts` 只做显示与"哪个入口现在真能走"，
   导航路径只认 `aiWorkspaceRouteRegistry` 白名单（解析不到返回 null，**不许猜路径**）。
6. **门户不要权限点，要数据范围**：三个接口都是 `@SaCheckLogin`。给它编一个
   `aig:portal:view` 等于发明一个"谁能用员工工作台"的授权面——而答案永远是"所有员工"，
   于是每建一个角色都要记得勾上，漏了就表现为"某人打开是空白"。
   `/my-tasks` 则**强制把提交人覆盖成登录用户**：少了这一条，这个连任务权限点都没有的接口
   就成了"能读别人任务"的入口。

**门户视图的边界（有专门用例守着）**：`AigPortalTaskVo` 刻意不带计费金额、供应商编码/任务号、
`traceId`、策略原因、错误详情；`AigPortalActionVo` 不带 `actionId`/`enabled`。
门户多一个字段不会报错，只会某天把内部细节发给全体员工——所以把边界写成断言。

**这一增量"还不能做什么"（如实说明）**：非导航类卡片（QUICK/FORM/STUDIO/SCENARIO）现在
**不能启动**：启动要走 Launch Resolver（增量 3）才有"谁、按哪张卡片、结果落在哪个任务"的凭证。
界面上这类卡片显示为禁用 + `START_PENDING_HINT`（"启动将在接入启动凭证后开放"），
**不给一个点了没反应的按钮**——那对员工来说就是"系统坏了"。NAVIGATION 类卡片可以真的打开页面。
