### 2.2 为什么要把"契约冻结"单独做一个增量

岗位包的 Action 会带 `routeKey`，门户据此跳转。这里有**三类"不会报错"的错法**，
它们都只能在运行期被用户发现：①前后端名单不一致（后端发得出、前端不认识 → 点了没反应；
反过来那个入口永远配不出来）；②键在白名单里但前端没有那个页面 → 点进去空白；
③启动方式/目标类型被扩成自由字符串 → 岗位包能声明平台没实现的类型。
所以这三条都钉到**构建期**（CI 会红），而不是靠评审。

### 2.3 契约测试做了什么（这是本增量真正的价值）

1. **前后端键集合必须完全一致**（读前端注册表源码解析键，两个方向都比）；
2. **每个 routeKey 的目标路径必须能在菜单脚本里找到组件**（`<path 去掉斜杠>/index`）——
   这条把"声明"与"真的存在那个页面"绑在一起，防的就是"入口能点、点进去空白"；
3. **不在白名单的键解析为 null/false**（调用方据此拒绝，不许猜路径）；
4. **三个枚举是封闭集合**（扩值必须同时改测试，是刻意的摩擦）；
5. 仓库根可定位（否则检查会静默空转）。

### 3.2 四个刻意的取舍（都在脚本注释里）

1. **`scenario_version.release_status` 沿用既有发布状态机取值**（F-10）——不另立一套状态、
   也不新造审批表。场景/岗位的发布走同一台机器。
2. **`role_binding` 只存 `sys_dept.dept_id` 与 `brand_id`，不做外键、不建授权体系**（F-05）：
   它只是"谁能看到卡片"的可见性过滤；真实数据权仍由 RuoYi 数据权限 + 治理层 `org_scope` 决定。
   脚本注释里写明了这一点，避免后来人把它当授权表用。
3. **`action` 拆表、`category` 留在 `manifest_json`**：action 要支持"按分类查卡片/排序/单独启停"，
   每次解析 JSON 不现实；分类数量少、与 action 同版本、总是整份读取，留清单里即可——
   多一张表就多一处要与版本对齐的地方。`action.category_code` 必须能在该版本清单里找到（服务层校验）。
4. **`workflow_adapter` 是封闭枚举而不是自由字符串**：它指向"这次交给谁去跑"
   （创作域阶段机/视频链路/内容链路/不挂流程），**不是流程引擎**；自由字符串会让人声明
   一个平台没实现的适配器，失效表现是"卡片能点、任务起不来"。

### 3.4 增量 1b：岗位包校验器（✅ 已完成）；服务与 API 仍待做

**校验规则**（一次列全，不抛第一个错）：岗位编码形态与版本 SemVer、分类至少一个且编码唯一、
默认分类必须在本包内、卡片至少一张且编码唯一、卡片分类必须在本包内、标题必填、
启动方式/目标类型必须在封闭枚举里、**纯导航的 routeKey 必须命中白名单**、

### 3.5 增量 1b 收尾：发布流转守卫、清单哈希、实体与 Mapper（✅ 已完成）

这三块在服务与 API 之前先落地（它们都是"配错了不会报错"的那类东西）：

| 落地物 | 它守的事 |
|---|---|
| `workspace/helper/AigRoleReleaseTransition`（+6 用例） | 允许的发布流转是**一张写死的边表**：DRAFT→TESTING→PUBLISHED，任何已存在的状态→DISABLED（可撤销），DISABLED 可重新启用。**刻意不允许 PUBLISHED→DRAFT**（否则"员工当时看到的是什么"答不上来）与 **X→X**（同状态不是流转）。`visibleToEmployees` 只有 PUBLISHED |
| `workspace/helper/AigRoleManifestHasher`（+5 用例） | 直接**复用训练台那份规范化实现**（`AigStudioContentHasher`），不写第二份：同一串内容在两处算出不同哈希是"两边各自都能跑、合起来才出错"。有用例把"复用同一实现"钉住 |
| `workspace/domain/{AigScenario,AigScenarioVersion,AigRoleProfile,AigRoleVersion,AigRoleAction,AigRoleBinding}` + 六个 `BaseMapperPlus<实体,实体>` Mapper | 六张表的实体与数据访问。泛型第二参数用实体自己（T==V）：本增量只需要数据访问，**不为了让 VO 好看而多加一层转换器**（守卫 `AigMapperVoConverterCoverageTest` 只对 T≠V 要求生成转换器） |

★这次 CI 抓到过一个**本地绿、CI 红**的真缺陷：`describeAllowed` 直接遍历 `Set.of(...)` 返回的集合，
而 **`Set.of` 的迭代顺序未定义** → 本地给 `TESTING/DISABLED`、CI 给 `DISABLED/TESTING`。
这不只是 flaky 测试：那是**给人看的报错文案**（"从当前状态能去哪"），不确定的文案会让人以为行为变了。
修法是按 `Enum.values()` 的**声明序**遍历再筛。同一教训在服务层又用了一次（`allowedTransitions` 也按声明序输出）。

**六条设计取舍**

1. **发布后不可变**：只有 DRAFT 能改清单/卡片，其余状态一律拒绝——否则"员工当时看到的是哪一份配置"无法回答。
   要改就出新版本。
2. **离开 DRAFT 必须先校验通过**（TESTING/PUBLISHED），且**校验的是库里那一份**（重新读清单 + 卡片行），
   不是调用方刚提交的入参：入库后才出现的"清单与卡片表漂移"只有这样才看得见。
   **停用不需要先证明它是对的**——叫停一个配错的东西不该被校验拦住。
3. **保存草稿不要求校验通过**：草稿就是"还没配好"的东西，能存下来才能继续配；门槛只放在发布那一步。
4. **覆盖草稿要带 CAS**（`expectedManifestSha256`）：两个人同时编辑时，后保存的不能默默盖掉先保存的。
   `casMatches` 刻意要求**两侧都非空白**——把"期望为空"当成匹配等于给并发编辑开后门。
5. **发布与停用是两个端点、两个权限点**：`@SaCheckPermission` 是静态的，一个"给我目标状态"的端点
   没法既是发布又是停用；合成一个就必然让"能发布"等于"能叫停"。发布接口只接受 TESTING/PUBLISHED。
6. **允许的流转与可见性由服务端算好**（`allowedTransitions` / `visibleToEmployees`）交给前端：
   前端各写一份判断，迟早会出现"界面说能点、后端拒绝"或"界面看不到但门户里能看见"两套口径。
   管理台的 `presentation.ts` 只做显示，**不复制状态机**。

另外两条小口径：`manifest_json` **入库即规范化**（`AigRoleManifestHasher.canonicalize`），
因此 `manifest_sha256 == hash(manifest_json)` 恒成立，谁手工改了库里的文本，重算哈希就对不上；
读一份已存版本时会额外核对**清单哈希**与**清单里的版本号**是否与记录一致（`storedProblems`）。

**prepare / commit 的分工**

- `prepare`：**无副作用**。解析卡片（走门户那条可见性路径）→ 算内容摘要 → 校验链 → 通过才发一张
  Redis 短期票据（TTL 5–10 分钟，配置上限 30 分钟）。它**不建任务、不改业务数据**。
- `commit`：确认后真正启动。**幂等**（同一幂等键重复提交只得到同一次启动）、**票绑人**
  （票转到别人手里用不了）、**票一次性**（成功后作废）、**过期即拒**，并在提交前**重新**跑一遍校验链。

**九条取舍（每条都对应一种"不报错但会出事"）**

1. **票据不落库**：它是短期凭证，过期即无意义；落库只会多一批要清理的行。落库的只有 commit 之后的
   `aig_launch_record`——那才是要长期回答的事实。
2. **校验做两遍**（prepare 与 commit 各一次）：两者之间隔着用户操作的时间，卡片可能被停用、
   场景版本可能被下架、配额可能耗尽。只在 prepare 校验，等于把"确认"变成绕过全部检查的入口。
3. **内容摘要防"幂等键被复用到另一次启动上"**：键相同而摘要不同 → `IDEMPOTENCY_CONFLICT`。
   少了它，用户改了输入又提交会**拿到第一次的结果**（改动被静默丢弃）。
   摘要对格式不敏感（复用 `AigStudioContentHasher` 那份唯一规范化实现），否则重试永远失败。
4. **不通不发票**：校验没过就不给票据。否则"拿到票"本身就等于"能启动"，
   校验链形同虚设（有用例专门断言这一点）。
5. **票据必须绑人**：票是"持有即能用"的凭证，绑到 prepare 的那个人；
   别人的票一律按过期处理（并且**不**告诉调用方"这票有效但不属于你"）。
6. **场景可用性是封闭集合**：只有 `STABLE` 算可用——而岗位包**发布**时只要求"引用存在"。
   两者刻意不同：发布时场景可能还在验证（引用对、还不能跑）；员工点下去时它必须已经就绪。
7. **任务类型由请求声明并做封闭校验**：`aig_role_action` 没有这一列；加列会改变**已发布版本**的清单结构，
   而版本发布后不可变。拿平台不认识的类型去建任务，表现是"任务建出来了但永远不动"，比当场拒绝难查。
8. **幂等键原样透传给 `aig_task`**：任务域自己也按 `(业务域, 提交人, 幂等键)` 幂等，两层用同一个键，
   重复提交在哪一层都不会建出第二个任务。
9. **commit 的业务拒绝用 200 + `problems` 返回**（而不是抛异常）：前端需要稳定错误码来决定怎么提示；
   真正的系统故障仍抛异常走全局处理。代价是调用方必须看 `passed`——所以它与问题码一起返回。

**★真库探针抓到的真缺陷（值得记）**：第一版脚本 `org_id` 允许 NULL，探针里
`(NULL, 用户, 幂等键)` **可以重复插入**——因为**唯一键不约束 NULL**。
后果是"没有部门的用户"这一整类的幂等**静默失效**（同一个键提交两次会建出两次启动）。
这与本仓 `aig_task.create_by` 上已经踩过的是**同一个坑**。
修法：`org_id NOT NULL DEFAULT 0`，服务层在无部门时写 **0 哨兵**（不再写 NULL），
探针补上三条断言（NULL 被 DB 拒绝、0 哨兵第一次成功、0 哨兵重复被 1062 拒）。
**教训**：凡"幂等键 = 组合唯一键"的设计，组合里任何一列**可为 NULL** 都等于给幂等开后门。

### 6.1 门户接口与设计稿的对应关系（哪些做了、哪些刻意没做）

设计稿 §6.1 列了 9 个门户接口。落地情况与理由：

| 设计稿接口 | 落地 | 说明 |
|---|---|---|
| `GET /roles` | ✅ `/aigov/portal/roles` | 服务端按可见性过滤 |
| `GET /roles/{roleCode}/home` | ✅ `/aigov/portal/roles/{roleCode}/home` | 服务端过滤卡片 |
| `GET /actions/{actionCode}/availability` | ⭕ **由 `prepare` 承担** | `prepare` 本来就是**无业务副作用**的（不建任务、不改数据，只在通过时往 Redis 放一张会过期的票），并返回 `problems` + `willCreateTask` + 解析后的目标。再单独做一个 availability，就会出现**第二条判定路径**——而两条路径不一致的表现是"预检说行、启动说不行"（只有用户能发现） |
| `POST /launch/prepare` | ✅ | 见增量 3 |
| `POST /launch/commit` | ✅ | 幂等提交 |
| `GET /my-tasks` | ✅ **仅聚合 `aig_task`** | 见下 |
| `GET /my-artifacts` | ✅ **仅聚合平台产物台账** | 见下（增量 6） |
| `POST /intent/suggest` | ✅ `/aigov/portal/intent/suggest` | 默认关闭；走平台网关；结果与服务端可见卡片求交（见增量 7） |
| `POST /favorites` | ✅ `/aigov/portal/favorites` | 见增量 5（另加 `/pref`、`/default-role`） |
| （额外）`GET /launch/records/by-task/{taskId}` | ✅ | 专业台回跳入口用（增量 4） |

> **门户"不带权限点"这条决定有构建期守卫**：`AigPortalContractTest` 用**目录扫描**（不是写死的文件清单）
> 断言门户 controller 的每个端点都带 `@SaCheckLogin`、且源码里**不出现** `SaCheckPermission`
> （查注解名本身，所以写成全限定名也拦得住），并断言 `AigConstants` 里没有 `aig:portal:*` 常量。
> 理由：给门户端点加权限点是**静默失效**——编译过、单测过（控制器测试通常不挂真实鉴权），
> 运行期表现是所有员工打开工作台都是空白，日志里仅一行 403。要加就得先改这条用例，
> 那一刻人必须回答"这个权限点授给谁"。
> **这条守卫做过反证**：临时插入 `@cn.dev33.satoken.annotation.SaCheckPermission("aig:portal:view")`
> 后用例确实变红（证明它不是空跑），随后还原。守卫自己也要防"扫描不到东西却算通过"。

**为什么 `my-tasks` 只聚合 `aig_task`**

图片/视频的 `image_task` / `video_task`、资产的 `cp_task_file` / `image_asset` / `video_asset`
分别属于各自模块，**它们的可见性规则也在各自模块里**。从本模块直接读那些表，等于把它们的访问规则
复制一份到 aigov——两份规则迟早不一致，而不一致的方向恰好是**放行**（越权）。
正确的接法是各域在 `ruoyi-api` 里提供只读端口（像 `DeptService` 那样），本模块只调端口。
这次没有为了让接口"看起来完整"而先直连那些表：**宁可少一个接口，也不要多一条自己猜出来的权限规则。**

> **2026-10-11 已按这个方向落地（增量 8，`/my-assets`）**：各域实现了 `MyAssetPort`，门户只做分组展示，
> 仍然**不直连**任何业务域的表。见 §十一。

`aig_task` 是例外且已落地：它是**平台的任务台账**（创作/内容的 EXTERNAL 任务也落在它上面），
而且平台任务本来就按登录用户归属，所以 `/my-tasks` 按 `create_by = 当前用户` 聚合它既准确又不越界。

**`my-artifacts`（增量 6）：这一条做得成，但只做平台台账那一段**

`aig_task_artifact` 同样是**平台自己的产物台账**（ADR-010），与任务域在同一个模块里，
而且它的可见性口径只有一条：**任务的提交人**。注意产物行自己的 `create_by` 是**生产方**
（执行器/调度器），不是员工——所以归属必须通过 JOIN `aig_task` 取，并且只取
`validation_status = 'PASS'`（与任务域默认查询同口径：被拒记录是证据，但不是给员工下载的东西）。

实现要点：`AigPortalArtifactMapper`（只读、`IPage` + XML）里**没有**"查谁的"这个参数，
`userId` 由服务层从登录态取；VO 只带元数据，**刻意不带**
`storage_ref` / `sha256` / `hash_verified` / `validation_detail` / `result_id` / `attempt_no`，
也**不给下载直链**（下载走专业台/任务域，那里的权限仍然生效）——这几条由
`AigPortalVoBoundaryTest` 逐字段钉住。

真库探针（3434，跑的是仓库自己的两份 DDL）验证了 SQL 语义：只返回"我的任务 + PASS + 未删除"那一条；
按**别人的** taskId 过滤为空；FAIL 与被删任务的产物都被排除；另一个用户只看到自己的；
DDL 重放后数据一字不变。

> 顺带修掉一处本增量自己引入的不一致：增量 4 把项目权改成 fail-closed 之后，
> 启动表单里的「项目ID」如果还留着可填状态，就会变成"填了必然被拒"。
> 现在它是**禁用 + 说明**（"项目绑定暂不可用"），后端判定口接入归属来源后再一起打开。

## 七、增量 5：门户偏好（收藏 / 默认岗位）（✅ 已完成）

对应附件 §6.1 的 `POST /ai-workspace/favorites` 与设计稿 §5 的 `aig_user_workspace_pref`。

**落地物**

| 层 | 文件 |
|---|---|
| 建表 | `script/sql/aig_user_workspace_pref.sql`（**`org_id NOT NULL DEFAULT 0`**，唯一键 `(user_id, org_id)`） |
| 实体/Mapper | `portal/domain/AigUserWorkspacePref`、`portal/mapper/AigUserWorkspacePrefMapper` |
| 编解码 | `portal/helper/AigWorkspaceFavorites`（`decode` / `encode` / `toggle`，+4 用例） |
| 服务 | `portal/service/IAigPortalPrefService` + `impl`（+6 用例） |
| 接口 | `portal/controller/AigPortalPrefController`：`GET /aigov/portal/pref`、`POST /favorites`、`POST /default-role`（都是 `@SaCheckLogin`） |
| 前端 | `api/aigov/portal/*` 加三个函数、`views/aigov/portal/index.vue`（星标收藏、设为默认、清空默认、收藏排前）、`presentation.ts` 加 `isFavorite` / `sortRolesByFavorite`（+1 用例） |

**四条取舍**

1. **偏好不参与可见性判定**：收藏与默认岗位只是"我想先看哪个"。展示哪些岗位**只认 `/roles` 的返回**；
   收藏清单里可能有已经不可见的岗位，所以排序是"把可见的收藏排到前面"，
   而不是"按收藏清单重建列表"——后者会让界面出现无法解释的空位。
2. **收藏/设默认前必须确认岗位对本人可见**：否则偏好表会变成一个"验证某个岗位编码存不存在"的探针，
   而且用户能收藏一个永远打不开的岗位（点了没反应）。
3. **留空即清空默认岗位**：只能"换一个默认"却没法"取消默认"时，用户无法表达"我不想有默认"。
   界面上单独给了「清空默认岗位」入口。
4. **坏数据不挡路 + 有上限**：收藏是偏好，一串坏 JSON 不该让员工打不开工作台，所以解码遇非法内容
   按"没有收藏"处理；同时只接受**字符串**条目（把 `1`/`true` 也收进来会存下永远匹配不上岗位的假条目）。
   收藏有上限（200），到上限**不记录新的、但不动已有收藏**——静默丢弃会让用户以为"点了没反应"。

**★复合唯一键的 NULL 陷阱（本仓第三次）**：`org_id` 若允许 NULL，**唯一键不约束 NULL**，
于是"没有部门的用户"能存出多份偏好（表现：我设的默认岗位一会儿变一个）。
这与 `aig_task.create_by`、`aig_launch_record.org_id` 上踩过的完全同一个坑。
这次在**建表时就**写成 `NOT NULL DEFAULT 0` + 服务层 `NO_ORG_SENTINEL = 0L`，
并由探针三条断言钉住（NULL 被 DB 拒 1048、0 哨兵首次成功、0 哨兵重复被 1062 拒）。

**验证**

| 项 | 结果 |
|---|---|
| aigov 单测 | **815 → 825**（+10：收藏编解码 4、偏好服务 6）；全量 **825/825** 绿 |
| 前端 | vue-tsc **0 error**、oxlint **0/0**（493 文件）；单测 **34 文件 / 354 → 355 用例** 通过 |
| 真库探针（临时 MariaDB 3432） | 脚本 exit=0；`org_id` **NOT NULL**、唯一索引 `(user_id,org_id)` **有序覆盖 2 列**；同 user+org 重复 → **1062 拒**，换组织/换用户 → 允许；**NULL org 被 DB 拒（1048）**、0 哨兵重复 → **1062 拒**；`favorites_json` 是 longtext；**重放 exit=0 且行数不变** |

> 探针自身又踩了一次"字面量过 `-e` 被破坏"的坑：这次是 **JSON 里的双引号**（`'["R1"]'` 被命令行吞掉引号后
> SQL 语法错）。证法是改用 `concat(char(91),char(34),'R1',char(34),char(93))` 拼装。
> 结论与之前一致、范围扩大：**探针 SQL 里不要出现中文字面量、也不要用裸双引号**，要拼就用 `char()`。

**前置**

- MariaDB/MySQL 单库（aigov 与各业务域同库，本方案没有跨库调用）；

  `script/sql/aig_ai_task.sql` 与 `script/sql/aig_task_artifact.sql`

  门户的后两个接口会在运行期报错，而单测与编译期都发现不了。

**按顺序执行（顺序有原因，别调换）**

|---|---|---|---|

## 九、增量 7：自然语言推荐（`/intent/suggest`）（✅ 已完成）

设计稿 §6.1 的 `POST /ai-workspace/intent/suggest`。它是唯一一个**会花真钱**的门户接口，
所以先把"哪些决定已经定了"写清楚——这三条都**沿用既有决定**，不是本次新拍的口径：

1. **走平台网关**（策略校验、配额、路由都在网关执行点）：与训练台的测试调用同一条链，
   不在推荐里另开一条调用通道。
2. **默认关闭**（`aigov.recommend.enabled=false`，与 `aigov.studio.test.enabled` 同口径）：
   开着就在花钱，所以由需要的人显式打开；关着时接口**明确报错**，而不是静默返回空列表。
3. **只推荐、不启动**：推荐只回答"哪几张卡片相关"，执行仍要用户确认（启动凭证见增量 3）。
   并且**推荐结果要按服务端算出的可见卡片做交集过滤**——提示词里只放可见卡片，
   但模型完全可能凭常识吐出不存在的编码，那种一律丢掉。

### 9.1 纯逻辑与开关（7a）

| 文件 | 作用 |
|---|---|
| `workspace/recommend/config/AigRecommendProperties` | 开关与上限：默认关、输入 ≤ 500 字符（硬上限 4000）、候选 ≤ 3（硬上限 10）、提示词清单 ≤ 60（硬上限 200）；另有 `capability-code`（默认 `intent_suggest`）与 `data-level`（默认 `INTERNAL`） |
| `workspace/recommend/helper/AigRecommendPromptBuilder` | 提示词构造：只列**本人可见**的卡片（列表本身就是一次外发）、要求严格 JSON（`{"actionCodes":[...]}`）、写明"只推荐不执行"；员工的**一句话需求**放在清单之后、【边界】之前 |
| `workspace/recommend/helper/AigRecommendParser` | 输出解析：**能容错但结论从严**——对象/纯数组/代码块/带前后解释都读得出；读不出结构→空列表；非字符串条目跳过；去重保序；超限截断。**可见性过滤不在这里**（由服务层用可见集合求交） |
| `AigRecommendHelperTest` | 4 条用例：提示词只含可见卡片 + 按上限截断；解析容错与从严两组合 |

### 9.2 服务层与接口（7b）

| 文件 | 作用 |
|---|---|
| `workspace/recommend/service/IAigRecommendService` + `impl/AigRecommendServiceImpl` | 服务层：关着报错 → 校验输入 → 取可见卡片 → 过网关 → 解析 → **与可见清单求交** |
| `workspace/recommend/domain/bo/AigRecommendSuggestBo` | 入参只有"一句话需求"（**不接受候选清单**：那会让推荐接口变成探测别人岗位编码的工具） |
| `workspace/recommend/domain/vo/AigRecommendResultVo` / `AigRecommendSuggestionVo` | 结果：推荐项 = `roleCode` + `roleName` + 门户卡片本体（`AigPortalActionVo`）。**不带** traceId/模型/策略原因——那些是运维视角，审计由网关写在 `aig_invocation_audit` |
| `POST /aigov/portal/intent/suggest`（`@SaCheckLogin`） | 门户端点，**不设权限点**（受 `AigPortalContractTest` 守卫） |
| 前端 `api/aigov/portal` + `views/aigov/portal/index.vue` | 一句话输入框 + 推荐结果卡片（可直接打开页面类、或打开启动表单）；`suggestionKey` 用 `roleCode#actionCode` 作列表键 |
| `AigRecommendServiceImplTest`（7 条） | 含**专门用例**：模型返回 `HALLUCINATED_CARD` 必须被丢掉 |

**服务层的三条取舍**

1. **调用失败要抛错，不能返回空**："没有推荐"与"这次没调成"是两件事。配额耗尽、策略拒绝、
   模型超时如果都返回空列表，员工会以为系统认为没有相关卡片——这类静默降级最难排查。
   （唯一不报错的"空"是：这个人当前确实没有任何可见卡片，此时**不调用模型**，如实说明原因。）
2. **候选清单只有一个来源**：`IAigPortalService#listMyRoleHomes` 的产物（与门户列表/详情
   共用同一条可见性路径）。编码来自模型，**卡片本体只可能来自服务端可见清单**，交集是结论的唯一出处。
3. **不带 `agentVersionId` / `taskId`**：推荐不属于任何任务，也不该被算作某个 Agent 版本的调用——
   否则推荐流量会被算进灰度证据。

**部署要点（运维）**

- 打开 `aigov.recommend.enabled=true` 后，还要登记能力编码对应的路由：默认能力是
  `intent_suggest`（可用 `aigov.recommend.capability-code` 改成别的），需在
  `aig_capability` + `aig_route_policy` 里给它一条可路由的策略（数据等级默认 `INTERNAL`）。
  没登记时调用会被网关拒绝，接口**报错**并说明原因——不是返回空。
- 推荐不新增任何表/脚本：审计复用 `aig_invocation_audit`，无需新的 SQL 落地步骤。

## 十、跨线裁定：运行时健康（`RUNTIME_UNHEALTHY`）不进入启动链（2026-10-11）

增量 3 起，启动校验链里 `runtimeUnhealthy` 一直是**写死的 `false`**，注释说明原因。本次把它
**正式裁定**（而不是继续挂在"待做"里），并加构建期守卫防它悄悄长成第二份判定：

1. **判定只有一处：路由引擎。** `AigRouteServiceImpl` 决定"这张卡片该用哪个模型"的同时判健康，
   口径是**只在明确「坏」（`DOWN`/`UNHEALTHY`）时排除候选，`UNKNOWN`/null/`DEGRADED` 一律放行**。
   理由：`health_status` 由人工点一下连通性测试才写入，绝大多数模型从未测过；要求 UP 等于把
   "没测过"判成不可用，会让所有既有路由失效。该口径由 `AigRouteServiceImplHealthTest`（7 条，
   含"空健康必须照常选中"与写入端词汇交集的反证）逐条钉住。
2. **启动链不自己判。** 它只保留一个**纯透传**布尔位（`AigLaunchChecklist.Input#runtimeUnhealthy()`）；
   今天没有任何地方把它置 true。启动前预检会**多一次路由查询**，且会与执行点形成两份判定
   （"预检说不行、执行说行"）——正是本项目反复踩过的"两份实现"。
3. **"健康未知"不算不可用。** 这一条与项目权判定刻意相反（项目权是"判不了就拒绝"）：健康**未知**
   是常态且不代表不可用；若当成不可用，所有从未测过的模型对应的卡片都会点不动。

**守卫**：`AigLaunchHealthBoundaryTest`（2 条）——目录扫描启动链源码
（`workspace/launch/**/*.java`，20 个文件，下限 15），不得出现健康数据源/路由解析入口
（`aig_model_governance`、`AigModelGovernance`、`healthStatus`、`HEALTH_BAD`、`dryRun`）；
并正向断言那个布尔位**仍然可用**（true → 只报 `RUNTIME_UNHEALTHY`，false → 放行）。
**已做反证**：临时在 `AigLaunchServiceImpl` 插入 `private static final String REVERSAL_PROBE =
"aig_model_governance";` → 用例变红，随后 `git checkout --` 还原全绿。

> 也就是说：要改成"启动前预检"，必须先改这条用例——那一刻人必须回答"预检与执行不一致时以谁为准"。

## 十一、增量 8：跨域资产聚合（`/my-assets`，按域分组）✅ 已完成

设计稿里"我的资产"要跨图片/视频/内容三个域。**做法是按域分栏，不做跨域全局排序/分页**
（2026-10-11 裁定）。理由：三个域的"我的"根本不是一回事，删除值也不同——

| 域 | 表 | "我的"口径 | 删除值 |
|---|---|---|---|
| IMAGE | `image_asset` | `user_id = 我`（模块自己的查询 `listOwnedAssets`） | `'2'` |
| VIDEO | `video_asset` | `user_id = 我`（同上） | `'2'` |
| CONTENT | `cp_task_file` | **所属任务的负责人**（`cp_task.owner_id = 我`） | `'1'` |

把它们合成一个列表再排序分页，就得在聚合层把三套口径揉成一个：要么内存归并（受数据量上限约束），
要么建聚合索引表（引入同步一致性问题）。**宁可不做全局分页，也不做一个会漏/会重的分页。**

**落地物**

| 层 | 文件 | 作用 |
|---|---|---|
| `ruoyi-api` | `org.dromara.asset.api.MyAssetPort` + `domain.MyAssetDTO` | 跨域只读端口：`domain()` + `listMyAssets(userId, limit)`；DTO 只放展示字段（**无存储键、无下载直链**） |
| `ruoyi-ai` | `image/api/ImageMyAssetPort`、`video/api/VideoMyAssetPort`、`asset/MyAssetRowMapper` | 直接复用各域自己的 `listOwnedAssets`（**不另写 SQL**）；`@ConditionalOnProperty` 与各模块同条件装配 |
| `ruoyi-content` | `api/ContentMyAssetPort`、`CpTaskFileMapper#listOwnedAssetRows` | JOIN `cp_task` 按 `owner_id` 过滤；附件自己的 `create_by` 是**上传动作的人**，不是责任人，所以不用它 |
| `ruoyi-ai-gov` | `portal/service/IAigPortalAssetService` + impl、`AigPortalAssetGroupVo`/`AigPortalMyAssetVo`、`GET /aigov/portal/my-assets`（`@SaCheckLogin`） | 只做分组展示；不判可见性、不直连业务域的表 |
| 前端 | `api/aigov/portal` + `views/aigov/portal/index.vue` + `presentation.ts#assetDomainLabel` | "我的资产"卡片：按域分栏、空栏如实显示 |

**三条取舍**

1. **域不是"有数据才出现"**：接了提供方但你没数据 → 该栏出现且为空；没接这个域 → 该栏不出现。
   两者含义不同，都显示成"空"会让"没上线"和"你没东西"混为一谈。
2. **单域故障不静默成空**：某个域的查询失败会让整个接口报错（界面 catch 后弹错），
   而不是把那一栏显示成"没有资产"——后者是最难排查的静默降级。
   同理，界面 catch 是必须的：否则一个域的故障会把整页刷新变成未捕获异常。
3. **同域多个提供方只认第一个**（按 `domain()` 排序固定），并在日志里告警配置重复：
   让结果由代码决定，而不是由 Bean 扫描顺序决定。

**验证**：aigov **846 → 853**（+7：聚合 6 + 门户 VO 边界 1）；`ruoyi-api` / `ruoyi-ai` / `ruoyi-content`
三个模块 `test-compile` 全绿；vue-tsc 0 error、oxlint 0/0、前端 **361 用例**。

**真库探针（端口 3435，临时 MariaDB 11.4）**：跑仓库自己的 `ry_image_task.sql` + `ry_video_task.sql` +
`cp_content.sql`，插入两个用户的数据后直接跑**各端口实际执行的那三条 SQL**：

| 图片/视频：只回本人 + `del_flag='0'`，按 id 倒序 | image `204 201`、video `301`（**删掉的那条被排除**） |

### 11.1 增量 10："最近资产"有界合并视图（✅ 已完成）

`/my-assets` 是**按域分组**的，界面上"最新一条在哪"要三个栏来回看。所以加了一个合并视图：
`GET /aigov/portal/my-assets/recent` —— 各域各取最近 10 条后按**时间倒序**合并，最多显示 **20** 条。

**它不是分页**（刻意如此）：没有 `total`、翻不到第二页、不承诺全量。路径也写成 `/my-assets/recent`
而不是给 `/my-assets` 加 `page` 参数——后者会让人以为它能翻页。真正的跨域全局分页要么内存归并
（受数据量上限约束），要么建聚合索引（引入同步一致性问题），在拿到真实产品需求前不做。

**实现要点**：排序是"时间倒序（无时间的排最后）→ 域 → ID"，三级键**保证结果稳定**——
两个域的资产可能同一秒创建，只按时间排会"刷新一下次序就变了"。合并项逐条带 `domain`，
否则看不出这条来自哪个域。
