### 11.3 ★发现并修复一个真缺陷：「无变化提案」的守卫是**死的**

**现象（可复现）**：对一份草稿，把 `/objective` 改成与草稿**完全相同**的值 → 提案**被接受**并落库（应被拒）。
把值换成"草稿里真实的值"（先从草稿详情读出来）再试，仍然被接受。

**根因（本地确定性证明，非推测）**：内容哈希有两条路径，且它们**算出不同的值**——

| 路径 | 算的是哪份 JSON |
|---|---|
| 写入草稿 `AigStudioDraftServiceImpl#createDraft` | 调用方**提交的那串**（`canonicalize(bo.getContentJson())`） |
| 改动草稿 `AigStudioProposalServiceImpl#hashOf` | 把 `contentJson` 解析成对象、**再序列化**后规范化 |

内容模型里带**非 null 默认值**的字段（`promptSections = new LinkedHashMap<>()`）在第二条路径中一定会被序列化出来
（`"promptSections":{}`），而调用方**省略**该字段时第一条路径的串里没有它 ⇒ 规范化结果多一个键 ⇒ 哈希不等
⇒ `if (afterHash.equals(draft.getContentHash()))` 恒为假 ⇒「提案没有产生任何内容变化」**永远不会触发**
（`apply` 里那处同源判断同理）。

**证明**（把观测变成可复现事实，而不是靠线上猜）：
1. 先在线上复现（`code=200`，创建了提案 `2109547082950877186`）；
2. 再在本地加一条断言把"两条路径必须一致"钉住 → **确实红**（`245b4873…` ≠ `99110d3e…`）；
3. 用临时诊断把两份规范化串打出来，差异是明确的：`{"agentCategory":…,"agentName":"A","objective":"出脚本"}` vs 同一串但多了 `"promptSections":{}`。

> ★为什么服务端骨架路径（页面上"新建草稿"）没暴露这个问题：`defaultSkeletonJson()` 走的就是**对象路径**
> 并且显式设了 `promptSections`，所以两条路径恰好一致。**只有"调用方传了 contentJson"这条入口会中招**——
> 这正是我用接口造数据时踩到的，也是外部/API 调用方会踩到的。

**修法（两条路径收敛成一条）**：让写入路径也走"对象往返"——
`AigStudioDraftServiceImpl#canonicalize(String)` 改为 `canonicalize(serialize(readValue(json)))`；
这样"存进去的串"就是"对象路径的规范化结果"，改动路径再算一次得到同一个值。
另给内容模型加 `@JsonInclude(NON_NULL)`（"不传"与"传 null"在内容语义上等价）。
**钉住测试**：`AigStudioContentHasherTest#pojoRoundTripCanonicalFormIsIdempotent`——
断言对象往返后的规范化结果**是不动点**、且哈希一致（修好后绿；修之前红）。

**★生效方式与前面不同**：这是**后端代码变更**（不是 SQL 种子），
**生产必须重新构建并部署后端镜像才会生效**；部署前生产上「无变化提案」仍然放行。

## 十五、写入口「防重复提交」的全面审计 + 构建期守卫（2026-10-12）

### 15.1 为什么要做

`@RepeatSubmit` 是**逐方法**加的注解：漏一个既没有编译期信号、也没有运行期信号，
只会在生产上表现成"**双击/网络重试多了一条账本行、多花了一次钱、或多推进了一次状态**"。
这与本仓已经踩过的 `menu_id` 撞号（权限行静默没种、接口永远 403）是**同一类失败形态**：
逐条声明、漏了没人知道。所以照同一套办法办——**把覆盖率做成构建期能红的检查**。

### 15.2 审计结果：没有"漏加"，但有 9 个入口需要**写明理由**

新增守卫 `ruoyi-modules/ruoyi-ai-gov/src/test/java/org/dromara/aigov/controller/AigRepeatSubmitCoverageTest.java`：
扫 `org.dromara.aigov` 下全部 `@RestController`，**每个写方法**（`@PostMapping`/`@PutMapping`/
`@DeleteMapping`/`@PatchMapping`，或 `@RequestMapping` 且 method 含写动词）**必须**带 `@RepeatSubmit`，
**除非**在 `EXEMPT_WITH_REASON` 里写明理由。另有两条自检：扫描结果非空、豁免清单无过期条目
（否则守卫自己会静默空转——这是上一次 `AigPermissionSeedCoverageTest` 留下的教训）。

实测扫出 9 个未保护入口，逐个查证后确认**都不是"忘了"**，而是各自已有更强或等价的机制：

| 入口 | 已有的机制 |

### 15.3 ★★一条容易把测试做废的运行时语义

读 `ruoyi-common-redis` 的 `RepeatSubmitAspect` 得到（默认间隔 **5000ms**）：

- `@Before`：用 `url + md5(token + 入参)` 作键，`setObjectIfAbsent` 成功才算"不是重复"；
- `@AfterReturning`：**结果 `R.code == 200` 时保留键**；否则 `deleteRepeatKey()`；
- `@AfterThrowing`：**一律删键**。

⇒ **防重键只在"第一次成功"时留着**。所以
**"用无效 body 连发两次，看第二次有没有重复提交提示"这个测法永远看不到提示**
（我第一次设计 TC-SEC-03 时就打算这么测——那是错的）。
该注解防的是"**成功之后**又被点一次"，而这恰好是会产生重复账本/重复计费/重复推进的那种；
"失败后重试"被放行则是**想要的行为**（否则一次失败会把用户堵在时间窗里）。
★要在生产上实测"触发"，**必须让第一次请求成功** ⇒ 必然落数据；这就是为什么本轮采用
"§11 实触发 + 本守卫把声明覆盖钉住"的组合，而不是在 9 个入口上各造一组账本。

### 18.1 现象（可复现，3/3）

### 18.2 三个关键观测（把"猜"排除掉）

| ① **轮次行不见了** | `/copilot/turns` 里始终只有 3 行（2 条 SUCCEEDED + 1 条 FAILED），**三次 500 一次都没留下** | 说明**不是"没走到插入"**——turn 行在调网关**之前**就插了（`chat` 第 100–110 行），而网关审计行**确实留下了**（见③）⇒ 插入执行过、**被回滚了** |

### 18.3 根因：跨事务边界 catch —— 内层事务方法抛异常会把共享事务标成 rollback-only

- `AigStudioCopilotServiceImpl#chat` 带 `@Transactional`；
- 它调用的 `AigStudioProposalServiceImpl#create` **也带** `@Transactional`
  （默认 `PROPAGATION_REQUIRED` ⇒ **参与同一个事务**，不是新事务）；
- 原设计是"**捕获** `create` 抛出的『模型越界』业务异常 → 记 `REJECTED` 后继续写结论"；
- 但内层事务方法抛异常时，Spring 会把**两者共享的那个事务**标记为 **rollback-only**；
  外层即使 catch 住并继续写完，**提交时仍抛 `UnexpectedRollbackException`**。

⇒ 用户看到被掩掉的 500，**整轮对话（含拒绝结论）被回滚**。
而 `aig_studio_copilot_turn` 的建表注释恰好写着：模型越界记 `REJECTED` 是
**"这条通道最该被看见的信号"**（说明提示词与白名单没约束住模型）——
**修之前，这个最该被看见的信号在生产上永远看不到。**

> ★**为什么单测全绿、线上却炸**：单测里没有事务代理，`catch` 住就能继续往下写；
> 只有真库上的**提交**才会炸。这与本仓早先"控制器测试不经过过滤器/鉴权"是同一类盲区
> （详见本次新增的守卫 `AigStudioProposalTransactionBoundaryTest` 的类注释）。

### 27.4 ★三个刻意的设计决定（都能变成你以后会问的问题）

**① 为什么是逻辑删除，不是物理删除。**
`aig_agent_resource_binding.delFlag` 上本来就有 `@TableLogic` ⇒ `deleteById` 会被框架改写成
"更新 del_flag"。行留着能回答"这条绑定曾经存在过"，而所有查询（含**重复检查**）
由框架自动追加 `del_flag='0'` ⇒ **删完同范围立刻可以重建**——这正是那句文案承诺的动作。
★**这条链还有一个隐性依赖**：如果哪天有人把 `@TableLogic` 去掉，逻辑删除仍会写 `del_flag`，
但**查询不再过滤已删除的行** ⇒ 重复检查会看见刚删掉的那条、回"同一条绑定已存在"，
而文案却让人"删掉旧的那条再建" ⇒ 用户会掉进死循环。**所以我把这个依赖钉成了断言**
（`AigAgentResourceBindingControllerTest#deleteIsLogicalSoSameScopeCanBeRebound`）。

**② 为什么不给删除入口加 `@RepeatSubmit`。**
本仓的守卫默认"每个写入口都要防重"，这里**故意申报豁免**：按 id 删除本身幂等
（重复点第二次得到"不存在或已删除"），而防重键默认 **5 秒**、
且**只在第一次成功时保留**（见 §15.3）⇒ 加了它会把"删掉之后马上重建"挡在 5 秒窗外，
**正好把本入口要支撑的操作破坏掉**。这条也用断言钉住了（`removeRequiresBindingPermissionAndMustNotBeRepeatGuarded`）。

**③ 为什么没有加"停用"（虽然选项里写了删除/停用）。**
`enabled` 看起来像少了个开关，但：
- 本表**没有执行语义**（附件 07 §10；§26.7 之前的 TC-RBD-09 源码审计已确认没有任何调用路径读它）
  ⇒ "停用"除了列表显示与筛选**没有任何运行时效果**；
- 更糟的是：**重复检查不看 `enabled`** ⇒ 一条被"停用"的绑定**仍然占着"同一范围"的名额**，
  用户于是被卡在"既用不了、也绑不上"的状态——那比现在更糟。
⇒ **删掉 + 重建**才是这个动作真正需要的语义。若你确实要"保留范围记录、只是暂时不用"，
说一声，我按"停用必须同步放掉重复检查名额"的口径来做（那是另一个设计，不是加个按钮）。

### 29.2 TC-ENV-01 的那 15 条索引（一条 SQL 全查）

```sql
select table_name, index_name,
       group_concat(column_name order by seq_in_index) as cols,
       case non_unique when 0 then 'UNIQUE' else '' end as uniq
  from information_schema.statistics
 where table_schema = database()
   and table_name in ('aig_studio_change_proposal', 'aig_agent_resource_binding',
                      'aig_studio_skill_draft', 'aig_studio_child_agent_draft',
                      'aig_studio_action_draft', 'aig_studio_copilot_turn',
                      'aig_sandbox_artifact_download')
 group by table_name, index_name, non_unique
 order by table_name, index_name;
```

### 29.3 TC-ENV-05 的唯一残留：宿主 env 有没有手工覆盖

**已经核完的三条**（都是仓里可查的事实）：

| 证据 | 结果 |
|---|---|
| `AigSandboxArtifactProperties` 的默认值 | `maxFileBytes = 64L*1024*1024`、`maxFilesPerRun = 200`、`maxTotalBytesPerRun = 512L*1024*1024` ⇒ **与用例期望的三个数完全一致** |
| `application-prod.yml` 有没有覆盖 | **没有** `aigov.sandbox.artifact` 段（grep 全仓 yml） |
| 部署脚本/compose 有没有用 env 覆盖 | **没有**（grep `.github` + `script`：无 `AIGOV_SANDBOX_ARTIFACT_*`） |

⇒ 所以生效值 **就是** 64MB/200/512MB，**除非**有人在宿主上手工加了环境变量。**只差这一条命令**：

```bash
docker exec <后端容器名> env | grep -i AIGOV_SANDBOX_ARTIFACT
```

- **空输出** ⇒ 生效值 = 代码默认 = 用例期望 ⇒ **TC-ENV-05 可以判 ✅**
- **有输出** ⇒ 把显式值记下来（用例原文也接受"已按需调整的显式值"）

★**为什么不能像其他项那样用行为探针**：`AigSandboxArtifactServiceImpl#upload` 的顺序是
**第 87 行 `requireRun(sandboxRunId)` → 第 100 行 `assertWithinLimits(...)`**——
**先查作业是否存在，后查限额**。没有真实沙箱运行，连"文件多大"这条校验都到不了，
而那两个限额报错文案本来是**自带配置值**的（`… + properties.getMaxFileBytes() + 字节（aigov.sandbox.artifact.max-file-bytes）`），
所以"能到那一步"就等于已经把值读出来了。⇒ 这条路与 G8-02 是**同一个宿主依赖**。
