| # | 坑 | 后果 |

## 一、发布前：确认 CI 成功 + 取得 digest

### 1.1 找到那次 CI

GitHub → **Actions → "Compile, test and build image"**（`ci.yml`）→ 选中 **head commit = `7ef870a…`** 的那次运行。

**必须先满足**：该运行 **status = success**，且它的 **Job Summary** 里有这样一段：

```
### Published image
`ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-7ef870a…`
Digest: `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:………`
```

> 没有 `Digest:` 这一行、或运行不是 success ⇒ **停止，不要发布**。

### 1.2 digest 的两种取法（建议相互核对一致）

```bash
# ① 权威来源：向 registry 解析 manifest digest
docker buildx imagetools inspect \
  ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-<7ef870a 的完整 40 位 SHA> \
  --format '{{.Manifest.Digest}}'

# ② CI 推送日志里那行（backend 镜像发布作业）
#    sha-<sha>: digest: sha256:<64hex>
```

两者应给出**同一个** `sha256:<64hex>`。
**部署输入必须是** `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>`（工作流用正则强校验这个形状）。

## 二、触发发布

### 方式 A：网页（推荐）

**Actions → Deploy Shenzhen Production Backend → Run workflow**

| 输入 | 怎么填 |
|---|---|
| `image` | **必填**：`ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<上一步的 64 位十六进制>`（**覆盖掉默认值！**） |
| `allow_unknown_disk` | 保持 **false**（它是磁盘读不到时的应急放行口子，会在日志留痕；正常不该用） |
| `preload_archive_sha256` | 仅当走 LAN 搬运（§四）时填，否则**留空** |
| `preload_archive_bytes` | 同上 |

### 方式 B：`gh` CLI

```bash
gh workflow run deploy-poc.yml \
  -f image='ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>'
```
（`-f preload_archive_sha256=… -f preload_archive_bytes=…` 仅在 LAN 搬运时需要。）

**触发后**：到 **Actions** 看那条 run；工作流跑在自托管 runner `[shenzhen, deploy]` 上，环境 `shenzhen-production`，并发组 `shenzhen-production`（同一时间只会有一个发布在跑）。

## 三、这条工作流会做什么（照着核对即可，不用干预）

按 `deploy-poc.yml` 的实际步骤：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | Validate image reference | 只接受 `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>`；归档校验和/字节数若填了也要合法 |
| 2 | **Pre-flight host capacity** | 根分区 **< 3GB 可用就拒绝**（2026-10-08 的事故：磁盘满会让**部署与回滚一起失败**）；顺手清掉多余的 `ruoyi-web-previous-*`（保留最近 3 个）。**读不到磁盘状态也拒绝**（除非显式开 `allow_unknown_disk`） |
| 3 | Checkout | `persist-credentials: false` |
| 4 | Preload（可选） | 仅当填了 `preload_archive_sha256`：`script/ci/registry-image-archive.py load` 把归档装进宿主 docker |
| 5 | **Prepare additive runtime schema** | ★**它自己会跑一批"只新增"的建表脚本**（对 `ai-video-poc-mysql-1` 的库 `ai_video_poc`），其中**包含本次的 5 份新建表**：`aig_studio_change_proposal` / `aig_studio_copilot_turn` / `aig_studio_artifact_draft` / `aig_agent_resource_binding` / `aig_sandbox_artifact_download`。都是幂等 `create table if not exists` ⇒ **无需手工再跑** |
| 6 | Deploy and verify backend | `sudo /usr/local/sbin/hotter-release backend "$IMAGE"`——这个受审计的入口自己做 registry 登录、候选镜像校验、**只切服务**、**失败自动回滚代码** |

**它明确不会做的**（`script/deploy/README.md` 的契约）：不 `docker compose down`、不删数据卷、不导 SQL、不恢复数据。

> ⚠️ 这一步**不包含菜单/权限脚本**（`aig_studio_menu.sql` 等）。那 5 份**已在本轮执行过**（`13-…md` 有实测证据）；若将来换到全新库，仍需按 `11-…执行单.md` §四 手工跑。

**顺带把 `11-…执行单.md` 里的占位符填上**（供查库/排障用）：
`<库名>` = **`ai_video_poc`**、`<mysql容器>` = **`ai-video-poc-mysql-1`**、宿主发布入口 = **`/usr/local/sbin/hotter-release`**、宿主环境文件 = `/opt/ai-video-poc/.env`。

## 四、宿主拉不动镜像时（走 LAN 搬运）

症状：工作流在 `docker login/pull` 阶段失败（宿主到 GHCR 网络不通）。做法（runbook §4.6 + README）：

1. 在能拉取的机器上按 digest 拉取并打包（**digest 必须与 CI 发布的完全一致**）：

```bash
docker pull ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>
docker save ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex> -o backend.tar
sha256sum backend.tar          # 记下这个 64 位十六进制
stat -c%s backend.tar          # 记下字节数
```

2. 把 `backend.tar` 送到宿主（或按 README 用仓库里的归档工具生成/校验）；
3. 重新触发 `deploy-poc.yml`，这次**额外**填：
   - `preload_archive_sha256` = 上面那个 sha256（64 位小写十六进制）
   - `preload_archive_bytes` = 上面那个字节数（1–10 位数字）

工作流会先 `registry-image-archive.py load` 装进宿主 docker，再走第 6 步切流。

## 六、失败怎么处置 / 怎么回滚

| 现象 | 判断 | 处置 |
|---|---|---|
| 第 1 步就失败 | `image` 形状不对，或用了 config digest | 按 §1.2 重新取 manifest digest |
| 第 2 步失败（磁盘） | 根分区 < 3GB | **先清盘**（`docker builder prune -af`、删陈旧 `previous-*` 容器、按 `image-gc.sh` 清旧镜像），再重发。**不要**用 `allow_unknown_disk` 绕 |
| 第 6 步失败 | 入口会**自动回滚代码**（它自己校验并切回上一个） | 看 run 日志确认已回滚；再查 registry 凭据（README §"Registry credential"：必须是 **classic PAT + 只 `read:packages`**） |
| 发布成功但 §二 第 2 步没有 `promptSections` | **跑的还是旧后端** | 检查 `image` 是否真是 `7ef870a` 的 digest（别是默认值） |

**主动回滚**：用**同一条工作流**，`image` 填**上一次记录的** digest（以及前端的 `git_sha`，如果也发了前端）。
→ `Actions → Deploy Shenzhen Production Backend → Run workflow → image=<上一个 digest>`。
数据与对象存储**不动**；新表与菜单行**不必回滚**（旧代码不读它们）。
