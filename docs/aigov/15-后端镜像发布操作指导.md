## 一、发布前：确认 CI 成功 + 取得 digest

### 1.1 找到那次 CI

GitHub → **Actions → "Compile, test and build image"**（`ci.yml`）→ 选中 **head commit = `7ef870a…`** 的那次运行。

**必须先满足**：该运行 **status = success**，且它的 **Job Summary** 里有这样一段：

```
### Published image
`ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-7ef870a…`
Digest: `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:………`
```

> 没有 `Digest:` 这一行、或运行不是 success ⇒ **停止，不要发布**。

### 1.2 digest 的两种取法（建议相互核对一致）

```bash
# ① 权威来源：向 registry 解析 manifest digest
docker buildx imagetools inspect \
  ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-<7ef870a 的完整 40 位 SHA> \
  --format '{{.Manifest.Digest}}'

# ② CI 推送日志里那行（backend 镜像发布作业）
#    sha-<sha>: digest: sha256:<64hex>
```

两者应给出**同一个** `sha256:<64hex>`。
**部署输入必须是** `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>`（工作流用正则强校验这个形状）。

## 四、宿主拉不动镜像时（走 LAN 搬运）

症状：工作流在 `docker login/pull` 阶段失败（宿主到 GHCR 网络不通）。做法（runbook §4.6 + README）：

1. 在能拉取的机器上按 digest 拉取并打包（**digest 必须与 CI 发布的完全一致**）：

```bash
docker pull ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex>
docker save ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:<64hex> -o backend.tar
sha256sum backend.tar          # 记下这个 64 位十六进制
stat -c%s backend.tar          # 记下字节数
```

2. 把 `backend.tar` 送到宿主（或按 README 用仓库里的归档工具生成/校验）；
3. 重新触发 `deploy-poc.yml`，这次**额外**填：
   - `preload_archive_sha256` = 上面那个 sha256（64 位小写十六进制）
   - `preload_archive_bytes` = 上面那个字节数（1–10 位数字）

工作流会先 `registry-image-archive.py load` 装进宿主 docker，再走第 6 步切流。

## 六、失败怎么处置 / 怎么回滚

| 现象 | 判断 | 处置 |
|---|---|---|
| 第 1 步就失败 | `image` 形状不对，或用了 config digest | 按 §1.2 重新取 manifest digest |
| 第 2 步失败（磁盘） | 根分区 < 3GB | **先清盘**（`docker builder prune -af`、删陈旧 `previous-*` 容器、按 `image-gc.sh` 清旧镜像），再重发。**不要**用 `allow_unknown_disk` 绕 |
| 第 6 步失败 | 入口会**自动回滚代码**（它自己校验并切回上一个） | 看 run 日志确认已回滚；再查 registry 凭据（README §"Registry credential"：必须是 **classic PAT + 只 `read:packages`**） |
| 发布成功但 §二 第 2 步没有 `promptSections` | **跑的还是旧后端** | 检查 `image` 是否真是 `7ef870a` 的 digest（2026-10-12 起该输入已无默认值，不太可能再"点了默认值"，但仍要核对粘进去的那串） |

**主动回滚**：用**同一条工作流**，`image` 填**上一次记录的** digest（以及前端的 `git_sha`，如果也发了前端）。
→ `Actions → Deploy Shenzhen Production Backend → Run workflow → image=<上一个 digest>`。
数据与对象存储**不动**；新表与菜单行**不必回滚**（旧代码不读它们）。

## 九、★部署前就绪性核查（**已于 2026-10-12 修好，此节保留为自查与兜底**）

### 9.1 这个坑是什么（历史问题，现已修复）

`deploy-poc.yml` 原先只自动重放 **12 份**"只新增"脚本，而 `script/sql/` 下有 **11 份 `aig_*` 加列迁移不在清单里**。

**风险形态很隐蔽**：少一列时 **部署本身会成功**（工作流全程绿、容器健康、版本号也对），但新镜像的相关接口会 500；
而且 RuoYi 把 SQL 异常统一掩成 `发生未知异常，请联系管理员`——**响应与日志里都看不到"缺哪一列"**。

**根因与修法**（见 **§9.4**）：这些补列脚本当初没被收进清单，只是因为"看起来不能重放"——
MySQL 8.0 没有 `ADD COLUMN IF NOT EXISTS`；实际上它们一律用 `information_schema` 判断 + `PREPARE`
动态执行 DDL 实现了幂等，**本来就可以安全重放**。

### 9.2 一条 SQL 列出"缺的表/列"（**任何一行输出都表示有问题**）

> 用途：①部署的是**早于本次修复的**工作流版本时，用它兜底；②日后怀疑"库比镜像旧"时，用它一句话定位。
> 如果部署的是 2026-10-12 之后的工作流，工作流自己会把该补的都补上，这两条查询应当返回 0 行。

```sql
-- ① 本次新增的 7 张表（缺任何一张都不行）
select t.name as missing_table
from (select 'aig_studio_change_proposal' name union all
      select 'aig_agent_resource_binding'      union all
      select 'aig_studio_skill_draft'          union all
      select 'aig_studio_child_agent_draft'    union all
      select 'aig_studio_action_draft'         union all
      select 'aig_studio_copilot_turn'         union all
      select 'aig_sandbox_artifact_download') t
left join information_schema.tables i
  on i.table_schema = database() and i.table_name = t.name
where i.table_name is null;

-- ② 11 份"不在部署清单里的加列迁移"所需的列（缺任何一列都不行）
select w.tbl as missing_column_table, w.col as missing_column
from (select 'aig_sandbox_run'      tbl, 'attestation'     col union all
      select 'aig_invocation_audit',      'agent_version_id'   union all
      select 'aig_invocation_audit',      'error_class'        union all
      select 'aig_invocation_audit',      'provider_id'        union all
      select 'aig_invocation_audit',      'usage_json'         union all
      select 'aig_invocation_audit',      'input_snapshot_ref' union all
      select 'aig_invocation_audit',      'scenario_code'      union all
      select 'aig_evaluation_run',        'executed_by'        union all
      select 'aig_model_governance',      'capability_tags'    union all
      select 'aig_model_governance',      'cost_limit_amount'  union all
      select 'aig_package_version',       'body_ref'           union all
      select 'aig_skill_version',         'package_version_id' union all
      select 'aig_task',                  'execution_mode') w
left join information_schema.columns c
  on c.table_schema = database() and c.table_name = w.tbl and c.column_name = w.col
where c.column_name is null
order by 1, 2;
```

**两条查询都返回 0 行 ⇒ 库与镜像对齐。** 有输出 ⇒ 该列/表确实缺：部署 2026-10-12 之后的工作流会自动补；
若手工补，直接重放 `script/sql/` 里对应的迁移即可（幂等）。

| # | 改动 | 为什么 |
|---|---|---|

**加了构建期守卫**：`ruoyi-modules/ruoyi-ai-gov/src/test/java/org/dromara/aigov/deploy/AigDeploySchemaReplayCoverageTest.java`（4 条）
—— 把"清单完整性"和"脚本幂等性"都钉在 CI 上，防止日后新增补列脚本又忘在清单外：

1. `everyAdditiveAlterMigrationIsReplayed`：`script/sql/aig_*.sql` 里**每个含 `ALTER TABLE` 的脚本都必须出现在重放清单里**；
2. `replayedMigrationsAreIdempotent`：清单里的脚本**必须自己幂等**（含 ALTER 的要有 `information_schema` + `PREPARE`；建表的要有 `IF NOT EXISTS`）——不幂等意味着第二次部署会在切镜像前以 `Duplicate column name` 失败；
3. `repoRootIsLocatable`、4. `replayListParserItselfWorks`：定位逻辑与**解析器本身**都要有断言，否则守卫会静默空转。

**守卫已验证不是空转**（先红后绿的实证）：加清单**之前**跑 →
`Tests run: 4, Failures: 1`，报错点名列出的正是那 11 份脚本；加进清单后 → **`Tests run: 4, Failures: 0`**；
`ruoyi-modules/ruoyi-ai-gov` 全模块 → **1041 tests, 0 failures, BUILD SUCCESS**（较上次 1037 多 4 条，无回归）。

> 保留它是因为它对"部署旧版工作流"和事后排障仍然有用。
