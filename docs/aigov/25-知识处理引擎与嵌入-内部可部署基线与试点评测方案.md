# 25 - 知识处理引擎与嵌入：内部可部署基线与试点评测方案

> 依据：附件《Agent 平台优化详细设计 v1.0》§6.4（知识中心）、§7.4（知识检索与引用）、
> 以及附件「依赖与选型」行的要求——**知识处理引擎：优先内部可部署，按试点评测选型**（技术负责人）。
> 分支：`feature/aigov-optimization-v1`。阶段 C 的数据模型/端口/接口见 `21-…阶段C实施说明.md`。

---

## 1 这份文档回答什么

附件把"用哪个引擎、哪个嵌入、哪个向量存储"交给**试点评测**决定，同时要求**优先内部可部署**。
这条要求如果只写在文档里，落地时会出现两种坏结果：

1. 链路是空的——"等选型"变成"什么都没有"，试点阶段连一批资料都跑不进去，评测也就无从谈起；
2. 悄悄硬编码一个方案——评测结论出来没人知道当初钉的是哪一个，也没人敢换。

本轮的落地方式是：**端口 + 内部可部署的基线实现 + 明确的评测与切换流程**。
基线让链路现在就能端到端跑通（解析 → 分段 → 嵌入 → 索引 → 检索测试），
换引擎只需换实现并在配置里填 `engineId`，业务路径不动。

## 2 已落地的实现（本轮）

### 2.1 端口（换引擎/换存储的接缝）

| 端口 | 位置 | 约定 |
| --- | --- | --- |
| `KnowledgeParsePort` | `knowledge/pipeline/KnowledgeParsePort.java` | 字节进、**来源块（文本 + 定位）**出；取不到文本必须抛 `PARSE_FAILED`，不许返回空 |
| `KnowledgeEmbeddingPort` | `knowledge/pipeline/KnowledgeEmbeddingPort.java` | 文本进、**定长向量**出；同一文本必须永远同一向量 |
| `KnowledgeVectorIndexPort` | `knowledge/pipeline/KnowledgeVectorIndexPort.java` | 按版本**整版本替换**写入；检索返回**余弦相似度**（-1..1，越大越像） |

### 2.2 内置基线实现（内部可部署、零外发）

| 引擎 ID | 实现 | 支持 | 说明 |
| --- | --- | --- | --- |
| `pdfbox-3` | `AigPdfParseEngine` | PDF | **Apache-2.0、纯 Java、离线**；一页一个来源块，定位 `页 N`；扫描件/纯图 PDF **显式失败**并指向 OCR |
| `builtin-text-v1` | `AigPlainTextParseEngine` | TXT / Markdown | JDK 即可；编码按 BOM → 严格 UTF-8 → 严格 GBK 判定，判不出就失败；Markdown 定位带标题路径 |
| `builtin-docx-v1` | `AigDocxParseEngine` | DOCX | JDK zip + `word/document.xml`；段落定位 `第 N 段`（只数非空段）；解压有上限 |
| `builtin-hash-ngram-v1` | `AigHashedNgramEmbedding` | 嵌入 | **可用性基线，不承诺效果**：CJK 单字 + 相邻双字、拉丁词；FNV-1a 64 位哈希投放 + 符号位抵消碰撞 + L2 归一化 |
| `builtin-file-cosine-v1` | `AigFileVectorIndex` | 向量索引 | **单节点**文件索引（`aigov.knowledge.pipeline.vector-index-dir`）；整版本原子替换；维度不一致直接失败 |

选型过程的两条硬理由（都写进了代码注释，避免以后被"优化掉"）：

- **PDF 为什么用库而不是自研抠字节**：现代 Word/浏览器导出的 PDF 普遍用 Identity-H 子集字体，
  正文字形要查 ToUnicode 才能还原。自研版本对一部分文件会抽出乱码或空文本，而**乱码同样会被索引、
  被检索**，线上只表现为"检索得到、内容看不懂"，没有任何信号。PDFBox 满足"内部可部署"，代价只是一个 jar。
- **为什么先给文件向量索引**：评测需要"真的写进去、真的搜得出来"才有数据可比；占位实现让评测拿不到任何结论。
  它的边界（单节点、全量扫描、不做增量）写在类注释与 §4。

### 2.3 处理链路与状态推进

- `AigKnowledgeChunker`：短块按序合并到目标长度（定位写成**范围**，如 `行 12～行 18`、`页 1～页 3`）；
  超长块内部重叠切分（定位补 `（片段 k）`）；**超过分段上限直接失败**，绝不"只索引前 N 段"。
- `AigKnowledgeProcessor`：解析 → 分段 → 嵌入（纯计算、不碰库）；分段正文只以 `text_excerpt` 落库，
  因此**分段长度不得超过预览列宽**（配置不自洽时处理前就报错，而不是静默截断）。
- `IAigKnowledgeIndexingService#index`：**干完一步才记一步成功**（`SCANNING → PARSING → CHUNKING →
  INDEXING → READY`），每步一个幂等键（`键#阶段`）；**失败同时落库与抛错**；不加外层事务
  （长处理不该占着一个事务，而且外层回滚会把 `FAILED` 记录一起回滚掉）。
- 接口：`POST /aigov/knowledge/document-versions/{versionId}/index`（`multipart/form-data`：
  `idempotencyKey` + `file`），权限沿用 `aig:knowledge:document:manage`，**无新增权限点**。
- 分段物理重建：`uk_aig_knowledge_chunk (document_version_id, ordinal)` 不含 `del_flag`，
  逻辑删除会让重建撞唯一键，所以重建前物理删除该版本分段（见 Mapper 注释）。

### 2.4 检索测试可对比两种模式

`POST /aigov/knowledge/retrieval-tests` 新增 `mode`（`KEYWORD` / `VECTOR`，空=关键字），
返回体回显实际模式：

- `KEYWORD`：现状口径（`text_excerpt` 包含匹配 + 段序），**也是正式执行路径**；
- `VECTOR`：查询文本嵌入后走 `KnowledgeVectorIndexPort`，按余弦相似度降序，**落点回库复查授权**
  （索引只回 chunkId，越权或已删除的一律丢掉）。

**为什么先不给"混合模式"**："可组合"要回答的是**排序参数**（谁排前、权重多少），
而这正是附件交给评测决定的部分。先把两路各自跑通、拿同一批资料对比，混合权重再由评测结论产出，
比现在拍一个没人说得清出处的权重可靠。

## 3 试点评测方案（"按试点评测选型"怎么评）

### 3.1 评测集

| 项 | 要求 |
| --- | --- |
| 资料 | **已批准**的业务资料（产品手册、售后政策、内部规范为主），覆盖 PDF / DOCX / Markdown / TXT 四类；含至少 1 份扫描件（用于确认 OCR 是否必须） |
| 规模 | 建议 20–50 份文档、500–3000 段；先小后大——分段与索引的边界问题在小规模就能暴露 |
| 查询集 | **≥ 50 条**，必须包含三类：①字面直问（与原文用词一致）②**同义改写**（换词、换语序）③**多跳/组合**（需要两段资料合起来回答）；每条标注**标准答案所在文档与页码/段落** |
| 无答案集 | 另加 **≥ 10 条**"资料里确实没有"的查询——用于测"知不知道"（对应 §7.4 的"没有支持资料时说明不足"） |

### 3.2 指标与判据

| 指标 | 定义 | 首期期望（建议，须由评测会确认） |
| --- | --- | --- |
| 命中率 Recall@5 | 标准答案所在分段出现在前 5 条的比例 | 字面类 ≥ 0.9；同义类 ≥ 0.6（这是向量唯一可能带来增量的地方） |
| 引用正确率 | 返回的引用**定位**确实指向标准答案所在页/段的比例 | ≥ 0.95（引用错页比检索不到更糟：它让人按错的出处核对） |
| 拒答正确率 | 无答案查询返回"资料不足"的比例 | ≥ 0.9 |
| 分段可用性 | 人工抽查 30 条分段：是否成句、是否跨页、定位是否可核对 | 跨页/错页 = 0 |
| 处理耗时 | 单份 20 页 PDF 的解析+嵌入+索引耗时 | 供容量规划，不作硬门槛 |

**结论怎么来**：以"字面类"表现判断解析与关键字是否够用，以"同义改写类"判断是否必须换嵌入模型
（哈希基线在语义改写上预期很差，这正是要观察的），以"扫描件"决定是否必须接 OCR，
以"拒答正确率"判断是否可以先不接重排。

### 3.3 候选清单与切换方式

| 环节 | 候选 | 状态 | 切换方式 |
| --- | --- | --- | --- |
| TXT/Markdown 解析 | 内置 `builtin-text-v1` | **已选定为基线** | 配置 `aigov.knowledge.pipeline.parser-engine-id` |
| DOCX 解析 | 内置 `builtin-docx-v1` | **已选定为基线** | 同上 |
| PDF 解析 | `pdfbox-3`（Apache-2.0，内部可部署） | **已选定为基线** | 同上 |
| 扫描件 OCR | 内部可部署 OCR（待评测；如 Tesseract）或转人工录入 | **未选定**：先由评测集里的扫描件判定"是否必须" | 新增 `KnowledgeParsePort` 实现（`supports(PDF)` + 内部判定为纯图时接管） |
| 嵌入 | ①`builtin-hash-ngram-v1`（基线）②内部部署的本地嵌入模型 ③已批准的外部嵌入服务 | **基线可用，最终未定** | 新增 `KnowledgeEmbeddingPort` 实现；换引擎后**已就绪版本的向量全部失效**，需要重新处理（见下方注） |
| 向量存储 | ①`builtin-file-cosine-v1`（单节点）②共享向量库 | **基线可用，多副本上线前必须替换** | 新增 `KnowledgeVectorIndexPort` 实现 |
| 排序组合 | 关键字 / 向量 / 混合（权重待定） | **未选定**：本轮提供两种模式做对比 | 由评测结论定权重后，在正式执行路径接一路组合实现 |

> **换嵌入引擎之后怎么重建**：`/document-versions/{id}/index` **只处理未就绪的版本**——
> 已 `READY` 的版本会被明确拒绝（"不能原地重建"，见 `21` §5.3）。两条理由：①设计 §8.1 的
> 版本不可变；②重建是"先删该版本分段再写新的"，中途失败会留下"状态就绪但分段只剩一半"的版本，
> 而 `READY` 是终态、失败不会把它降级，阅读方看不出资料不完整。
> 因此"换引擎后的存量重建"属于**运维迁移作业**：登记新版本后逐个索引，或另写迁移任务
> （届时需要先把目标版本从 `READY` 迁出，属于独立变更）。

## 4 已知边界（不承诺的部分）

1. **准确率不承诺**：基线嵌入是"可用性基线"，不是效果结论；附件明确要求由评测确定。
2. **向量索引是单节点的**：默认落本地磁盘，多副本时每个实例只看得见自己写的文件；
   上线多副本前必须换成共享实现（同时把 `vector-index-dir` 指向共享卷只是权宜，并发写同一目录无协调）。
3. **全量扫描检索**：`builtin-file-cosine-v1` 把候选版本的向量全读进来算余弦；
   十万级分段会变慢——这也属于"评测后定"。
4. **不做 OCR、不做表格解析、不做重排**：扫描件直接失败并指向 OCR；XLSX 在登记阶段就被拒绝（走结构化导入）。
5. **文件本体不在本服务**：`/index` 由调用方上传文件；按 `sourceRef` 从对象存储取文属于后续接入范围。
6. **正文不落业务表**：分段只存受限长度的 `text_excerpt`；因此分段长度必须 ≤ 预览列宽（已由配置自检强制）。

## 5 验证

```bash
# 后端（知识相关）
./mvnw -o -Plocal -pl ruoyi-modules/ruoyi-ai-gov -am test "-Dmaven.test.skip=false" \
  "-Dtest=AigKnowledge*,AigPlainText*,AigDocx*,AigPdf*,AigHashed*,AigFile*,AigKnowledgeChunker*" \
  "-Dsurefire.failIfNoSpecifiedTests=false"
```

本轮新增/更新的测试（明细见 `24-…总体实施与评审说明.md` §4）：

- `AigPlainTextParseEngineTest`：编码判定（BOM/UTF-8/GBK/判不出即失败）、行号定位、Markdown 标题路径与围栏；
- `AigDocxParseEngineTest`：段落只数非空段、实体只解一遍（`&amp;lt;` 不变形）、制表/换行还原、三种坏输入；
- `AigPdfParseEngineTest`：每页一个来源块 + `页 N` 定位、扫描件失败指向 OCR、非 PDF 说明、归一化；
- `AigHashedNgramEmbeddingTest`：确定性/定长/归一化、空文本零向量、字面相近相似度更高、双字与大小写；
- `AigFileVectorIndexTest`：余弦排序、整版本替换、维度不一致失败、索引损坏暴露、非法条目；
- `AigKnowledgeChunkerTest`：短块合并（定位写范围）、超长块重叠切分、超上限失败、重叠夹取；
- `AigKnowledgeProcessorTest`：序号连续、等级原样传递、预览截断带省略号、配置不自洽报错、嵌入失败分类；
- `AigKnowledgeParseRegistryTest`：按类型选默认、指定引擎生效、指定不存在/不支持时报错；
- `AigKnowledgeIndexingServiceImplTest`：状态推进顺序与幂等键、分段落库内容与索引引用、整版本向量替换、
  幂等重入不重复处理、失败落库+抛错、上下文缺失报错；
- `AigKnowledgeRetrievalServiceTest`：新增向量模式（排序、越权落点丢弃、索引为空的原因、关闭/空向量同理）、
  向量路径与关键字**共用同一套授权判定**。
