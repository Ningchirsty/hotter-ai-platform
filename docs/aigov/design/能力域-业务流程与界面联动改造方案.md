# 能力域 · 业务流程与界面联动改造方案

> 你的要求：**先把业务流程逻辑梳理清楚，再和界面对齐**，避免"界面好看但用起来更难"。
> 本文档的顺序因此是：**流程现状 → 流程断点 → 目标流程 → 流程×界面对应 → 改造计划**。
> 界面基线仍是你已确认的 v3：**试调＝右侧常驻对话助手**、**详情＝整页 + 展开配置详情**（`治理台-能力域-demo-v3.html`）。
> 字段级细节见 `P0-能力域-字段级规格与改动清单.md`；现状证据见 `能力域-现状走读与重构方案.md`。

---

## 1 一页结论：**界面乱的根源，是流程没有单一入口**

界面那 23 条问题（导航平铺、ID 直出、无空态…）是"表症"。真正的"用起来困难"来自 5 条**流程级断点**：

| # | 流程断点 | 使用者会遭遇什么 |
| --- | --- | --- |
| **B1** | **能力上线没有门槛、也没有"生效确认"**：能力、候选模型、策略三者都是单人可增删改，改完没有任何"这条链路现在还能跑通"的确认（只有 Agent 版本发布有五道门槛） | 改完策略以为生效；直到某天业务调用失败才发现被自己的策略拒了 |
| **B2** | **试调（dryRun）不校验授权与配额** —— 它只跑路由决策（`AigInvokeServiceImpl.dryRun` 直接 `decide` 后返回），**不看** `hasValidGrant`、也不看 `assertWithinQuota` | "试调通过"被理解成"能调"，实际真实调用会被审批/配额拦下 → 白高兴一场（这条是读代码才发现，界面上必须说清） |
| **B3** | **系统/调度发起的调用，在需审批的能力上永远拿不到授权**：授权按 `callerId` 判定，调度/后台没有调用人 → 代码 fail-closed（`调用人（userId=null）对该能力×数据等级没有未过期授权`） | 定时任务/后台流程用不了"需审批"的能力，而且原因只在审计里 |
| **B4** | **员工与审批人没有自助界面**：`GET /aigov/quota/my-usage`（我的额度）与 `GET /aigov/approval/my`（我的申请）**接口已有、页面没有** | 员工只能去问管理员"我还能用多少""我申请到哪了" |
| **B5** | **变更与退役没有影响面**：改策略/换模型/删能力时，平台回答不了"谁在用这个能力"（`listResourceReferences` 只支持 TOOL / KNOWLEDGE，**没有能力维度**） | 一个能力被 N 个 Agent 版本引用，改动只能"先改再看谁报错" |

界面层随之要做的是：**把上面 5 条流程缺口在 v3 的 6 屏里"显形"并能就地处理**——而不是再加页面（那就更乱）。

## 2 现状业务流程全图（6 条流程）

### 流程 1｜能力上线（治理者）

```
①建能力            POST /aigov/capability          aig_capability（编码/名称/标签/输入输出 Schema/数据策略/审计等级）
②挂模型候选        POST /aigov/binding             aig_capability_model（能力×模型：用途 PRIMARY/FALLBACK/GRAY + 优先级）
③配路由策略        POST /aigov/route               aig_route_policy（能力×数据等级：允许外发 / 调用前审批 / 无模型时行为）
④（可选）场景指定  POST /aigov/route/binding       aig_route_scenario_binding（场景×能力→指定供应商，只收窄）
⑤（无）验证         —— 没有"这条链路能通吗"的确认步骤
⑥（无）发布门槛     能力/候选/策略都是即时生效，无审批、无生效记录
⑦观测             GET /aigov/audit/list           aig_invocation_audit
⑧变更/退役         PUT/DELETE 同上三组接口        无影响面、无引用校验
```
**断点**：⑤⑥ 完全缺失；⑧ 无保护。⇒ 这就是 B1/B5/B12。

### 流程 2｜Agent 接入能力（训练者）

```
①训练台草稿声明能力   前端手打 capabilityCode（studio:193 / artifactDraft:266）  ← 不校验存在性
②预检                AigStudioPrecheck → 只报 CAPABILITY_MISSING（"未声明"），不报"不存在"
③提交 / 发布         PUT /aigov/studio/draft/submit → 发布要过五道门槛（含三方人工批准）
④执行时路由          AigTaskExecutorImpl → AigInvokeService.invoke（带 capabilityCode/dataLevel/allowExternal/scenarioCode）
```
**断点**：①手打 + ③看不到"这个能力是否已就绪（有候选、有策略）"。⇒ 训练者拿到的是"提交成功"，不是"跑得通"。

### 流程 3｜一次真实调用（业务/员工）—— 真实顺序（读代码确认）

```
1 traceId
2 数据等级校验（PUBLIC/INTERNAL/RESTRICTED/STRICT）
3 路由决策 decide()：能力存在→策略命中→场景收窄→预算过滤→候选可用性(治理/生命周期/等级上限/健康/标签)→排序
4 写策略决策账本 aig_policy_decision_log（真实调用每次一行；**早期 return 也写**）
5 DENIED  → 审计 FAILED + errorClass=POLICY_DENIED → 返回（不调模型）
6 MANUAL  → 审计 FAILED + manualDecision=PENDING → 返回（转人工）
7 需审批？ hasValidGrant(callerId, capability, dataLevel) —— **在配额之前**（注释理由：没授权时的正确结论是"去申请"，不是"配额超了"）
8 配额     assertWithinQuota(callerId) → 超限 QUOTA_EXCEEDED
9 调模型   候选循环（失败换候选 / 重试）/ outputSchema 校验 / 错误分类
10 finally 审计落库 + 账本回填（实际执行的 model_id / external_call）
```
**断点**：这一步的每一步判定都很清楚，但 **用户侧看不到**：员工只知道"失败了"；
`reasonCode`（细因）与 `policyHits`（逐条排除原因）只进审计与账本，不进用户界面。⇒ B2/B8。

### 流程 4｜失败诊断（运维）

```
现状：任务详情 → 调用审计页（15 列 / 原始 JSON / 裸 ID）→ 能力页 → 路由策略页 → 模型页 → 回审计
问题：跨 4 个页面、零跳转；没有"这次决策的链路视图"；policyHits 只在审计表里躺着
```
⇒ B7。

### 流程 5｜授权与配额生命周期（审批人 / 管理员 / 员工）

```
员工被策略要求审批 → 应去治理台「调用授权」提交申请 → 审批人批准（带有效期 valid_until）
→ 有效期内免再审 → 过期 → 再来一遍
配额：管理员按人配日/月上限（要手填 sys_user.user_id）→ 员工无法自查剩余
超时扫描：POST /aigov/approval/expire-scan（挂 approval:approve 权限，无确认按钮）
```
**断点**：员工侧无"我的申请 / 我的额度"；审批人决策时看不到"这次调用的输入摘要与数据等级"；配额配错要先知道内部 ID。⇒ B4/B8。

### 流程 6｜变更与退役（治理者）

```
改策略 / 换候选 / 改标签 / 删能力 —— 全部即时生效，且：
· 没有"哪些 Agent 版本 / 任务在用这个能力"的清单（能力维度没有引用查询）
· 删除能力没有引用校验 → 候选/策略/审批里的行变孤儿，永远不生效
· 数据等级上限、生命周期、健康等治理属性改动，也没有"会影响哪些调用"的提示
```
⇒ B5/B12。

## 4 目标业务流程（To-Be）：3 条主旅程

### 旅程 A｜治理者：让一个能力"能跑通、可观测、可安全变更"

| 步 | 动作 | 界面上必须看到 | 必须能做什么 | 与现状的差别 |
| --- | --- | --- | --- | --- |
| A1 | 建能力（编码/名称/标签/人设） | 编码唯一性即时校验；人设字数计数 | 保存草稿 | 一致 |
| A2 | 挂模型候选 | **候选数、用途、优先级、健康**（缺则红） | 新增/编辑用途与优先级/停用 | **补编辑能力** |
| A3 | 配策略（能力×4 个数据等级） | **覆盖度 M/4**（缺的等级灰显） | 逐等级设置外发/审批/无模型时行为 | 一致 |
| A4 | （可选）场景指定 | 场景编码**从已有场景中选择**（非手打） | 新增/删除 | **补校验** |
| A5 | **链路体检** | 一屏结论：**候选/策略/场景/健康** + 缺环用橙色加号引导 | **右侧试图对话里点"会走哪条路"**（dryRun） | **新增** |
| A6 | 提交发布（**门槛待你拍板**） | 若加门槛：谁批、批什么（策略快照） | 提交/批准/驳回 | **可能新增** |
| A7 | 上线后观测 | 看板：调用量/失败率/外发量/失败 TOP | 钻取到某个能力的调用与决策 | **新增** |
| A8 | 变更 | **影响面**：哪些 Agent 版本/任务在用 | 一键看影响面 → 再改 | **新增** |
| A9 | 退役 | 退役后的影响与可恢复性文案 | 停用（不删）/删除（带校验） | 补校验 |

### 旅程 B｜训练者：让 Agent 用上"确实就绪"的能力

| 步 | 动作 | 界面上必须看到 | 与现状的差别 |
| --- | --- | --- | --- |
| B1 | 选能力 | **下拉即列能力 + 就绪状态**（就绪/缺候选/缺策略） | **从手打改下拉** |
| B2 | 预检 | 未声明 → 阻断；**不存在 → 阻断**；缺候选 → 阻断（附"去补候选"入口） | **补"不存在/未就绪"两类校验** |
| B3 | 试跑 | 复用同一试调助手（只读、不产生费用） | **新增** |
| B4 | 提交/发布 | 既有五道门槛不变 | 一致 |
| B5 | 看任务 | 任务详情 → 一键跳到"这次决策的链路视图" | **新增跳转** |

### 旅程 C｜员工 / 审批人：被拦时知道该做什么

| 步 | 动作 | 界面上必须看到 | 与现状的差别 |
| --- | --- | --- | --- |
| C1 | 发起任务 | 正常发起 | 一致 |
| C2 | 被拦（审批/配额/策略） | **人话原因**（"该能力在「限制」等级需要审批" / "今日额度已用完"）+ **下一步按钮**（去申请 / 找谁提额） | **新增**（`reasonCode` 翻译） |
| C3 | 申请 | 申请单：能力/数据等级/用途说明/期望有效期 | 一致（但入口更近） |
| C4 | 审批 | 决策卡：**申请人 · 能力 · 数据等级 · 输入摘要 · 接收方 · 有效期** | **补决策所需信息** |
| C5 | 自助 | **我的额度（剩余/上限/刷新时间）**、**我的申请（状态/有效期）** | **新增**（接口已有） |
| C6 | 到期 | 到期前提示 + 一键续期 | 新增（P2） |

| B3 试跑 | 复用试调助手 | 同上 | 提问 | 同上 |
| B5 任务跳转 | 任务详情 → 「本次决策」 | traceId/decision/policyHits | 跳链路视图 | `task:query` + `audit:list` |
| C2 被拦 | 门户/任务页的失败卡 | 人话原因 + 下一步 | 一键申请 | 既有 |
| C4 审批 | 调用授权页 | 申请要素 + **输入摘要** | 批准/驳回 | `approval:approve` |
| C5 自助 | 门户「我的额度/我的申请」 | 剩余/上限/有效期 | 自查 | 新增 `quota:self` / `approval:self`（或用 `/my-*` 免权限点口径） |

## 7 改造计划（按"流程收益"组织，而不是按页面；已并入 §8 的 6 条业务决定）

### P0 —— 让"能跑通"看得见（不改表、不加权限点）

| 交付 | 流程收益（谁不再需要做什么） | 界面对应 | 后端 |
| --- | --- | --- | --- |
| 能力清单（创建卡/筛选/卡片/hover 菜单） | 治理者不再靠编码在 12 个页面里找人 | v3 清单页 | + `GET /capability/overview` |

### 8.1 "高风险变更"清单（Q1 的落地定义，建议）

**需要 `aig:capability:high-risk` 才能做**：
1. 任一数据等级的策略行把 `allow_external` 从 `N` 改成 `Y`（放开外发）；
2. 新增一条 `allow_external='Y'` 的策略行；
3. 把某等级的 `preferred_deployment` 改成外部部署类型；
4. **数据等级 ≥ 限制（RESTRICTED/STRICT）** 的能力：新增/停用候选、改用途或优先级、改策略、改能力标签（都会改变路由结果）；
5. 删除能力、删除候选、停用能力（不可逆或影响面大）。

**不需要**：新建"内部/公开"等级的能力、改名称/描述、未放开的策略微调。
> 这份清单是**规则**，可配置化（P2 做成开关），但第一版写死并写进界面提示更稳妥。

### 8.2 Q2 的"取最高"示例（供你核对语义）

| 能力声明 `min_data_level` | 调用方传入 | 生效等级 | 效果 |
| --- | --- | --- | --- |
| 空（不声明） | INTERNAL | INTERNAL | 与现状一致 |
| 空 | STRICT | STRICT | 与现状一致 |
| **RESTRICTED** | INTERNAL | **RESTRICTED** | 业务方把等级标低也拦不住（这正是要堵的洞） |
| RESTRICTED | STRICT | STRICT | 取高 |
| STRICT | 任意 | STRICT | 该能力一律禁止外发 |

## 9 不做的事（防止越改越乱）

1. **不再新增一级导航**：A8 影响面放进详情区块、C5 自助放进门户，治理台导航保持在 6 个模块；
2. **不把"能力"和"Agent/工具/知识"合并成一个对象**：它们是四层（能力＝做什么；Agent＝谁在什么岗位用什么能力；工具/知识＝资源），合并会回到"绑"字四义的老问题；
3. **不给员工暴露 dryRun 与策略细节**：员工只需要"人话原因 + 下一步"；
4. **不做"自动修配置"**：助手只给建议，改动一律经人确认（与"机器只提议不生效"的平台规矩一致）；
5. **不在 P0 动表结构**：所有 P0 交付都可回滚为"关掉入口"。
