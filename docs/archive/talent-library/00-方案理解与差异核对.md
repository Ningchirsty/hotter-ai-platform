# 00 方案理解与差异核对

> 对设计文档《集团人才库详细设计方案 RuoYi-Vue-Plus v6.0.0》（v1.0 评审稿，2026-09-12）的逐节理解，以及与代码基线核对后发现的**必须修正之处**。

---

## 1. 方案本质（一句话）

不新建系统、不新建前端、不新增域名：在现有 RuoYi 管理后台内新增**一个一级业务目录 + 一个领域模块 `talent-library`（表前缀 `tl_`）**，平台能力（账号/组织/角色/菜单/数据权限/OSS/Excel/日志/加密脱敏）全部复用，只开发人才领域能力。

---

## 2. 方案的三条硬约束（决定了实现方式，不可妥协）

| # | 约束 | 出处 | 实现落点 |
|---|---|---|---|
| 1 | 区域范围**不能依赖前端参数**；列表必须服务端追加可见范围；按 ID 访问必须二次校验 | §4.3、§7.3、§8 | `TalentScopeHelper`（唯一权威实现），人才库 Mapper 不加 `@DataPermission` |
| 2 | **不自动合并、不命中即覆盖**：重复只给预警清单，人工确认结论落库 | §7.1 | `tl_talent_duplicate` + `duplicateConfirmed` 开关 |
| 3 | 敏感信息不外泄：手机号密文+哈希双存、查阅者脱敏、日志禁止记录完整号码/Token/简历正文/临时 URL、下载导出全量审计 | §5.2、§6.3、§10 | `@EncryptField` + `phone_hash` + `@Sensitive` + `TalentAuditRecorder`(REQUIRES_NEW) |

## 3. 与设计文档的差异（**已修正**，逐条给出依据）

| # | 文档写法 | 基线实际 | 处置 |
|---|---|---|---|
| 1 | §9 部署清单写 `mysql:8` / `redis:7`，但 §2、§9 表格、§10 写 MySQL 8.4 / Redis 8.6（**文档内部自相矛盾**） | v6.0.0 release notes：MySQL 8.4.9、Redis 8.6.3 | 统一到 **MySQL 8.4 / Redis 8.6**，与 6.0.0 基线一致 |
| 2 | §1.2 说"复用 RuoYi Excel 能力" | 6.0.0 已从 FastExcel 迁移到 **Apache Fesod**，导入导出构建器重构 | 实现按 Fesod 的 `ExcelBuilder` 写，**不沿用 5.x EasyExcel/FastExcel 写法** |
| 3 | §3.2/§4.2 隐含用框架数据权限做区域范围 | `DataScopeType` 是封闭枚举（1–6），模板只覆盖 `dept_id`/`create_by`，**无法表达 `region_code`**；且接口带 `@SaCheckPermission` 时若角色未绑定该 perms 会注入 ` 1 = 0 ` **静默空结果** | **不使用框架数据权限**，改为服务端显式区域过滤（理由见 `02-6.0.0框架API核对表.md` §2.3） |
| 4 | §6.2「文件上传至临时/隔离位置……才转为正式附件」 | `OssClient` **没有 copy/move 接口**，无法物理搬移 | 用 `scan_status` 状态机实现"扫描通过前禁止下载"，安全效果等价 |
| 5 | §5.1 `tl_talent_attachment` 记录 **RuoYi OSS 文件 ID** | 框架 `ISysOssService.upload` 写死对象键；且 `sys_oss` 下载接口只校验 `system:oss:download`，**登记进去会形成绕过人才库授权的下载旁路** | 改为 `OssClient` 自定义对象键直写 `talent-private/`，元数据只存 `tl_talent_attachment`；`oss_id` 保留为可空列备用 |
| 6 | §6.2「Nginx、Spring 与 OSS 三层一致配置 25MB」 | `application.yml` 的 `spring.servlet.multipart` 默认 10MB/20MB | 需在部署时显式改为 25MB（已列入验收清单 §9） |
| 7 | §5.1 手机号"密文 + 不可逆标准化哈希" | `@EncryptField` 的 `enable` **默认 false**，默认算法 BASE64（等于没加密） | 上线前必须置 `mybatis-encryptor.enable=true` 并配 AES 密钥（已列入验收清单 §9） |
| 8 | §10「POC 必须满足：病毒扫描」 | 框架不含杀毒；`OssClient` 也无隔离能力 | 一期提供 `scan_status` 状态机 + 回调接口，`talent.virus-scan-enabled=false` 时置 `CLEAN` 并留痕 |
| 9 | §12-P3 解析能力 | 6.0.0 已集成 Spring AI + snail-ai，**技术不是阻塞**；真正阻塞是 §13.4 的个人信息处理审批 | 默认 `talent.parse-enabled=false`，解析任务落 `DISABLED`，只用虚构样本 |
| 10 | §3.2 模块标识 `talent-library`，Java 包"按项目实际模块约定" | 6.0.0 模块命名统一为 `ruoyi-xxx` | artifactId `ruoyi-talent`，包 `org.dromara.talent`，表前缀 `tl_` 不变 |

## 4. 文档要求已逐项落到实现

| 文档章节 | 实现落点 |
|---|---|
| §3.2 六子模块 + 权限标识 | `sql/V2__talent_menu_role_dict.sql` 的 19 个权限标识与 `docs/04-接口契约与权限矩阵.md` |
| §3.3 菜单布置（一级目录 + 6 菜单） | V2 中 1 个 `M` 目录 + 6 个 `C` 菜单（component 与 `plus-ui/src/views/talent/*` 严格对应），**未新增前端路由文件** |
| §4.1 组织结构（集团—深圳—汕头） | 区域由 `tl_talent.region_code` 表达；区域范围**基于角色标识**而非部门，因此不依赖特定部门 ID，避免与现场组织数据耦合 |
| §4.2 角色与范围矩阵 | `docs/04-接口契约与权限矩阵.md` §3/§4，6 个 `talent_*` 角色 |
| §5.1 九张业务表 | `sql/V1__talent_schema.sql` |
| §5.3 索引与约束 | V1 中逐条落地（region+status+del_flag、phone_hash、name+region、attachment 当前版本、audit 检索） |
| §6.1 存储目录 | `talent-private/{talentId}/{attachmentId}/v{version}/original{ext}`、`talent-private/exports/{exportId}/talent-ledger.xlsx` |
| §6.3 Excel 台账 | `TlTalentExportVo` 列定义 + 链接指向应用入口（**不含任何 OSS URL**） |
| §8 接口设计原则 | `docs/04-接口契约与权限矩阵.md` §2，前缀 `/talent`（与平台其他模块一致） |
| §11 验收映射 | `docs/05-验收与测试用例.md` 8 组用例 |

## 5. 仍需你方确认的问题（不阻塞编码）

| # | 问题 | 当前默认处理 |
|---|---|---|
| 1 | POC 对象存储：MinIO 还是腾讯 COS | 已做存储抽象（`talent.oss-config-key`），**代码不改即可切换** |
| 2 | 本地账号登录名用工号还是邮箱前缀 | 与人才库无关，沿用平台账号体系，不额外处理 |
| 3 | Cloudflare 是否额外启用 Access | 属部署层，人才库不感知 |
| 4 | 解析服务供应商/数据地域/日志留存/个人信息处理审批 | **未确认前不处理真实简历**；`talent.parse-enabled=false` |
| 5 | 病毒扫描服务选型 | 状态机与回调接口已就绪，`talent.virus-scan-enabled=false` 时直接置 `CLEAN` 并留痕 |
| 6 | 是否需要"人才删除"（当前只提供归档） | 按 §5.1 与其他章节口径，**只做归档 + 逻辑删除**，不做物理删除 |
| 7 | `mybatis-encryptor` 的 AES 密钥由谁托管 | 已列为上线前必查项（验收清单 §9），密钥不入代码库 |
