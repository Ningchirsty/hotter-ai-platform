## 3. 与设计文档 / 实现规范的偏差清单

### 3.1 架构级（已在 `02-6.0.0框架API核对表.md` 说明证据）

| # | 偏差 | 原因 |
|---|---|---|
| 1 | 不使用框架 `@DataPermission`，改为服务端显式区域过滤 | `DataScopeType` 封闭枚举无法表达区域；且漏配角色时会静默返回 ` 1 = 0 ` |
| 2 | 人才附件**不登记** `sys_oss`，直写 `talent-private/` 自定义对象键 | 登记进 `sys_oss` 会形成绕过人才库授权的下载旁路（`system:oss:download`） |
| 3 | 不做物理隔离区搬移，改 `scan_status` 状态机 | `OssClient` 无 copy/move 接口 |
| 4 | 受控下载走服务端流式代理，**不下发**预签名 URL | 避免 URL 进入日志/Referer；`presign` 能力保留但不使用 |
| 5 | 自建 `tl_export_task` + `@Async` | 框架无异步导出实现、无导出任务表 |

### 3.2 编码期发现并修正的规范错误

| # | 规范写法 | 实际 | 处置 |
|---|---|---|---|
| 1 | `ExcelBuilder.sheet(...)` | 实际方法名是 **`sheetName(String)`** | 改为 `sheetName` |
| 2 | `@ExcelDictFormat` 单独使用 | 必须写在 `@ExcelProperty(converter = ExcelDictConvert.class)` 上 | 按基线 `SysDeptVo` 写法修正 |
| 3 | `@Translation` 简写 | **必须写 `mapper = "源字段"`**，否则翻译自身值 | 全部补 `mapper` |
| 4 | 实体统一 `@EqualsAndHashCode(callSuper = true)` | `TlSensitiveAudit` 不继承 `BaseEntity`，该写法 **直接编译报错** | 该实体用 `callSuper = false` |
| 5 | 模块 pom 声明 lombok / mapstruct-plus-processor | 基线在根 pom 的 `annotationProcessorPaths` 统一配置 | 模块 pom 不重复声明 |
| 6 | `TlTalentVo` 未列 `ageSourceDate` | 服务层需要它展示"识别年龄+识别日期"（设计 §5.2） | 已补字段 |
| 7 | 接口表漏了解析任务创建/字段查询入口 | `ITalentParseService` 有对应方法 | 已补 `POST /talent/parse`、`GET /talent/parse/fields/{taskId}` |

### 3.3 实现中主动加固（超出规范要求）

| # | 加固点 | 价值 |
|---|---|---|
| 1 | `checkTalentVisible` 额外落实 `share_scope`：`GRANT_ONLY` 除管理员外一律拒绝；`GROUP` 对任何有区域权限者可见 | 堵住跨区域越权读取 |
| 2 | 重复预检命中时**只回条数、不回他人姓名/区域** | 防止用预检接口探测越权数据；完整清单仍落 `tl_talent_duplicate` |
| 3 | 详情接口下发明文手机号时**同时补写 `VIEW_FULL_PHONE` 审计** | 防止绕过专用接口无痕查看 |
| 4 | **更新手机号也走重复预检** | 堵住"更新绕过新增预检"的通道 |
| 5 | 导出快照冻结 `regions` + `operatorId` | 异步线程无登录态，用创建时冻结的区域范围，避免执行时角色漂移导致范围扩大 |
| 6 | `TalentSecurityGuard` 启动自检 | 把"加密开关未开""哈希盐仍是默认值"等**静默不安全**变成启动日志里的显式告警 |
| 7 | `TalentAuditRecorder` 用 `REQUIRES_NEW` 且异常不外抛 | 审计不因业务回滚丢失，审计失败也不阻断业务 |
| 8 | 导出列**不含手机号** | 从数据源头规避"非 JSON 场景不一定走脱敏"的风险 |

## 4. 已知限制与残余风险

| # | 项 | 影响 | 建议 |
|---|---|---|---|
| 1 | 上传"先写 OSS、后写库"，DB 失败会留孤儿对象 | 存储残留（非数据泄露） | 二期加对账/清理任务；`OssClient` 无 copy/move，无法两阶段 |
| 2 | 删除附件只逻辑删除、保留对象 | 存储残留 | 保留期后由运维按策略清理；符合"原文件始终保留"的设计口径 |
| 3 | 异步导出线程内无登录态，该条 `EXPORT` 审计的 `operatorId` 为 null | 审计可追溯性下降 | 任务行有 `create_by` 可关联；后续可改为显式传入操作人 |
| 4 | `fullPhone` 接口要求 `talent:profile:phone` 菜单权限，因此"仅有单条授权 `VIEW_FULL_PHONE`"的账号无法调用该接口 | 单条授权路径未完全打通 | 需产品确认：是否允许"授权即可看完整号码"。当前口径是"菜单权限优先，单条授权为附加条件" |
| 5 | `tl_sensitive_audit` 无 `region_code`，区域 HR 只能按关联人才区域收窄 | `talent_id` 为空的导出类审计对区域 HR 不可见 | 如需要，可在审计表加区域快照列 |
| 6 | 病毒扫描未接入 | 本期无真实扫描能力 | `talent.virus-scan-enabled=false` 时置 `CLEAN` 并留痕；回调接口已就绪 |
| 7 | 解析能力默认关闭 | 简历解析不可用 | 需 §13.4 的个人信息处理审批 |
| 8 | SQL 未在真实 MySQL 执行 | 建表可能因环境差异失败 | 已在测试库执行一次并核对菜单渲染 |
| 9 | 前端未做端到端联调 | 页面交互未经真机验证 | 需部署后按 `05-验收与测试用例.md` 执行 |

## 5. 权限设计的一处待确认

`GET /talent/profile/fullPhone/{talentId}` 当前需要 `talent:profile:phone` 权限。若业务要求"用人部门查阅者经单条授权即可查看完整号码"，需要二选一：

- **方案 A（当前）**：菜单权限优先，单条授权为附加条件。查阅者始终看不到完整号码。
- **方案 B**：接口只校验登录，在 Service 内由 `TalentScopeHelper.canViewFullPhone()` 判定（已实现该方法，天然支持"菜单权限 **或** 单条授权"）。

`canViewFullPhone()` 的逻辑已经是"菜单权限 **或** 单条授权"，因此**只需把 Controller 上的 `@SaCheckPermission` 换成 `@SaCheckLogin`，方案 B 即刻生效**——无需改动 Service 层。请确认口径后我再调整。
