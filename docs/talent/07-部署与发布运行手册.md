# 07 部署与发布运行手册（集团人才库 → Ubuntu 生产环境）

> 目标环境：深圳生产（`ai-edge-sz`，Ubuntu 24.04.5 LTS，`192.168.2.134`）
> 对外地址：`https://pm.hottter.cn`（Cloudflare 接入，已实测可达）
> 本手册基于仓库内 `.github/workflows/deploy-*.yml`、`script/deploy/README.md`、
> `docs/ubuntu-ruoyi-comfyui-deepseek-handoff.md` 的实际约定编写。

---

## 一、部署架构（**不是**从开发机直接 SSH 部署）

```
本地/CI 构建 → GHCR 不可变镜像（按 digest 引用）
                        │
                        ▼
        GitHub Actions 手动触发 workflow_dispatch
                        │
                        ▼
   自托管 Runner（就在 Ubuntu 生产机上，标签 shenzhen, deploy）
                        │
                        ▼
        sudo /usr/local/sbin/hotter-release backend|frontend <IMAGE> [SHA]
                        │
                        ▼
        仅切换服务容器；不动数据卷、不导入 SQL、不做回滚数据
```

| 关键事实 | 说明 |
|---|---|
| 发布触发方式 | **只有** `workflow_dispatch` 手动触发，没有自动发布 |
| 镜像引用 | 必须是 `@sha256:` 不可变摘要，不接受 tag |
| 前端额外要求 | 必须传入完整 40 位 Git SHA（用于校验镜像内 `/version.json`） |
| 部署入口 | `/usr/local/sbin/hotter-release`（root 拥有、750，仅通过 sudoers 放行） |
| 运行编排 | 服务器私有 `/opt/ai-video-poc/compose.yaml` + `.env`（root:gh-deploy，**不在仓库里**） |
| 持久化卷 | `ai-video-poc-mysql-data`、`ai-video-poc-redis-data` —— **发布过程绝不重建或删除** |
| 主要容器 | `ai-video-poc-backend-1`、`ai-video-poc-mysql-1`、`ai-video-poc-redis-1`、`ruoyi-web` |

### ⚠️ 最大的坑：发布入口**不会执行 SQL**

`script/deploy/README.md` 明确写着：发布入口 *"never runs `docker compose down`,
deletes volumes, **imports SQL**, or restores data"*，并且
**schema 不兼容的发布必须走另行审批的前向修复流程**。

人才库**恰恰是 schema 变更**（新增 9 张 `tl_` 表 + 菜单/角色/字典）。
所以：**必须在切换后端镜像之前，由有权限的管理员手工执行迁移脚本**，
否则新后端一旦访问人才库功能就会报表不存在。

## 三、发布步骤

### 步骤 1：合并 PR

打开：https://github.com/Ningchirsty/hotter-ai-platform/compare/main...feature/talent-library?expand=1

点 **Create pull request** → 等 CI（Backend CI / Frontend CI）跑绿 → **Merge**。

> 仓库文档规定 `main` 禁止直接推送，请走 PR 合并。

### 步骤 2：取镜像摘要

合并后 `main` 的 push 会触发 CI 的 `publish-image` job，在 **workflow run 的 Summary**
里会打印类似：

```
### Published image

`ghcr.io/ningchirsty/hotter-ai-platform-backend:sha-<SHA>`
Digest: `ghcr.io/ningchirsty/hotter-ai-platform-backend@sha256:....`
```

把 **backend** 与 **frontend**（Frontend CI 同理）两个 digest 与那个 40 位 SHA 记下来。

### 步骤 3：执行数据库迁移（**不可跳过，且必须在步骤 5 之前**）

我在仓库中准备了**幂等**的生产迁移脚本：

```
script/sql/ry_talent_migration.sql
```

它相对初始化脚本做了两处安全化改造：

- 移除全部 `drop table if exists` → 改为 `create table if not exists`（**重跑不会清空数据**）
- 全部 `insert into` → `insert ignore into`（固定主键，重跑不会重复插入）

在服务器上由有权限的管理员执行（库名以生产 `.env` 实际配置为准）：

```bash
# 1) 确认后端实际连接的库（不要凭猜）
sudo docker exec ai-video-poc-backend-1 env | grep -i -E 'datasource|mysql|url' | sed 's/:[^:@]*@/:***@/g'
# 或从 compose/.env 中读取（需 root）
sudo grep -i -E 'MYSQL|DATASOURCE|DB_' /opt/ai-video-poc/.env | sed 's/=.*/=***/'

# 2) 把脚本送进容器并执行（示例：库名 ry-vue，请替换为实际值）
sudo docker cp script/sql/ry_talent_migration.sql ai-video-poc-mysql-1:/tmp/
sudo docker exec -i ai-video-poc-mysql-1 sh -c \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" <库名> < /tmp/ry_talent_migration.sql'

# 3) 校验：应看到 9 张 tl_ 表
sudo docker exec -i ai-video-poc-mysql-1 sh -c \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" <库名> -e "show tables like \"tl_%\";"'
```

**预期结果**：`tl_export_task / tl_parse_field / tl_parse_task / tl_sensitive_audit /
tl_talent / tl_talent_access_grant / tl_talent_attachment / tl_talent_contact /
tl_talent_duplicate` 共 9 张。

> 迁移对现有功能**无影响**：新表无人使用，新菜单只绑定到新建的 `talent_*` 角色，
> 而没有任何现有用户被授予这些角色，因此菜单不会出现在现有用户界面上。
> 顺序安全，可以先迁移后发布。

### 步骤 4：补齐生产配置（需 root/运维）

人才库有两个**默认值不安全**的配置，`TalentSecurityGuard` 会在启动时打印醒目告警：

| 配置项 | 生产要求 | 不配的后果 |
|---|---|---|
| `mybatis-encryptor.enable` | 必须 `true`，并配置 AES 密钥 | 手机号密文字段等同**明文存储** |
| `talent.phone-hash-salt` | 改为密钥管理提供的随机盐，**不得用默认值** | 手机号哈希可被跨库比对/彩虹表反推 |
| `talent.virus-scan-enabled` | 与真实扫描服务一致 | 语义与事实不符 |
| `talent.parse-enabled` | 获批前保持 `false` | 违反个人信息处理审批前提 |

写入 `/opt/ai-video-poc/.env`（或 compose 的 environment 段），例如：

```
MYBATIS_ENCRYPTOR_ENABLE=true
MYBATIS_ENCRYPTOR_PASSWORD=<由密钥管理提供的 AES 密钥>
TALENT_PHONE_HASH_SALT=<随机盐>
TALENT_VIRUS_SCAN_ENABLED=false
TALENT_PARSE_ENABLED=false
```

> Spring Boot 的 relaxed binding 会把 `MYBATIS_ENCRYPTOR_ENABLE` 映射到
> `mybatis-encryptor.enable`、`TALENT_PHONE_HASH_SALT` 映射到 `talent.phone-hash-salt`。
> 具体变量名以生产 `.env` 既有风格为准。

### 步骤 5：发布后端

GitHub → Actions → **Deploy Shenzhen Production Backend** → Run workflow：

- `image` 填步骤 2 拿到的 **backend digest**（必须 `@sha256:` 形式）

workflow 会校验摘要格式 → 在自托管 Runner 上执行
`sudo /usr/local/sbin/hotter-release backend <IMAGE>`。

### 步骤 6：发布前端

GitHub → Actions → **Deploy Shenzhen Production Frontend** → Run workflow：

- `image` 填 **frontend digest**
- `git_sha` 填步骤 2 记录的 **40 位 SHA**

> 前端镜像会自检 `/version.json` 中的 `gitSha` 与传入值一致，填错会失败。

### 步骤 7：验收

按 `docs/talent/05-验收与测试用例.md` 执行，**至少先跑这几条**：

| 编号 | 检查 | 期望 |
|---|---|---|
| — | 打开 `https://pm.hottter.cn` 登录 | 现有功能正常 |
| — | 用超管进入「系统管理 → 菜单管理」查看 | 存在一级目录「集团人才库」及 6 个子菜单 |
| — | 给测试账号授予 `talent_admin` 角色 | 左侧出现「集团人才库」一级目录 |
| A-01 | 分别用 SZ / ST HR 查看人才档案列表 | 只见本区域 + GROUP，越权记录不可见 |
| A-02 | SZ HR 请求 `regionCode=ST` | 不返回 ST 专属记录 |
| B-04 | 越权下载他人附件 | 被拒且写入审计 |
| G-01 | 查阅者查看手机号 | 显示脱敏值 |

同时确认启动日志中**没有**人才库安全告警（否则说明 §步骤 4 没配好）：

```bash
sudo docker logs ai-video-poc-backend-1 2>&1 | grep -F '[人才库安全告警]'
```

## 四、回滚

| 场景 | 做法 |
|---|---|
| 仅代码问题 | 用**上一个已验证的镜像 digest** 重新派发同一个 workflow（前端需同时给上一个 SHA）。数据库与对象数据保持不动 |
| Schema 已变更且需回退 | **不能**用应用回滚路径。`script/deploy/README.md` 要求走已审批的前向修复或数据恢复流程 |
| 想撤销人才库 | 应用回滚后，新表与新菜单可以保留（对现有功能无影响）；如需彻底清理，另行走审批的 SQL |

> 请**不要**在发布/回滚过程中 `docker compose down`、删除
> `ai-video-poc-mysql-data` / `ai-video-poc-redis-data` 卷，或直接改生产 compose。
