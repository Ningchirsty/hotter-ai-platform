## 四、M-003 / M-004：健康语义与声明字段的界面口径

  1. **界面/接口区分三态**：`HEALTHY` / `DEGRADED` / `DOWN` / **`UNKNOWN`/未测（不是 HEALTHY）**——具体落点：`AigModelGovernanceVo` 增加 `healthKnown`（或让前端按 `health_status` 为空/UNKNOWN 显示"未测"），**不改路由**；

  3. **告警**：`UNKNOWN`/`NULL` 超过 N 天未探测 → 提示。
- **验收**：界面文案不得把 UNKNOWN 显示为"健康"；`dryRun` 结果**与改动前一致**（证明只动展示）。
- **是否改生产**：① 是（前端/接口，需发版）；② 是（新增定时任务）。

### M-004：`provider_capability` 界面标注"仅声明、不参与路由"

## 五、M-005：策略决策落账（`aig_policy_decision_log`）—— 唯一必须新增表的项

### 为什么必须有

ADR-006 要求"外发管控在执行点强制且**可举证**"。现在 `decide()` 的结论只进内存 + `policyHits` 文本，
**调用被拒时除了日志没有可查询的结构化证据**，无法回答"上周三那次外发是谁批准的、命中了哪条策略"。

### 表设计（草案，按现有规范核对后落地）

```sql
-- 只增不改；字段类型按现有雪花 ID / 逻辑删除 / utf8mb4 规范核对
create table if not exists aig_policy_decision_log (
  decision_id     bigint(20)   not null                  comment '决策ID',
  capability_code varchar(64)  not null                  comment '能力编码',
  data_level      varchar(16)  not null                  comment '数据等级',
  decision        varchar(16)  not null                  comment 'MODEL/MANUAL/DENIED',
  model_id        bigint(20)   default null              comment '选中模型ID（DENIED/MANUAL 时为空）',
  deployment_type varchar(24)  default null              comment '部署类型',
  policy_id       bigint(20)   default null              comment '命中的路由策略ID',
  allow_external  char(1)      default null              comment '本次生效的 allow_external（含 STRICT 强制置 N 后的值）',
  approval_required char(1)    default 'N'               comment '策略是否要求审批',
  external_call   char(1)      default 'N'               comment '本次是否真的外发',
  reason_code     varchar(64)  default null              comment '细因（见 contract/error-codes.json 的 reasonCodes）',
  excluded_json   varchar(2000) default null             comment '被排除候选与原因摘要（来自 policyHits）',
  caller_id       bigint(20)   default null              comment '调用人（调度/系统发起为空）',
  agent_version_id bigint(20)  default null              comment '本次归属的 Agent 版本',
  task_id         bigint(20)   default null              comment '关联任务',
  trace_id        varchar(128) default null              comment '追踪ID',
  request_digest  char(64)     default null              comment '请求摘要（同幂等键不同摘要要能看出来）',
  operate_time    datetime     default null              comment '决策时间',
  primary key (decision_id),
  key idx_policy_decision_time (operate_time),
  key idx_policy_decision_cap (capability_code, data_level, operate_time),
  key idx_policy_decision_trace (trace_id)
) engine=innodb comment='AI 调用策略决策账本（可举证：为什么放行/为什么拒绝）';
```

### 写入点（关键：**不要在路由引擎里写**）

`AigRouteServiceImpl.decide()` 是**纯判定**（无调用人、无 DB 写），保持它纯净。
写入点应在 **`AigInvokeServiceImpl`**：拿到 `decide()` 结果之后、真正发起调用之前，一次落一行
（`decision`/`modelId`/`policyId`/`allowExternal`/`approvalRequired`/`excluded_json` 全部现成可得；
`callerId`/`taskId`/`agentVersionId`/`traceId` 从调用上下文取）。

### 验收判据

1. 一次**被拒**的外发调用（T-005 式：STRICT 资料发外部服务）→ `aig_policy_decision_log` 有且仅有一行，
   `decision=DENIED`、`reason_code=EXTERNAL_DISALLOWED`、`external_call=N`，且**审计表无外呼记录**（真没发出去）；
2. 一次成功调用 → 一行 `decision=MODEL`、`model_id` 与审计里的 `model_key` **对得上**（防"配 A 跑 B"）；
3. `dryRun` **不写**该表（dryRun 是预检，不是决策执行）——需明确这条口径并测。

### 回滚

`drop table`（新表、无历史依赖）；代码侧加开关（默认写、可关），关掉即回到今天的行为。

### 是否改生产

✅ **是**（新增表 + 代码 + 发版）。

## 六、M-006：`agent_version_id` 的传递与告警

### 现状

- 任务驱动链路**已经**带上：`AigTaskExecutorImpl` 把 `task.getAgentVersionId()` 放进 `AigInvokeBo`；
- 直接调能力（不经任务）**本来就没有版本归属**——这是**正确的**（不能乱记到某个版本头上，否则灰度达标就是假账）。

### 改法（只做"发现异常"，不改归属规则）

1. **一致性巡检**（只读 SQL，可先做成运维脚本/定时任务，不必改代码）：
   找出"**任务上有 `agent_version_id`，但对应审计行的 `agent_version_id` 为空**"的记录——
   这类才是**接线 bug**（该带没带），与"本来就不该带"要分开。

   **关联字段已确认**（生产实测）：`aig_invocation_audit` **只有 `trace_id`，没有 `task_id`**；
   `aig_task` 同时有 `task_id` 与 `trace_id`。所以按 `trace_id` 关联：

   ```sql
   select t.task_id, t.agent_version_id as task_av,
          a.audit_id, a.agent_version_id as audit_av, a.capability_code
     from aig_task t
     join aig_invocation_audit a on a.trace_id = t.trace_id
    where t.agent_version_id is not null
      and a.agent_version_id is null
    order by t.task_id desc
    limit 50;
   ```

   配套的反向核对（"审计有版本归属但任务没有"——不该出现）：
   ```sql
   select count(*) from aig_task t
     join aig_invocation_audit a on a.trace_id = t.trace_id
    where t.agent_version_id is null and a.agent_version_id is not null;
   ```

2. **告警**：上述巡检结果 > 0 即告警（对应设计文档 §21.2 的"审计中 `agentVersionId` 缺失"）。
3. **一致性基线**：本单未在生产跑该 SQL（属只读，可随时跑）；**建议第一次跑就把结果留档**，
   作为"接线是否完好"的基线。
4. **验收**：T-013 的反面——不经任务的直接调用**不应**被计入任何版本灰度；
   任务驱动的调用**必须**逐笔对得上（`task_av` 与 `audit_av` 相等）。

### 首轮实测（2026-10-08，只读，未改任何数据）

| 项 | 实测 |
|---|---|
| `aig_task` 行数 | **0** |
| `aig_task` 中 `agent_version_id` 非空 | 0 |
| `aig_invocation_audit` 行数 | 277 |
| 审计中 `agent_version_id` 非空 | **0** |
| 建立关联的任务/审计对数 | **0** |
| 主巡检（接线 bug） | 0 |
| 反向核对（不该出现） | 0 |

> ⚠️ **这里的 0 不能读成"接线完好"**。`joined_pairs = 0` 说明**巡检零覆盖面**：
> 生产上没有任何任务，也没有任何审计行带 Agent 版本归属——所以这次巡检
> **什么也没证明**。**"0 bug" 与 "没有可查的数据" 是两件事**（这正是本单 §六-1
> 把该查询叫"发现异常"而不是"确认健康"的原因）。
>
> **顺带得出一个对整条发布链更要紧的事实**：既然 277 条审计里**没有一条**带
> `agent_version_id`，那么 `CANARY` 门槛（灰度证据按"归属该 Agent 版本的调用"统计）
> 在**当前生产上永远无法满足**——不是"数据少"，而是**根本没有归属数据**。
> 这与基线 §3.1 的"任务表为空"是同一个根因：**版本归属这条链路在生产上从未被跑过**。
> 建议把它作为阶段 1 的前置验证项：**先让一条真实任务带着 `agent_version_id` 走完**，
> 再谈灰度。

### 验收前提（修正）

原判据"主巡检 = 0 即完好"**不成立**。正确判据是：
**`joined_pairs > 0` 且 主巡检 = 0 且 反向核对 = 0**。
如果 `joined_pairs = 0`，巡检结论应为"**无覆盖面，未能验证**"，而不是"通过"。

### 是否改生产

- 巡检 SQL：**只读，不需要授权**；
- 定时任务/告警：是（新增任务）。
