## F-05 冻结结论（2026-10-08 由运维确认）

**背景**：本节此前列为阻塞项，原因是"品牌/项目主数据在哪张表"未定。经生产实测，
地图已画出，因此收敛为三句**可执行**结论（不再需要新开会）。

### 实测依据

| 事实 | 证据 |
|---|---|
| 组织树**只有两层可用**：集团 → 子公司 / 中心 → 部门 | `sys_dept` 21 行：纵享集团(`…100`) → 合火人智能科技(`…101`)、星堡电子科技(`…102`)、汕头澄海成乐玩具、广东星堡精密科技、东莞模房、人力资源中心、经营管理中心 |
| **全库没有品牌主表** | `information_schema` 中品牌相关只有 `dp_brand_brief` 与其备份表 |
| `dp_brand_brief` **不是品牌档案** | 其主键关联是 `task_id`（`cp_task.task_id`），注释「视觉项目，一个项目一行」——是**任务级的品牌要求** |
| 治理表**已预留**组织维度但全空 | `aig_agent_binding.company_id` / `brand_id` 两列存在，表 **0 行**、两列 **0 非空**；`aig_task` 无 `org_scope` 类列 |
| `sys_role_dept` 存在但 **0 行** | 数据权限尚未启用 |

### 三句冻结结论

| # | 结论 | 理由 |
|---|---|---|
| **Q1** | **BRAND 层 = 新增业务主表**（如 `biz_brand`），由业务域维护；治理层只存 `brand_id`（**无外键**，与 `aig_agent_binding` 现状一致） | 品牌是**业务概念**，一个品牌可能跨多个法人（`sys_dept` 下已有 4 家玩具相关公司）；塞进 `sys_dept` 会与 HR/财务的组织口径打架 |
| **Q2** | **PROJECT 层暂不引入**——当前只有"任务"粒度（`cp_task.task_id`） | `aig_task.project_id` 指向的是内容任务，**不是项目**；等真出现跨任务的项目概念再补 |
| **Q3** | **GROUP / SUBSIDIARY = `sys_dept` 前两级**，复用不新建；授权**先用** RuoYi 既有数据权限（`sys_role_dept`）+ 治理层显式 `org_scope` 兜底，**不新造第三套** | `sys_dept` 结构已可用；`sys_role_dept` 已存在（0 行，启用即可） |

**为什么现在冻它零成本**：`aig_agent_binding.company_id/brand_id` **列已存在**且无任何数据，
**不需要任何迁移**即可直接使用。

### 遗留：1 项待业务确认（不影响开工）

`sys_dept` 里 4 家玩具相关公司——**合火人智能科技有限公司**、**星堡电子科技有限公司**、
**汕头市澄海区成乐玩具有限公司**、**广东星堡精密科技有限公司**——**是否都算"子公司"层**？
本结论只从 `sys_dept` 结构推断（它们都直挂集团下），**业务口径需人确认**。
若其中某家实为"部门"或"品牌"，只需调整映射，**不改变 Q1~Q3 的结论**。

### 一、实测数据（生产库）

| 表 | 行数 |
|---|---|

### 二、结论一：今天**不存在**"覆盖/冲突"，因为业务侧根本不读绑定表

全仓逐个看过 `AigAgentBinding*` 的引用（含 `*.xml` mapper：**0 处**），绑定表只有**两个**读取方：

| 读取方 | 位置 | 作用 |
|---|---|---|
| **发布门槛** | `AigAgentRegistryServiceImpl.assertBindingExistsIfLimitedChannel()` | 受限通道（`TESTING`/`BRAND`/`DEPT`）的 **Agent 版本**发布到 `CANDIDATE`/`STABLE` 时，必须有 `enabled='Y'` 的绑定行，否则**抛异常拒绝发布** |
| 治理台列表 | `AigAgentRegistryQueryServiceImpl.queryBindingPage()` | 分页展示（`GET /aigov/agent/binding/list`） |

**没有任何运行时消费方**（invoke / 路由 / 业务列表）按绑定过滤可见范围。
所以绑定目前只是**发布许可证**，不是**运行时可见性**：F-06 问的"覆盖/冲突"是**尚未发生**的
——不是因为两边一致，而是因为业务侧还没读它。

> 顺带说明：`AigReleaseChannelEnum` 与 `AigAgentBinding` 的 javadoc 里写的
> "这个版本在业务侧根本不可见"目前**无法被验证**——它描述的是**将来要实现**的语义。
> （门槛那条规则本身是**真的落在代码里**的，不是只写在注释里；这一点已单独核实。）

### 三、结论二：三个必须先定的缺口（这才是 Owner 要回答的）

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **绑定只能新增，不能撤销/禁用** | API 只有 `POST /aigov/agent/binding` + `GET /aigov/agent/binding/list`，**没有 update / delete / disable**；`frontend/src/api/aigov/binding/index.ts` 同样只有 `addBinding` / `listBinding`，页面也没有编辑/删除按钮。⇒ 误加的绑定只能直接改库才能去掉；而门槛看的是 `enabled='Y'`，这个值**产品里没有任何入口能改**（对照组：路由的场景绑定 `aig:route:binding` **有**编辑与删除，所以这是遗漏而非既定策略） |
| 2 | **门槛忽略 `effective_from` / `effective_to`（也忽略 `del_flag`）** | 门槛只查 `agent_version_id = ? and enabled = 'Y'`。⇒ 一条**已过期**的绑定照样放行发布。若将来运行时按有效期判断可见性，就会出现"门槛说能发布、运行时说看不见"——正是 F-06 要防的那类不一致 |
| 3 | **"空维度 = 不参与收窄"的语义目前无处可验** | `AigAgentBindingBo` 注释要求"为空表示该维度不参与收窄……必须与服务层的收窄逻辑一致，否则会出现『因为没填所以全都不可见』"，但服务层**没有**这段收窄逻辑（没有消费方）。⇒ 这条约定今天既未实现也未测试，写第一个消费方时最可能在这里出错（一行全空 = 对所有人可见，还是谁都不可见？） |

### 四、收窄后的问题（Owner 只需回答三条）

1. 谁来**撤销/禁用**一条错误绑定？（需要 disable/delete 入口 + 权限，现在没有）
2. 绑定的**有效期**要不要真的生效？
   （生效 ⇒ 门槛必须一起校验 `effective_from/to`；不生效 ⇒ 删掉这两列，别留着骗人）
3. **运行时可见性**由谁实现、何时实现？
   （不实现 ⇒ `release_channel` 只影响发布门槛，不影响任何人实际看到什么）

## F-11 盘点结果（2026-10-08，只读实测）

**原待办**：「前端动态页面组件选型与 PSD/SVG 预览能力边界。决定 Scenario 的 `presentations`
能做到什么程度。」
**可以确定的是"现有能力边界"**（下面全部是实测）；**"`presentations` 该做到什么程度"仍需 Owner 定**，
因为定义它的设计文档（§22.2 那份）**不在本仓**——本仓只有在 `03` 这一处提到过 `presentations`。

### 一、现状：能预览什么（逐项实测，不是猜）

| 能力 | 现状 | 证据 |
|---|---|---|
| 位图（png/jpg/webp/gif） | ✅ 放大/旋转/切换 | `frontend/src/components/ImagePreview/index.vue`（`el-image` + `preview-src-list`），`views/system/oss` 在用 |
| 视频 | ✅（**必须带鉴权取 blob**） | `views/video/index.vue:510` 明确写着"`<video src>` 不会携带 Authorization 头"，所以先取回 blob URL |
| 图表 / 代码 / JSON | ✅ | 依赖里的 `echarts` / `highlight.js` / `vue-json-pretty` |
| 富文本 / 图片裁剪 / 前端压缩 | ✅ | `@wangeditor-next` / `vue-cropper` / `image-conversion` |
| **PDF / Office（doc/xlsx/pptx）** | ❌ 只能当附件上传 | 依赖里**没有** pdf.js、没有 docx/xlsx 渲染器；`FileUpload` 的 `fileType` 只是**接受类型**，不是预览 |
| **PSD** | ❌ 完全没有 | 依赖里没有任何 PSD 解析器；后端镜像内也没有任何栅格化工具（实测 `convert`/`magick`/`gm`/`rsvg-convert`/`inkscape`/`python3` **全部不存在**，只有 `app.jar`） |
| **SVG** | ⚠️ 仅"当图片看" | `vite-plugin-svg-icons-ng` 是**构建期图标雪碧图**工具（devDependency），**不能**用来预览用户上传的 SVG；且依赖里**没有消毒库**（无 DOMPurify） |
| **服务端渲染（HTML→图）** | ✅ **已存在**，但不在后端里 | 宿主机上跑着 `creative-renderer`（Node + **Chromium 131** + Noto Sans CJK SC），与后端同处 `ai-video-poc-backend` 网络：`GET /health` → `{"status":"ok","browser":true,"version":"1.1.0"}`；`GET /templates` → 按模板编码渲染（如 `HERO-H02`，含 checksum/bytes），`defaultWidth=750`、`widthRange=[200,4000]` |

### 二、能力边界（结论）

1. **SVG**：零新增依赖可做的上限是 `<img src="...">`——浏览器原生渲染，且这种方式**不执行** SVG 内的脚本。
   若要内联 `<svg>` / `<object>` / 可交互图层，必须先有消毒（SVG 可携带脚本），而当前**没有消毒库**，
   因此**不建议**在 `presentations` 里承诺"SVG 可交互预览"。
2. **PSD**：客户端与服务端**目前都做不到**——但要说清"服务端"指谁：
   **后端镜像**里没有任何栅格化工具；而宿主机上**已有一个带 Chromium 的渲染服务**
   `creative-renderer`（见上表最后一行），它能渲染 HTML/SVG，**但 Chromium 读不了 PSD**。
   三条路各有代价：
   (a) 前端加解析器（如 `ag-psd`）——拿到合成图，但图层效果/字体/智能对象只能是近似；
   (b) 给渲染链路加 PSD 转换（给 `creative-renderer` 装 ImageMagick/`psd-tools`，或后端镜像加）；
   (c) **要求设计侧随 PSD 一起交一张 PNG/WebP 预览图**——最省、最忠实。
   **建议 (c)**：把"能预览 PSD"这个期望从 `presentations` 里去掉。
3. **HTML/SVG 动态渲染**：**不要**去给后端镜像加渲染依赖——`creative-renderer` 已在同一 docker 网络里
   提供 Chromium 渲染（带 CJK 字体、模板有 checksum）。但它**不在本仓的发布流程里**
   （镜像 `local/creative-renderer:r52`，无 registry，已运行 7 天），
   所以一旦依赖它，就必须同时记录：**它的升级/回滚由谁负责、`health-check.sh` 是否要加它的健康检查**。
   这属于新增的跨系统耦合，不该在 `presentations` 里悄悄引入。
3. **PDF/Office**：同上，要么加库/加服务端转换，要么不承诺。当前**没有任何**实现。

### 三、收窄后的问题（Owner 只需回答）

1. `presentations` 允许的组件白名单是什么？（建议：位图 / SVG 当图片 / 视频 / iframe 嵌入 /
   图表 / 代码 / JSON——即上表 ✅ 的那些，**不含** PSD、PDF、Office）
2. PSD/PDF 的"预览"要不要做？若要做，选 (a)/(b)/(c) 哪条（建议 (c)，即不做预览、要求交预览图）？
