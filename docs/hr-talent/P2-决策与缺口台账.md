# P2 决策记录与 DDL 缺口台账

> 生成背景：P2（招聘主线）开发期间，对 P1 的 36 张表做了 **§8.x 功能字段全量对照审计**。
> 结论：P1 的 DDL 是按设计文档 **§9.2「核心字段」列**生成的，而那一列是**核心字段摘要、不是全集**；
> 各功能页的完整字段清单在 **§8.x**。因此存在一批系统性缺列，本文件记录处理结论。
>
> 契约文件：`SPEC-P1-地基.md`、`SPEC-P2-招聘主线.md`

## 1. 定案的口径修订（相对 P1）

| 项 | P1 原写法 | 修订后 | 依据 / 原因 |
|---|---|---|---|
| 分页返回 | `PageQuery` + `TableDataInfo<T>` | **`PageQuery` + `PageResult` + `R<PageResult<T>>`** | 本基线 **v6.0.0 不存在 `TableDataInfo`**（全仓仅 1 处误引用）；`ruoyi-ai-gov` 全用 `PageResult` |
| VO 标签 | 未要求 | **必须用 `@Translation`** 回填字典标签与人员昵称 | 全仓惯例（`ai-gov` 所有 VO 都带 `xxxLabel`）；已给模块 pom 加 `ruoyi-common-translation` |
| 主键列名 | `@TableId(value = "id")`（SPEC-P2 初稿笔误） | **表级主键名**：`demand_id`/`change_id`/`plan_id`/`item_id`/`rollover_id`/`rel_id`/`job_id` | `hr_recruit.sql` 实际 DDL |
| 需求 `submitted → recruiting` | 未定义入口 | **新增显式 `confirm` 动作**（权限复用 `PERM_DEMAND_SUBMIT`，写 `confirmed_by/confirmed_time`） | 设计文档 §20「一期先采用**提交确认**」；不复用"再次 submit"这种含糊语义 |
| 需求暂停/关闭原因 | — | **记在 `hr_recruit_demand_change.reason`**，需求表不设原因列 | 已有变更历史表可承载，避免冗余列 |
| 来源类型大小写 | §9.4 写 `NEW`/`CARRYOVER` | **以小写 `new`/`carryover` 为准** | §10 与 DDL 均小写；§9.4 属文档内部口径不一致 |
| 表数量 | 36 张 | **36 张 + 4 张待增**（见 §4） | §9.2 是"建议包含"的表清单，§8.x 要求更多 |

## 4. 结构性缺口（需新增表，**本次不实施**）

审计发现 4 处 §8.x 要求但 §9.2 无对应表的设计，**留待各自所属阶段决策**：

| # | 建议表 | 依据 | 归属阶段 |
|---|---|---|---|
| 1 | 计划任务状态刷新日志（触发事件/原状态/新状态/刷新时间） | §7.1.5、§21.15「append status change log」 | P3（状态自动刷新的触发事件来自候选人流程） |
| 2 | **月度结转批次表**（批次状态、成功/失败计数、批次级重试审计） | SPEC §4.3.7「先建批次再逐条执行」、§9.6；`hr_recruit_plan_rollover` 的 DDL 注释自认「无批次表」 | **P2 已用变通方案上线，补表属后续增强** |
| 3 | 人才分组（公共分组 / 个人收藏） | §8.15、§5.1 菜单「人才池与分组」 | P3 |
| 4 | 人才导出任务（筛选条件/字段清单/导出人/用途/记录数/结果文件/过期时间） | §8.20、§11、§21.10、§15.2 | P4 |
| 5 | 导入预览暂存 | §8.11、§13.2、§13.1「确认前不得将数据写入正式业务表」 | P4 |

> 第 2 项由 B 组在实现中独立发现（审计报告未识别）。**P2 的变通方案**：批次表达为明细行上的
> `batch_id`（雪花）+ `batch_no`，`GET /recruit/plan-rollovers` 按明细分页、行内带 `batchNo` 供前端分组，
> `GET /{batchNo}` 返回该批明细，`/{batchNo}/retry` 按批次重试失败行。
> **能力边界**：无独立的批次级状态字段与批次级审计记录。补表需服务层改造，不在 P2 范围。

**注意**：现有 36 张表**不覆盖**上述 4 项。开工到相应阶段时必须先补表，否则该阶段功能无法落地。

## 5. 审计判定"不算缺口"的项（备查，避免重复提出）

- **派生/计算**：待招聘人数 `= max(需求人数 - 实际到岗, 0)`；当月计划人数/到岗汇总/结转人数 = `plan_item` 三列聚合；
  是否报到 = `arrival_date` 非空；渠道推荐/到面/通过/到岗 = 按 `application.source_channel_id` 统计；超期需求与招聘周期 = 派生。
- **已由其他表/列承载**：需求暂停/关闭原因 → `demand_change.reason`；需求计划月份/当月计划人数 → `plan_item`；
  专业与毕业院校 → `talent_education`；归属公司 → `owner_dept_id`；解析器版本 → `parse_task.parser_version`。
- **依据不足、未计入**：`job.post_id`（§20 为"可选关联"）、导入撤销字段、`plan_application_rel` 待人工分配标记、
  面试改期历史（倾向多条记录）、profile 保留到期/冻结/匿名化（§15.4 措辞为"预留"）、资料完整度（可计算）。

## 6. P2 落地时采纳的实现决定（已评审，勿在后续阶段误改）

| # | 决定 | 理由 |
|---|---|---|
| 1 | `POST /recruit/plans` 命中同公司同月表头时**报错**，不静默复用 | 静默返回他人表头会误导前端；结转内部另走 `ensureTargetPlan` 静默复用 |
| 2 | 结转自动创建的下月表头 `status=executing`；本批有成功结转后 `generated_flag=1` | 结转产物是执行中的任务，不是草稿 |
| 3 | **结转不复制 `job_id` / `demand_id`**，只复制岗位名称等执行信息快照 | `hr_recruit_job.plan_item_id` 是 N:1，复制 `job_id` 会造成跨月共享的岗位记录，与"每条计划任务独立跟进"冲突；岗位执行项由岗位域按需新建 |
| 4 | `completion_status` **不因暂停/取消冻结**，始终按人数计算；"已取消/暂停"只体现在主展示状态优先级 | 与 §4.2「按人数自动计算」一致；§21.15 伪代码在 CANCELLED/PAUSED 分支不改 completion，属表述差异，已在 JavaDoc 写明 |
| 5 | 结转 `result` 增加 `processing` 编码作为幂等占位闸门 | DDL 注释为"success/failed/skipped**等**稳定编码"，在其范围内；顺序为「占位插 processing → 建目标任务 → 回填 success + 原任务置 rolled_over」 |
| 6 | `GET /recruit/plan-items/similar` 返回 `PageResult<RecruitPlanItemVo>` | 只做"存在相似计划"提示，不参与合并（§7.1.1 禁止自动合并） |
| 7 | P2 中 `execution_status` 保持 `pending`；`refresh-status` 只重算 `remaining_qty`/`completion_status`/`last_refresh_time`，**绝不覆盖 `control_status`** | 应聘记录属 P3，尚无驱动源；"人工暂停不得被自动刷新覆盖"是 §7.1.5 硬约束 |
| 8 | 岗位域新增 `converter/AssistantIdsConverter`（`String ↔ Long[]`，`@Component`，经 `@AutoMapper(uses=...)` 接入） | 前端契约要 `Long[]`、DDL 列是 varchar 逗号串，MapStruct 同名不同类型会编译失败；注册 Bean 是 mapstruct-plus 生成的代码按 Bean 名取 `uses` 实例所必需 |
| 9 | 岗位 `assistantIds` **收发对称**：VO 与 BO 均为 `Long[]` | 避免"提交数组 / 读回字符串"的不对称；翻译另走只读 `getAssistantIdText()`（`@JsonIgnore`） |
| 10 | 岗位 `statusLabel` 不用 `@Translation`，改由 `JobStatusEnum` 只读 getter 兜底 | §10 无岗位状态字典组，不凭空造字典组 |
| 11 | 岗位域统一用 `ServiceException` + 中文提示，未用 `HrTalentErrorCode` | 该文件当时被并行 agent 修改，避免写冲突；SPEC §4.1 允许 |
| 12 | 结转每条来源任务在**独立 `REQUIRES_NEW` 事务**中执行，失败另起事务记 `failed + failure_reason + retry_count` | §9.6「单条失败应记录原因并允许安全重试」，不得回滚已成功条目 |

> **口径提醒**：`@Translation` 的 `USER_ID_TO_NICKNAME` / `USER_ID_TO_NAME` 实现**只支持单个 ID 或逗号分隔字符串**。
> 若把多值字段声明成数组，翻译会静默失败——多值场景必须另提供一个拼成逗号串的只读 getter 作为 `mapper` 源
> （岗位域的 `getAssistantIdText()` 即此模式）。
