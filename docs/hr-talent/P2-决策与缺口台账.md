## 1. 定案的口径修订（相对 P1）

| 项 | P1 原写法 | 修订后 | 依据 / 原因 |
|---|---|---|---|
| 分页返回 | `PageQuery` + `TableDataInfo<T>` | **`PageQuery` + `PageResult` + `R<PageResult<T>>`** | 本基线 **v6.0.0 不存在 `TableDataInfo`**（全仓仅 1 处误引用）；`ruoyi-ai-gov` 全用 `PageResult` |
| VO 标签 | 未要求 | **必须用 `@Translation`** 回填字典标签与人员昵称 | 全仓惯例（`ai-gov` 所有 VO 都带 `xxxLabel`）；已给模块 pom 加 `ruoyi-common-translation` |
| 主键列名 | `@TableId(value = "id")`（SPEC-P2 初稿笔误） | **表级主键名**：`demand_id`/`change_id`/`plan_id`/`item_id`/`rollover_id`/`rel_id`/`job_id` | `hr_recruit.sql` 实际 DDL |
| 需求 `submitted → recruiting` | 未定义入口 | **新增显式 `confirm` 动作**（权限复用 `PERM_DEMAND_SUBMIT`，写 `confirmed_by/confirmed_time`） | 设计文档 §20「一期先采用**提交确认**」；不复用"再次 submit"这种含糊语义 |
| 需求暂停/关闭原因 | — | **记在 `hr_recruit_demand_change.reason`**，需求表不设原因列 | 已有变更历史表可承载，避免冗余列 |
| 来源类型大小写 | §9.4 写 `NEW`/`CARRYOVER` | **以小写 `new`/`carryover` 为准** | §10 与 DDL 均小写；§9.4 属文档内部口径不一致 |
| 表数量 | 36 张 | **37 张 + 4 张待增**（见 §4；P3 经用户裁定补入 `hr_recruit_plan_item_status_log`） | §9.2 是"建议包含"的表清单，§8.x 要求更多 |

## 5. 审计判定"不算缺口"的项（备查，避免重复提出）

- **派生/计算**：待招聘人数 `= max(需求人数 - 实际到岗, 0)`；当月计划人数/到岗汇总/结转人数 = `plan_item` 三列聚合；
  是否报到 = `arrival_date` 非空；渠道推荐/到面/通过/到岗 = 按 `application.source_channel_id` 统计；超期需求与招聘周期 = 派生。
- **已由其他表/列承载**：需求暂停/关闭原因 → `demand_change.reason`；需求计划月份/当月计划人数 → `plan_item`；
  专业与毕业院校 → `talent_education`；归属公司 → `owner_dept_id`；解析器版本 → `parse_task.parser_version`。
- **依据不足、未计入**：`job.post_id`（§20 为"可选关联"）、导入撤销字段、`plan_application_rel` 待人工分配标记、
  面试改期历史（倾向多条记录）、profile 保留到期/冻结/匿名化（§15.4 措辞为"预留"）、资料完整度（可计算）。

## 6. P2 落地时采纳的实现决定（已评审，勿在后续阶段误改）

| # | 决定 | 理由 |
|---|---|---|
| 1 | `POST /recruit/plans` 命中同公司同月表头时**报错**，不静默复用 | 静默返回他人表头会误导前端；结转内部另走 `ensureTargetPlan` 静默复用 |
| 2 | 结转自动创建的下月表头 `status=executing`；本批有成功结转后 `generated_flag=1` | 结转产物是执行中的任务，不是草稿 |
| 3 | **结转不复制 `job_id` / `demand_id`**，只复制岗位名称等执行信息快照 | `hr_recruit_job.plan_item_id` 是 N:1，复制 `job_id` 会造成跨月共享的岗位记录，与"每条计划任务独立跟进"冲突；岗位执行项由岗位域按需新建 |
| 4 | `completion_status` **不因暂停/取消冻结**，始终按人数计算；"已取消/暂停"只体现在主展示状态优先级 | 与 §4.2「按人数自动计算」一致；§21.15 伪代码在 CANCELLED/PAUSED 分支不改 completion，属表述差异，已在 JavaDoc 写明 |
| 5 | 结转 `result` 增加 `processing` 编码作为幂等占位闸门 | DDL 注释为"success/failed/skipped**等**稳定编码"，在其范围内；顺序为「占位插 processing → 建目标任务 → 回填 success + 原任务置 rolled_over」 |
| 6 | `GET /recruit/plan-items/similar` 返回 `PageResult<RecruitPlanItemVo>` | 只做"存在相似计划"提示，不参与合并（§7.1.1 禁止自动合并） |
| 7 | P2 中 `execution_status` 保持 `pending`；`refresh-status` 只重算 `remaining_qty`/`completion_status`/`last_refresh_time`，**绝不覆盖 `control_status`** | 应聘记录属 P3，尚无驱动源；"人工暂停不得被自动刷新覆盖"是 §7.1.5 硬约束 |
| 8 | 岗位域新增 `converter/AssistantIdsConverter`（`String ↔ Long[]`，`@Component`，经 `@AutoMapper(uses=...)` 接入） | 前端契约要 `Long[]`、DDL 列是 varchar 逗号串，MapStruct 同名不同类型会编译失败；注册 Bean 是 mapstruct-plus 生成的代码按 Bean 名取 `uses` 实例所必需 |
| 9 | 岗位 `assistantIds` **收发对称**：VO 与 BO 均为 `Long[]` | 避免"提交数组 / 读回字符串"的不对称；翻译另走只读 `getAssistantIdText()`（`@JsonIgnore`） |
| 10 | 岗位 `statusLabel` 不用 `@Translation`，改由 `JobStatusEnum` 只读 getter 兜底 | §10 无岗位状态字典组，不凭空造字典组 |
| 11 | 岗位域统一用 `ServiceException` + 中文提示，未用 `HrTalentErrorCode` | 该文件当时被并行 agent 修改，避免写冲突；SPEC §4.1 允许 |
| 12 | 结转每条来源任务在**独立 `REQUIRES_NEW` 事务**中执行，失败另起事务记 `failed + failure_reason + retry_count` | §9.6「单条失败应记录原因并允许安全重试」，不得回滚已成功条目 |

> **口径提醒**：`@Translation` 的 `USER_ID_TO_NICKNAME` / `USER_ID_TO_NAME` 实现**只支持单个 ID 或逗号分隔字符串**。
> 若把多值字段声明成数组，翻译会静默失败——多值场景必须另提供一个拼成逗号串的只读 getter 作为 `mapper` 源
> （岗位域的 `getAssistantIdText()` 即此模式）。

## 7. P3 落地时采纳的实现决定与"不算缺口"裁定

### 7.1 实现决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | 淘汰/候选人放弃/暂缓/人才保留**只改 `current_status`，不改 `current_stage`**；`stage_log.to_stage` 记等于 `from_stage` | 字典 `recruit_candidate_stage` 只有 9 个阶段值，没有这 4 个结果值；强行落码会与字典和前端不一致 |
| 2 | `POST /recruit/applications/{id}/transition` **不允许**直接进入 `arrived`，走 `/arrival` | 报到必须在同一事务内累加计划任务到岗人数并刷新状态（§21.7），独立 transition 会破坏原子性 |
| 3 | 报到放行条件 = 处于 `pending_arrival` **或** 已记录「邀约结果 + 计划报到日期」 | 等价满足 §7.2 第 5 条的资料要求，避免强制三步走 |
| 4 | `POST /{id}/transfer` 追加一条 `action_type=transfer` 的 `stage_log`（阶段未变） | 追溯"谁在何时把候选人转给了谁"；不违背 §8.5 的"只追加" |
| 5 | `/no-arrival` 的应聘结果码取 `withdrawn` | 字典 `recruit_application_result` 无「未报到」专用码，权宜口径；精确表达需补字典码 |
| 6 | 阶段历史**不提供删除接口** | §8.5 明确只追加，不允许业务人员物理删除 |
| 7 | `/recruit/applications` 与 `/recruit/candidates` 列表**都要套 `TalentScopeDomainService`** | §11.1「人才查询接口统一调用人才范围服务」，候选人列表会暴露人才档案信息 |
| 8 | 审计记录器（`support/SensitiveAuditRecorder`）**永不抛异常**，失败只记日志 | 审计失败不得让业务操作失败或回滚 |
| 9 | 领域事件在 `TransactionSynchronization#afterCommit` 发布（无事务时立即发） | §21.6「涉及一致性的监听器使用事务提交后机制」；且事件只承载派生刷新 |
| 10 | 报到路径**同步**调用 `IPlanItemStatusService.refreshItemStatus()`，而非仅靠事件 | §21.7 要求「报到 + 计划到岗计数 + 状态刷新」同事务；§11.1 禁止各服务自行拼接状态值 |

### 7.4 P1 遗留缺陷：`TalentScopeDomainService.visibleTalentWrapper()` 生成的 SQL 不可用（P3 修复）

**发现者**：P3 应聘域（在尝试给自己的列表套可见范围时，把领域服务拿到真实 MyBatis-Plus 上跑了一遍）。

**缺陷（我在 P1 写的 `visibleTalentWrapper(ScopeCondition)`，三处，任一处都足以致命）**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 用**多次 `wrapper.apply(...)`** 拼接可见性 OR 分支（`"(p.visibility_type='{0}'"` + `"OR (...)"` + `")"`） | MyBatis-Plus 会把相邻 `apply` 片段用 **AND** 连接 → 生成 `AND OR (...)`，并留下悬空 `AND )`，**SQL 语法报错** |
| 2 | `getCustomSqlSegment()` **自带 `WHERE`** | 调用方把它当片段二次拼接（如 `wrapper.apply(scope.getCustomSqlSegment())`）→ `... AND WHERE (...)`，语法报错 |
| 3 | 片段内参数是 `#{ew.paramNameValuePairs.MPGENVALn}`，属于**源 wrapper** 的参数表 | 片段"搬家"到别的 wrapper 后 `ew` 变成外层，同名 key 指向**别的值**，缺失键为 null → 条件恒不成立 |

**影响面**：`/recruit/candidates`、人才档案列表、人才变更历史。实测除超管/集团管理员外
**候选人列表恒为空**（是 fail-closed、非越权泄漏，但功能不可用）。单条鉴权走的
`visible(TalentScopeTarget, ScopeCondition)` 纯 Java 谓词**不受影响**，是正确可用的。

**根因（诚实记录）**：P1 只做了**编译级**验证，从未在真实 wrapper 上执行过；P2/P3 之前也没有调用方，
所以缺陷潜伏到 P3 才暴露。**教训：凡"生成 SQL"的共享基础设施，必须在真实 MyBatis-Plus 上跑一次并断言输出片段。**

**修复口径（P3 执行）**：
1. 把可见性 OR 分支**合并为一次 `apply(...)`**：分支之间显式写 `OR`、整体加括号、值**内联为字面量**，
   不再使用 `{0}`/`{1}` 占位符（消除 MP 自动插 `AND` 与参数错位两个问题）。
2. 调用方**禁止**"片段搬家"，改为**把 wrapper 原样传入 Mapper**：
   `@Select("SELECT p.talent_id FROM hr_talent_profile p ${ew.customSqlSegment}")`，
   此时 `ew` 即源 wrapper，`WHERE` 前导正好是 `${ew.customSqlSegment}` 所需，分页总数亦正确。
3. `visible(...)` 纯 Java 判定逻辑**不动**。

| 1 | 领域事件统一**事务提交后**发布（`TransactionSynchronization#afterCommit`，无事务时立即发） | §21.6「涉及一致性的监听器使用事务提交后机制」；应聘域与背调域口径已一致 |
| 2 | 发布机制允许两种等价写法：应聘域用 `SpringUtils.context().publishEvent(...)`，背调域用**构造注入 `ApplicationEventPublisher`** | 后者让单测可脱离 Spring 上下文（本机 JVM 禁止 Mockito 自附加 Agent）；发布时机与载荷语义完全一致，**不强制统一** |
| 3 | 全局 `mybatis-encryptor` 由 `enable:false / BASE64` 改为 **`enable:true / AES`，密钥取自环境变量 `HR_ENCRYPT_KEY`** | 用户裁定。设计文档 §9.4/§15 要求电话、邮箱、背调明细**密文**落库；BASE64 只是编码不是加密。密钥**不进仓库**；缺失时首次加解密报错（fail-closed，不静默存明文） |
| 4 | 新增 6 个字典组（`recruit_job_status`、`recruit_rollover_result`、`recruit_background_status`、`recruit_background_failure_reason`、`recruit_interview_status`、`recruit_interview_method`），字典组由 23 增至 **29** | 用户裁定补齐。§10 未覆盖这些状态/结果编码，导致前端只能硬编码中文、后端无法 `@Translation` 回填标签。其中 `recruit_background_failure_reason` 的 7 个编码为**本次新定义**（§8.7 只写了"未通过原因分类"未枚举） |
| 5 | 人才主档新增契约外字段 `CandidateCreateBo.duplicateAck` | §3.1 要求"疑似重复不得静默创建"，但原契约未给"确认不是同一人"的入口；该字段即此入口 |
| 6 | 保留"中匹配"依赖 `hr_talent_resume.file_hash` / `hr_talent_education.school_name` 的 `EXISTS` 子查询 | 开发者曾误以为这两张表 P4 才建、建议删掉分支；**实测它们是 P1 交付物、表已存在**，分支可正常运行。若删掉，§21.15 中匹配只剩"姓名+公司"，能力白砍 |
| 7 | 附件业务记录鉴权 `AttachmentBizAccessChecker` **不得 fail-open**，统一收到人才可见范围判定 | 原实现"无实现即放行"等于：任何持有 `recruit:attachment:download` 的用户猜到 attachmentId 即可下载任意公司候选人附件（横向越权）。与模块内既有 fail-closed 姿态一致 |

### 7.6 并行开发的代价：共享文件写竞争（真实事故，务必留档）

P3 期间 `domainservice/TalentScopeDomainService.java` 被**两个 agent 并发重写**，产生过一版**比原缺陷更糟**的实现：

- 改成 `wrapper.apply(sql, params.toArray())`，但 SQL 里用的是 `?` 而不是 `{0}`；
- MyBatis-Plus 的 `apply(sql, values...)` **要求 `{0}`/`{1}` 占位符**，传 `?` 会**调用即抛**
  `MybatisPlusException: Please check the syntax correctness! sql not contains: "{0}"`
  （原缺陷只是运行期 SQL 语法错，这版是**调用即抛**）；
- 最终由后动手的一方用正确实现覆盖，并补了「片段中不得出现 `#{` / `?` / `{0}`，且
  `getParamNameValuePairs()` 必须为空」的断言，把这类回归钉死在测试里。

**教训（两条）**：
1. **授权 agent 修改共享文件前，必须先确认没有其他 agent 正在改同一个文件**——本轮我同时授权两条线改同一个方法，属调度失误。
2. **"生成 SQL"的共享基础设施必须用真实 MyBatis-Plus 断言输出片段**（含占位符与参数表是否为空），
   仅编译通过不足以发现此类缺陷——P1 的原始缺陷正是这样潜伏了两个阶段的。

### 7.7 已记录但暂不处理的已知限制

| 项 | 说明 |
|---|---|
| 背调「当前有效」判定 | `hr_recruit_background` 无 `current_flag`/`superseded` 编码，新背调只能用 `status=cancelled` 覆盖旧记录，与"人工取消"不可区分；且无唯一索引，高并发理论上可并存两条有效记录 |
| 附件版本号并发 | `(biz_type,biz_id,file_type,version_no)` 无唯一约束，靠"先 selectMax 再 insert"+事务，非严格并发安全（OSS 对象键含随机附件ID，不会互相覆盖） |
| 常量与枚举两处定义 | `RolloverResultEnum` ↔ `PlanRolloverDomainService.RESULT_*`、`InterviewStatusEnum` ↔ `RecruitInterviewServiceImpl.STATUS_*` 值一致但定义重复，存在漂移风险，待后续统一 |

### 7.8 计划任务状态自动刷新（P3-F）的落地口径与遗留

**已落地**：`execution_status` 由 `PlanItemStatusDomainService.resolveExecutionStatus(...)` 纯函数推导
（优先级 `pending_arrival > offer > interviewing > recruiting > pending`），由
`PlanItemStatusEventListener` 在**事务提交后**驱动刷新。更新语句只写 5 个派生列
（`credited_arrival_qty`/`remaining_qty`/`completion_status`/`execution_status`/`last_refresh_time`），
**绝不写 `control_status`/`control_reason`**（§7.1.5 硬约束，P2 既有断言仍绿）。

| # | 口径 | 说明 |
|---|---|---|
| 1 | 「任务已启动」= 所属 `hr_recruit_plan.status = executing` | `hr_recruit_plan_item` **无启动标记列**（DDL 缺口）。与 §7.1.4「出现有效招聘动作**或**人工启动」两条合起来覆盖原文语义 |
| 2 | `passed`（已完成）按**正向终态**处理，**不**从推导中剔除 | 它仍承载"待录用/待报到"语义。**只有负向终态 `rejected`/`withdrawn`/`talent_pool` 整体剔除（勿改）** |
| 3 | `paused`（暂缓）视为"仍有效"，所在阶段照常参与推导 | §21.14/§7.2 未定义暂缓对任务阶段的影响，不额外造冻结语义 |
| 4 | 阶段/结果编码未知或为空 → **忽略该条记录** | fail-safe：不因脏数据把任务状态推到错误阶段；空结果视为处理中 |
| 5 | 事件监听必须 `@TransactionalEventListener(fallbackExecution = true)` | 生产方用 `TransactionSynchronization#afterCommit` 在**事务已提交后**发布，此时无活动事务；**不加 `fallbackExecution` 事件会被静默丢弃** |
| 6 | 事件路径只调 `refreshItemStatus(itemId)`，不同步刷表头汇总 | 与 P2 报到路径一致；表头汇总由 `refreshItemsOfPlan` / 定时校准维护 |
