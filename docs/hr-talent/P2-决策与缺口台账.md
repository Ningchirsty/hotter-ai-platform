## 1. 定案的口径修订（相对 P1）

| 项 | P1 原写法 | 修订后 | 依据 / 原因 |
|---|---|---|---|
| 分页返回 | `PageQuery` + `TableDataInfo<T>` | **`PageQuery` + `PageResult` + `R<PageResult<T>>`** | 本基线 **v6.0.0 不存在 `TableDataInfo`**（全仓仅 1 处误引用）；`ruoyi-ai-gov` 全用 `PageResult` |

| 主键列名 | `@TableId(value = "id")`（SPEC-P2 初稿笔误） | **表级主键名**：`demand_id`/`change_id`/`plan_id`/`item_id`/`rollover_id`/`rel_id`/`job_id` | `hr_recruit.sql` 实际 DDL |
| 需求 `submitted → recruiting` | 未定义入口 | **新增显式 `confirm` 动作**（权限复用 `PERM_DEMAND_SUBMIT`，写 `confirmed_by/confirmed_time`） | 设计文档 §20「一期先采用**提交确认**」；不复用"再次 submit"这种含糊语义 |
| 需求暂停/关闭原因 | — | **记在 `hr_recruit_demand_change.reason`**，需求表不设原因列 | 已有变更历史表可承载，避免冗余列 |
| 来源类型大小写 | §9.4 写 `NEW`/`CARRYOVER` | **以小写 `new`/`carryover` 为准** | §10 与 DDL 均小写；§9.4 属文档内部口径不一致 |
| 表数量 | 36 张 | **37 张 + 4 张待增**（见 §4；P3 经用户裁定补入 `hr_recruit_plan_item_status_log`） | §9.2 是"建议包含"的表清单，§8.x 要求更多 |

## 5. 审计判定"不算缺口"的项（备查，避免重复提出）

- **派生/计算**：待招聘人数 `= max(需求人数 - 实际到岗, 0)`；当月计划人数/到岗汇总/结转人数 = `plan_item` 三列聚合；
  是否报到 = `arrival_date` 非空；渠道推荐/到面/通过/到岗 = 按 `application.source_channel_id` 统计；超期需求与招聘周期 = 派生。
- **已由其他表/列承载**：需求暂停/关闭原因 → `demand_change.reason`；需求计划月份/当月计划人数 → `plan_item`；
  专业与毕业院校 → `talent_education`；归属公司 → `owner_dept_id`；解析器版本 → `parse_task.parser_version`。
- **依据不足、未计入**：`job.post_id`（§20 为"可选关联"）、导入撤销字段、`plan_application_rel` 待人工分配标记、
  面试改期历史（倾向多条记录）、profile 保留到期/冻结/匿名化（§15.4 措辞为"预留"）、资料完整度（可计算）。

## 6. P2 落地时采纳的实现决定（已评审，勿在后续阶段误改）

| # | 决定 | 理由 |
|---|---|---|
| 1 | `POST /recruit/plans` 命中同公司同月表头时**报错**，不静默复用 | 静默返回他人表头会误导前端；结转内部另走 `ensureTargetPlan` 静默复用 |
| 2 | 结转自动创建的下月表头 `status=executing`；本批有成功结转后 `generated_flag=1` | 结转产物是执行中的任务，不是草稿 |
| 3 | **结转不复制 `job_id` / `demand_id`**，只复制岗位名称等执行信息快照 | `hr_recruit_job.plan_item_id` 是 N:1，复制 `job_id` 会造成跨月共享的岗位记录，与"每条计划任务独立跟进"冲突；岗位执行项由岗位域按需新建 |
| 4 | `completion_status` **不因暂停/取消冻结**，始终按人数计算；"已取消/暂停"只体现在主展示状态优先级 | 与 §4.2「按人数自动计算」一致；§21.15 伪代码在 CANCELLED/PAUSED 分支不改 completion，属表述差异，已在 JavaDoc 写明 |
| 5 | 结转 `result` 增加 `processing` 编码作为幂等占位闸门 | DDL 注释为"success/failed/skipped**等**稳定编码"，在其范围内；顺序为「占位插 processing → 建目标任务 → 回填 success + 原任务置 rolled_over」 |
| 6 | `GET /recruit/plan-items/similar` 返回 `PageResult<RecruitPlanItemVo>` | 只做"存在相似计划"提示，不参与合并（§7.1.1 禁止自动合并） |
| 7 | P2 中 `execution_status` 保持 `pending`；`refresh-status` 只重算 `remaining_qty`/`completion_status`/`last_refresh_time`，**绝不覆盖 `control_status`** | 应聘记录属 P3，尚无驱动源；"人工暂停不得被自动刷新覆盖"是 §7.1.5 硬约束 |
| 8 | 岗位域新增 `converter/AssistantIdsConverter`（`String ↔ Long[]`，`@Component`，经 `@AutoMapper(uses=...)` 接入） | 前端契约要 `Long[]`、DDL 列是 varchar 逗号串，MapStruct 同名不同类型会编译失败；注册 Bean 是 mapstruct-plus 生成的代码按 Bean 名取 `uses` 实例所必需 |
| 9 | 岗位 `assistantIds` **收发对称**：VO 与 BO 均为 `Long[]` | 避免"提交数组 / 读回字符串"的不对称；翻译另走只读 `getAssistantIdText()`（`@JsonIgnore`） |
| 10 | 岗位 `statusLabel` 不用 `@Translation`，改由 `JobStatusEnum` 只读 getter 兜底 | §10 无岗位状态字典组，不凭空造字典组 |
| 11 | 岗位域统一用 `ServiceException` + 中文提示，未用 `HrTalentErrorCode` | 该文件当时被并行 agent 修改，避免写冲突；SPEC §4.1 允许 |
| 12 | 结转每条来源任务在**独立 `REQUIRES_NEW` 事务**中执行，失败另起事务记 `failed + failure_reason + retry_count` | §9.6「单条失败应记录原因并允许安全重试」，不得回滚已成功条目 |

> **口径提醒**：`@Translation` 的 `USER_ID_TO_NICKNAME` / `USER_ID_TO_NAME` 实现**只支持单个 ID 或逗号分隔字符串**。
> 若把多值字段声明成数组，翻译会静默失败——多值场景必须另提供一个拼成逗号串的只读 getter 作为 `mapper` 源
> （岗位域的 `getAssistantIdText()` 即此模式）。

## 7. P3 落地时采纳的实现决定与"不算缺口"裁定

### 7.1 实现决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | 淘汰/候选人放弃/暂缓/人才保留**只改 `current_status`，不改 `current_stage`**；`stage_log.to_stage` 记等于 `from_stage` | 字典 `recruit_candidate_stage` 只有 9 个阶段值，没有这 4 个结果值；强行落码会与字典和前端不一致 |
| 2 | `POST /recruit/applications/{id}/transition` **不允许**直接进入 `arrived`，走 `/arrival` | 报到必须在同一事务内累加计划任务到岗人数并刷新状态（§21.7），独立 transition 会破坏原子性 |
| 3 | 报到放行条件 = 处于 `pending_arrival` **或** 已记录「邀约结果 + 计划报到日期」 | 等价满足 §7.2 第 5 条的资料要求，避免强制三步走 |
| 4 | `POST /{id}/transfer` 追加一条 `action_type=transfer` 的 `stage_log`（阶段未变） | 追溯"谁在何时把候选人转给了谁"；不违背 §8.5 的"只追加" |
| 5 | `/no-arrival` 的应聘结果码取 `withdrawn` | 字典 `recruit_application_result` 无「未报到」专用码，权宜口径；精确表达需补字典码 |
| 6 | 阶段历史**不提供删除接口** | §8.5 明确只追加，不允许业务人员物理删除 |
| 7 | `/recruit/applications` 与 `/recruit/candidates` 列表**都要套 `TalentScopeDomainService`** | §11.1「人才查询接口统一调用人才范围服务」，候选人列表会暴露人才档案信息 |
| 8 | 审计记录器（`support/SensitiveAuditRecorder`）**永不抛异常**，失败只记日志 | 审计失败不得让业务操作失败或回滚 |
| 9 | 领域事件在 `TransactionSynchronization#afterCommit` 发布（无事务时立即发） | §21.6「涉及一致性的监听器使用事务提交后机制」；且事件只承载派生刷新 |
| 10 | 报到路径**同步**调用 `IPlanItemStatusService.refreshItemStatus()`，而非仅靠事件 | §21.7 要求「报到 + 计划到岗计数 + 状态刷新」同事务；§11.1 禁止各服务自行拼接状态值 |

### 7.4 P1 遗留缺陷：`TalentScopeDomainService.visibleTalentWrapper()` 生成的 SQL 不可用（P3 修复）

**发现者**：P3 应聘域（在尝试给自己的列表套可见范围时，把领域服务拿到真实 MyBatis-Plus 上跑了一遍）。

**缺陷（我在 P1 写的 `visibleTalentWrapper(ScopeCondition)`，三处，任一处都足以致命）**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 用**多次 `wrapper.apply(...)`** 拼接可见性 OR 分支（`"(p.visibility_type='{0}'"` + `"OR (...)"` + `")"`） | MyBatis-Plus 会把相邻 `apply` 片段用 **AND** 连接 → 生成 `AND OR (...)`，并留下悬空 `AND )`，**SQL 语法报错** |
| 2 | `getCustomSqlSegment()` **自带 `WHERE`** | 调用方把它当片段二次拼接（如 `wrapper.apply(scope.getCustomSqlSegment())`）→ `... AND WHERE (...)`，语法报错 |
| 3 | 片段内参数是 `#{ew.paramNameValuePairs.MPGENVALn}`，属于**源 wrapper** 的参数表 | 片段"搬家"到别的 wrapper 后 `ew` 变成外层，同名 key 指向**别的值**，缺失键为 null → 条件恒不成立 |

**影响面**：`/recruit/candidates`、人才档案列表、人才变更历史。实测除超管/集团管理员外
**候选人列表恒为空**（是 fail-closed、非越权泄漏，但功能不可用）。单条鉴权走的
`visible(TalentScopeTarget, ScopeCondition)` 纯 Java 谓词**不受影响**，是正确可用的。

**根因（诚实记录）**：P1 只做了**编译级**验证，从未在真实 wrapper 上执行过；P2/P3 之前也没有调用方，
所以缺陷潜伏到 P3 才暴露。**教训：凡"生成 SQL"的共享基础设施，必须在真实 MyBatis-Plus 上跑一次并断言输出片段。**

**修复口径（P3 执行）**：
1. 把可见性 OR 分支**合并为一次 `apply(...)`**：分支之间显式写 `OR`、整体加括号、值**内联为字面量**，
   不再使用 `{0}`/`{1}` 占位符（消除 MP 自动插 `AND` 与参数错位两个问题）。
2. 调用方**禁止**"片段搬家"，改为**把 wrapper 原样传入 Mapper**：
   `@Select("SELECT p.talent_id FROM hr_talent_profile p ${ew.customSqlSegment}")`，
   此时 `ew` 即源 wrapper，`WHERE` 前导正好是 `${ew.customSqlSegment}` 所需，分页总数亦正确。
3. `visible(...)` 纯 Java 判定逻辑**不动**。

| 1 | 领域事件统一**事务提交后**发布（`TransactionSynchronization#afterCommit`，无事务时立即发） | §21.6「涉及一致性的监听器使用事务提交后机制」；应聘域与背调域口径已一致 |
| 2 | 发布机制允许两种等价写法：应聘域用 `SpringUtils.context().publishEvent(...)`，背调域用**构造注入 `ApplicationEventPublisher`** | 后者让单测可脱离 Spring 上下文（本机 JVM 禁止 Mockito 自附加 Agent）；发布时机与载荷语义完全一致，**不强制统一** |
| 3 | 全局 `mybatis-encryptor` 由 `enable:false / BASE64` 改为 **`enable:true / AES`，密钥取自环境变量 `HR_ENCRYPT_KEY`** | 用户裁定。设计文档 §9.4/§15 要求电话、邮箱、背调明细**密文**落库；BASE64 只是编码不是加密。密钥**不进仓库**；缺失时首次加解密报错（fail-closed，不静默存明文） |
| 4 | 新增 6 个字典组（`recruit_job_status`、`recruit_rollover_result`、`recruit_background_status`、`recruit_background_failure_reason`、`recruit_interview_status`、`recruit_interview_method`），字典组由 23 增至 **29** | 用户裁定补齐。§10 未覆盖这些状态/结果编码，导致前端只能硬编码中文、后端无法 `@Translation` 回填标签。其中 `recruit_background_failure_reason` 的 7 个编码为**本次新定义**（§8.7 只写了"未通过原因分类"未枚举） |

| 6 | 保留"中匹配"依赖 `hr_talent_resume.file_hash` / `hr_talent_education.school_name` 的 `EXISTS` 子查询 | 开发者曾误以为这两张表 P4 才建、建议删掉分支；**实测它们是 P1 交付物、表已存在**，分支可正常运行。若删掉，§21.15 中匹配只剩"姓名+公司"，能力白砍 |

### 7.6 并行开发的代价：共享文件写竞争（真实事故，务必留档）

P3 期间 `domainservice/TalentScopeDomainService.java` 被**两个 agent 并发重写**，产生过一版**比原缺陷更糟**的实现：

- 改成 `wrapper.apply(sql, params.toArray())`，但 SQL 里用的是 `?` 而不是 `{0}`；
- MyBatis-Plus 的 `apply(sql, values...)` **要求 `{0}`/`{1}` 占位符**，传 `?` 会**调用即抛**
  `MybatisPlusException: Please check the syntax correctness! sql not contains: "{0}"`
  （原缺陷只是运行期 SQL 语法错，这版是**调用即抛**）；
- 最终由后动手的一方用正确实现覆盖，并补了「片段中不得出现 `#{` / `?` / `{0}`，且
  `getParamNameValuePairs()` 必须为空」的断言，把这类回归钉死在测试里。

**教训（两条）**：
1. **授权 agent 修改共享文件前，必须先确认没有其他 agent 正在改同一个文件**——本轮我同时授权两条线改同一个方法，属调度失误。
2. **"生成 SQL"的共享基础设施必须用真实 MyBatis-Plus 断言输出片段**（含占位符与参数表是否为空），
   仅编译通过不足以发现此类缺陷——P1 的原始缺陷正是这样潜伏了两个阶段的。

### 8.1 3 个敏感权限登记了却零角色绑定（对非超管完全不可达）

DB 核查（`sys_menu` 有 `perms`，但 `sys_role_menu` 无该 `menu_id` 的任何行）发现：

| 权限 | 归属功能 | 核查前状态 |
|---|---|---|
| `recruit:background:view-sensitive` | 背调明细查看（P3-D） | 零绑定 |
| `talent:profile:phone-view` | 人才电话明文 | 零绑定 |
| `talent:resume:download` | 简历下载（P4-A） | 零绑定 |

对照：`recruit:candidate:phone-view` 是绑给集团招聘管理员的——**同类权限口径本就不一致**。
这三项在 P1 编写时被**刻意**留空（menu SQL 注释原文："高度敏感附件仍需独立权限 → 不授"），
但"任何角色都不默认持有"等于功能死亡。**这是产品与安全决策，主控未擅自裁定，提交用户决定。**

**用户裁定：按设计 §6 的职责绑给对应角色。** 已落地（两个 SQL 文件同步）：

| 权限 | 绑定角色 |
|---|---|
| `recruit:background:view-sensitive` | 集团招聘管理员 `hr_recruit_admin_group` |
| `talent:profile:phone-view` | 集团人才管理员 `hr_talent_admin_group` |
| `talent:resume:download` | 集团人才管理员 `hr_talent_admin_group` |

同时**修正了与 SQL 自相矛盾的注释**：原文称背调明细与候选人电话明文"按 §6 需单独授权，故本角色默认不授"，
但同一文件的 `sys_role_menu` 里 `recruit:candidate:phone-view` 早已绑给集团招聘管理员。
现改为：§6 的"不能查看其他公司的候选人明文和背调"**由可见范围（`TalentScopeDomainService`）落地，
不再靠"不授权限"实现**；公司招聘负责人仍不授这两项。

**已验证**：迁移脚本连跑两次（幂等）exit=0；DB 复查三条绑定精确落库；
`1766` 段 `sys_menu` 已**无任何孤儿权限**（SQL 反连接查询返回空）。

### 8.2 `purpose` 的空值校验放在参数校验层 → 被拒绝的敏感访问永不落审计

`PhoneViewBo.purpose` 原带 `@NotBlank`，而控制器有 `@Validated`：校验框架**先**返回 400，
服务层那条"purpose 为空 → 先写 `denied` 审计 → 再拒绝"的分支**永远不可达**。
后果：一次**被拒绝**的敏感访问完全不留痕——而它恰恰是最该留痕的（可能是越权探测），违反 §15.2。

**已修**：移除 `purpose` 的 `@NotBlank`（保留 `@Size(max=255)`），非空校验落到服务层。
口径与简历受控下载、附件受控下载一致。`PhoneViewPurposeAuditTest` 用**反射断言**锁死
"`purpose` 不带 `@NotBlank`、仍带 `@Size`"——锁的是**链路可达性**，任何人回退加回注解都会立刻红。

**派生缺陷（同因，已一并修复）**：`CandidateServiceImpl.viewPhone` 在"人才不存在/不可见"时
不写 `denied` 审计，而人才档案侧新端点会写。已修：落空时先写 `denied` 再抛错，且
**保持"不存在"与"不可见"不可区分**（不拆分错误信息，避免给出探测候选人是否存在的旁路）。

**但"不可区分"不能以牺牲可运维性为代价**——两类落空的处置方向完全不同：
- `no_application` = 该人才没有应聘记录（**数据没录**，要补数据）；
- `out_of_scope_or_absent` = 人才存在但在可见范围外（**权限配置问题**，要调授权）。

若审计里只有 `denied`，运维无从分辨。故改为用 `SensitiveAuditRecorder` 的 **6 参重载**把真实原因
写进 `detailJson`（`{"reason":"<枚举码>"}`），**对外异常类型与文案仍完全一致**，只有审计明细不同。
判定方式采用**显式分段捕获**（分别 try 包 `assertCandidate` 与 `getPhonePlain`），
**不按异常 message 匹配**——后者过于脆弱。

对应用例 `shouldRecordReasonOnlyInAuditDetail` 断言四件事：异常类与 message **相同**、
审计串最后一个 `|` 之前的主字段**相同**、两串整体**不同**、结尾分别为两个原因码。
即"对外不可区分"与"对内可诊断"两个约束**同时被锁死**。

### 8.3 人才档案页的电话明文按钮接错了端点与权限

前端实况：`views/hrtalent/talent-profile/index.vue` 两处按钮为 `v-hasPermi="['recruit:candidate:phone-view']"`，
`api/hrtalent/profile/index.ts` 调 `POST /recruit/candidates/{id}/phone-view`。两个后果：

1. **人才池成员查不了明文**：候选人侧端点会先断言该人才存在应聘记录，而"人才档案"最主要的场景正是**无应聘记录**的人才。后端 A 线已**专门新增**不要求应聘记录的端点，前端未接。
2. **归属角色看不到按钮**：`recruit:candidate:phone-view` 只绑给集团招聘管理员，人才档案页的归属角色是集团人才管理员——它没有该权限。

同时 `api/hrtalent/profile/index.ts` 与 `types.ts` 中留有一段**已过期且错误**的注释，
声称"本期只有 `/recruit/candidates/{id}/phone-view`，不存在 `/talent/profiles/{id}/phone-view`"。
**已要求修正为**：接 `POST /talent/profiles/{id}/phone-view`（权限 `talent:profile:phone-view`），并更正该注释。

### 8.5 新增门禁：`perm-orphan-chk.mjs`（孤儿权限检查）

8.1 是靠**人工偶然发现**的，不可接受。已补 `.tools/perm-orphan-chk.mjs` 作为可复跑门禁，检查：

| # | 检查项 | 为什么需要 |
|---|---|---|
| 1 | **arity** —— 命名空间内 `sys_menu` 行必须解析出 22 列 | **解析串位是检查器最危险的失效模式：不报错、却给出错误结论** |
| 2 | **逐文件孤儿** —— 每个定义权限的文件必须在该文件内绑定它 | 绑定若跨文件聚合，某一文件漏绑会被另一文件**掩盖** |
| 3 | 全局孤儿 | 综合所有文件仍无绑定 → 非超管不可达 |
| 4 | 重复 `menu_id` | 同一菜单 ID 被赋予不同 `perms` |

**刻意不检查**"同一 `perms` 挂在多个 `menu_id` 上"：这是 RuoYi 标准写法（C 菜单带 list 权限，
其下列表按钮镜像同一权限串，本模块 17 处均属此例）。对正常约定持续告警的检查器最终会被忽略。

**门禁本身也做了反向验证**（`.tools/_perm-negtest.mjs`，5 个场景全过）：基线 exit=0；
分别从两个文件抽掉绑定、两文件都抽掉、新增一条零绑定权限——**四种已知缺陷全部被抓到**。
理由：检查器"通过"本身不是证据，能抓到已知缺陷才算。

### 8.6 已知规格偏差：`minCompleteness`（资料完整度筛选）本期未实现，传入即拒绝

SPEC-P4 §2.6 依据设计文档 §8.17，把**「资料完整度」列为人才组合检索的一个条件**。
实现**未提供**该筛选：`TalentProfileServiceImpl.requireSupportedFilters` 在
`query.getMinCompleteness() != null` 时直接抛中文业务异常（fail-fast），
前端 `api/hrtalent/profile/types.ts` 同步声明"页面不提供该筛选条件"。

**理由（实现方的判断，成立）**：完整度是**跨表派生值**——由主档 15 个基础字段的填充率算出
（见 `TalentProfileServiceImpl.fillCompleteness`），主档表**没有完整度列**，本期也未物化。
在 SQL 侧按派生值筛选要么物化一列（DDL 变更 + 全写入路径维护 + 历史数据回填），
要么拼一个 15 项的表达式；两者都超出本期范围。**fail-fast 优于静默返回错误结果**。

**为什么不物化一列**：新增列属结构性变更，需用户裁定；且一旦物化就必须在**所有**主档写入路径维护，
漏一处即产生与实际填充分歧的脏值。故本期不物化。

**影响与后续**：人才列表与详情**仍会计算并展示**完整度（含 `completeness` / `completenessLevel`），
只有"按完整度筛选"不可用。若后续需要该筛选，建议路径：物化 `completeness` 列并回填
（需用户批准 DDL），或改为 SQL 侧 15 项表达式下推。

### 8.7 新增门禁：`api-unused-chk.mjs` 与 `menu-parity-chk.mjs`

8.3 / 8.4 同样是**人工偶然发现**的。已补 `.tools/api-unused-chk.mjs`：扫描
`ruoyi-hr-talent` 全部 `@RestController` 的映射路径，与 `frontend/src/api/hrtalent/**.ts`
的 `url:` 声明比对，列出**后端有端点但前端从未调用**的清单。

**默认只报告、不作门禁**（退出码恒 0，`--strict` 才失败）：后端端点不被前端调用**可能是有意的**
（外部集成、内部调用、运维接口），把"零调用"一律当缺陷会产生大量误报，最终被忽略——
与 §8.5 刻意不检查"重复 perm"是同一个判断。

**首轮实跑结果**：116 个端点，113 个有前端调用，**3 个零调用**，全部为同类缺陷：

| 端点 | 权限 | 缺失入口 |
|---|---|---|
| `DELETE /recruit/attachments/{ids}` | `recruit:attachment:delete`（已登记已绑定） | 附件组件无删除按钮 |
| `GET /recruit/audits/export` | `recruit:audit:export`（已登记已绑定） | 审计页无导出按钮 |
| `GET /recruit/plan-items/{id}/status-logs` | 沿用既有查询权限 | 计划任务页无状态变更日志入口（该表正是用户裁定新增的） |

**工具自身的缺陷也留档**：首版提取器只认纯字面量与模板字面量，漏了**字符串拼接**
（`url: '/talent/profiles/' + id`）——该写法在仓库中有 31 处，导致 116 个端点里 **34 个被误报**为"零调用"。
修好后误报降到 3 个。**一个误报率高的检查器和没有检查器一样没用**，所以"通过/输出"必须用真实数据核对比例。

#### `menu-parity-chk.mjs` —— 初始化脚本与迁移脚本的等价性

**新装环境跑 `hr_talent_menu.sql`，已装环境跑 `hr_talent_migration.sql`**。两者若分叉，
会出现"新装能用、升级不能用"（或反之），且**不会立刻报错**——只在特定环境的特定操作上失败，
典型症状是"我本地好的、线上 403"。故补此门禁，比较 `1766` 命名空间的：

- `sys_menu`：`menu_id → menu_type|perms|menu_name`
- `sys_role_menu`：`role_id -> menu_id` 全集

**当前结果**：112 行菜单、246 条角色绑定，两脚本**完全等价**。
反向验证：从迁移脚本删除 1 条绑定 → 246 → 245，`exit=1` 并精确报出 `1766100000000000002->1766000000000002702`。

> **反向验证本身也会失效，必须检查它是否真的改变了输入。** 该门禁第一次反向验证"通过"了，
> 原因是我用来测试的那条绑定**在原文件中已存在**，集合未发生变化（计数仍为 246/246 就是证据）。
> 修正为"从迁移脚本删除一条既有绑定"后才真正验证成功。这与 §8.8 第 2 条是同一类错误：
> **"没报错"不等于"验证有效"，必须确认输入确实被改动。**

### 8.8 敏感台账导出复用 `talent:profile:phone-view` 作为「独立权限」（有意决定，可回退）

SPEC-P4 §2.6 依据 §8.20 要求：**敏感台账**（姓名、联系方式、薪资、附件访问地址）导出
"**需要独立权限和导出原因**"。实现选择**复用** `talent:profile:phone-view` 作为该"独立权限"，
**不新增权限串**。理由见 `TalentExportServiceImpl` 类注释第 73 行与独立权限判定方法第 746-762 行
（原文："本期不新增权限串，因此无需改动菜单 SQL（复用既有独立按钮，符合 §8.20「独立权限」要求）"）。

**语义**：`talent:profile:export` 是导出的**基础**权限；要做**敏感**台账还需再具备
"已被信任可访问敏感数据"的 `talent:profile:phone-view`。即"能导出敏感数据"蕴含"已被授权访问敏感数据"，
逻辑自洽；且与 §8.19「共享授权不自动授予电话明文…与导出权限」的隔离要求不冲突。

**已知代价（若需变更，改动面很小）**：

| 代价 | 说明 |
|---|---|
| 无法分离授权 | 不能只授"敏感台账导出"而不授"电话明文查看"。当前二者绑给同一角色（集团人才管理员），实际无差别 |
| 报错文案暴露内部权限名 | 拒绝时提示"无权导出敏感台账：需要独立权限 `talent:profile:phone-view`"，运维可据此授权，但字面上"导出报电话权限"略显跳跃 |

**若后续要求分离**：新增权限串 `talent:profile:export-sensitive`（`HrTalentConstants` + 两个 SQL 文件各加 1 个 F 按钮 + 绑角色）、
把 `TalentExportServiceImpl` 的 `hasSensitiveExportPermission()` 换用新串、改前端 tooltip 文案即可；
**新增权限串后必须同步两个 SQL 文件**，否则接口对非超管永远 403（SPEC-P4 §2.6 明确警告过这一点）。

### 8.9 核查方法论教训（留档以防复发）
1. **不采信自我报告。** 本轮 5 项缺陷全部由主控的交叉核查发现，没有一项是 agent 自报的。各 agent 的报告都真实，但**各自只看得见自己那一层**——控制器、SQL、前端分属不同 agent 时，"两端没接上"不归任何人负责。
2. **"通过"必须用已知缺陷反向验证。** 新版检查器首次运行报"通过"，但反向验证立刻暴露它**抓不到"单文件漏绑"**（跨文件聚合掩盖）——而那正是它存在的理由。修完盲区才敢用。
3. **负数测试改写文件必须保真。** 用 PowerShell `Set-Content -Encoding utf8` 重写 SQL 副本**不保真**：实测加 BOM、字节数 115880 → 125105 被改变（已在 `hr_talent_menu.sql` 上复现）。副本被改坏后，旧版检查器**静默**产出了 14 处假"重复 id"结论。现负例一律改用 node 改写文件。
4. **`-D` 参数经 `.cmd` 包装脚本交给 PowerShell 会被拆碎**（`-Dmaven.test.skip=false` 变成 `-Dmaven` + `.test.skip=false`，Maven 报 `Unknown lifecycle phase ".test.skip=false"`）——而 Maven 仍然退出并留下"看起来像失败"的痕迹时，很容易被误读成测试失败。改用 `cmd /c "…"` 单字符串调用。**一次"测试失败"其实是调用方式错误，测试根本没跑。**
5. **解析不确定性优先怀疑来源，而非重跑。** 同一检查器在真实仓库连跑 3 次通过、在副本上失败，第一反应应是"两次输入不同"，而不是"重跑看看"。
6. **"没报错"不等于"验证有效"。** `menu-parity-chk.mjs` 的第一次反向验证"通过"了，原因是测试注入的那条绑定**在原文件中已存在**，输入根本没变（可对照计数 246/246 未动即知）。**反向验证必须确认输入确实被改动**，否则它验证的是"什么都没发生"。

### 8.11 6 个菜单指向不存在的页面文件（比"缺一个按钮"严重）

**发现经过**：为核查"审计页为何没有导出按钮"，才发现 **`views/hrtalent/audit/index.vue` 这个文件从未存在**——
菜单第 14 项 `敏感操作审计` 早已注册 `component='hrtalent/audit/index'`、`perms='recruit:audit:list'`，
但页面文件是空的。用户点进去得不到 404 提示，而是**空白页**。

**根因（重要）**：前端 `store/modules/permission.ts` 用 `import.meta.glob` 预建查找表，
`loadView()` 找不到文件时**返回 `undefined` 而不抛错**：

```ts
export const loadView = (view: any, name: string) => {
  const loader = viewModuleMap.get(view);
  if (loader) return createCustomNameComponent(loader, { name });
  return undefined;            // ← 缺文件时静默降级
};
```

好处是**不会崩掉整棵路由树**（其它页面照常可用）；坏处是**任何构建、lint、单测都不会报错**，
因为不存在的文件没有任何构建产物。这也是"看代码"永远发现不了这一类的原因。

**全量核查结果（`menu-page-chk.mjs`）**：另查出 5 个同类菜单，且比审计页更严重——
它们的**整层功能都不存在**（实体/Mapper/服务/控制器/前端页面全缺），只有 DDL、权限常量、
菜单与角色绑定在 P1 就位：

| 菜单 | component | 表 | 权限常量 | 后端 | 前端 | 归属 |
|---|---|---|---|---|---|---|
| 管理驾驶舱 | `hrtalent/dashboard/index` | —（统计派生） | ✅ | ❌ | ❌ | 阶段 4（SPEC-P2/P4 §0 明确排除） |
| 招聘渠道 | `hrtalent/channel/index` | `hr_recruit_channel`(+`_survey`) | ✅ | ❌ | ❌ | **未被指派到任何一期** |
| 同行信息 | `hrtalent/peer/index` | `hr_recruit_peer_company` | ✅ | ❌ | ❌ | **未被指派到任何一期** |
| 招聘标准 | `hrtalent/standard/index` | `hr_recruit_standard` | ✅ | ❌ | ❌ | **未被指派到任何一期** |
| 数据导入中心 | `hrtalent/import-center/index` | `hr_recruit_import_batch/_error` | ✅ | ❌ | ❌ | 阶段 4（SPEC-P2/P4 §0 明确排除） |

**用户裁定：5 个全部先隐藏（`visible='1'`），功能另行排期。**

处置细节：
- 只改 `visible`，**不动 `status`**（`status='1'` 是"停用"，语义不同，会把菜单当作已废弃处理）。
- 其下的 **F 按钮（权限串）保留不动**——权限已绑定角色，功能上线后无需再改权限配置。
- 功能实现后把 `visible` 改回 `'0'` 即恢复显示。
- 审计页（第 14 项）**不隐藏**：该功能（列表 + 导出）后端完整、页面已补建，属已交付。

**门禁设计**：`menu-page-chk.mjs` 区分两种情况——**可见菜单缺页面 = 错误（exit 1）**，
**已隐藏菜单缺页面 = 已知项（仅报告）**。理由同 §8.5：对着一项有意的决定持续告警的检查器会被忽略。

### 8.12 部署陷阱：`insert ignore` 无法把「字段修改」下发到已有库

**发现经过**：把 5 个菜单改成 `visible='1'`（两个 SQL 文件都改了、`menu-parity-chk` 也通过）之后，
**DB 复查发现 `visible` 仍然是 `0`** —— 改动完全没有生效。

**根因**：迁移脚本通篇使用 `insert ignore into ... values(...)`。它只保证"**行不存在时插入**"，
**对已存在的行一律跳过**。因此凡是"修改某个已发布菜单的字段值"，只改 insert 语句，
**在新装库上生效、在升级库上静默不生效**，且不报任何错。

**这是本项目最容易造成"我本地是好的"的陷阱**，而且：

> **`menu-parity-chk.mjs` 发现不了这一类** —— 它比较的是两个 SQL **文件**是否一致；
> 而这个陷阱的危害恰恰是"文件一致，但 DB 不跟随文件"。**必须拿真实 DB 与初始化脚本对照。**

**修复**：在 `hr_talent_migration.sql` 的四、菜单段之后，追加显式 UPDATE（放在 insert **之后**）：
新装库 insert 已写入正确值、UPDATE 为幂等空操作；升级库由 UPDATE 修正。

```sql
update sys_menu set visible = '1'
 where menu_id in (1766000000000000101, 1766000000000000109, 1766000000000000110,
                   1766000000000000111, 1766000000000000112);
```

**验证**：迁移重跑后 DB 复查 —— 脚本与 DB 的可见菜单数均为 **107**，`visible/status/perms/component`
四项完全一致（`db-menu-sync-chk.mjs`，含反向验证）。

**今后规则（写入约束）**：
1. **凡改动既有菜单行的任何字段，必须在迁移脚本中追加对应 `update`**，不能只改 insert。
2. 新增行仍用 `insert ignore`（保证幂等与可重复执行）。
3. 上线前用 `db-menu-sync-chk.mjs` 对照一次真实库，不要只看文件。
